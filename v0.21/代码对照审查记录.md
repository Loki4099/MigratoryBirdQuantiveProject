## 1. 审查方式

本轮不直接开发 v0.21。每个阶段均按以下顺序推进：

1. 阅读当前代码、数据库迁移、Catalog、API、前端和测试；
2. 对照 v0.21 方案，区分“现有能力、可扩展能力、必须新增能力”；
3. 记录建议决策和未决问题；
4. 双方确认本阶段无疑问；
5. 再进入下一阶段。

建议阶段顺序：

0. 整体设计与生命周期；
1. Asset / Catalog / Data；
2. Factor；
3. Signal；
4. Model；
5. Strategy；
6. Experiment / Research Workspace；
7. Product Release / Monitoring；
8. 跨阶段集成、迁移、性能与发布验收。

将 Asset、Catalog、Data 放在同一阶段，是因为当前代码中资产身份、Universe、数据需求、数据发布和 Eligibility 是不可分割的正式输入链，单独只讨论资产页面会遗漏 point-in-time 与可研究性问题。

## 2. 阶段 0：整体设计——代码事实

### 2.1 当前架构

v0.2 是一个 PostgreSQL + Python/FastAPI + React 的模块化单体，正式领域为：

```text
Catalog → Data → Factor → Signal → Model → Strategy → Experiment
              ↘        Lineage / Ops        ↗
```

当前代码明确划分九个领域：`catalog`、`data`、`factor`、`signal`、`model`、`strategy`、`experiment`、`lineage`、`ops`。核心计算遵循 Calculator / Service / Repository 或 Publication Service 分层，前端不重新计算金融结果。

### 2.2 已有的可靠底座

- Artifact 支持不可变发布、精确依赖、语义指纹、内容哈希和生命周期审计；
- PostgreSQL 触发器阻止已发布对象被静默修改，并校验跨层依赖；
- `ops.run_attempt`、`run_event`、`run_error`、`run_artifact`、`quality_check_result` 已存在；
- Experiment 已能记录运行步骤、失败、质量检查、结果复用和输出 Artifact；
- Strategy Grid 和 Experiment Suite 已支持批量物化及部分并发；
- API 与 React 已覆盖资产、数据、因子、信号、模型、策略、实验、比较和血缘的只读展示；
- 数据库已到最新迁移，无缺失 Schema；
- 213 个 Python 单元测试和 10 个前端测试通过；前端 typecheck 与 lint 通过。

### 2.3 v0.21 不能直接复用的边界

1. 当前 FastAPI 全部是 GET，只读语义写入 `ApiContext`；没有研究草稿、编译、提交任务、人工审核或产品状态写接口。
2. 当前 CLI 调用计算服务时仍以同步执行为主；`run_attempt` 能记录过程，但还不是一个由独立 Worker 消费的持久任务队列。
3. 当前 Strategy Grid 以固定 Catalog 和 Model × Strategy × K × Frequency 展开，不具备前端逐层选择、逐边兼容校验和 Compiled Research Spec。
4. 当前代码中的“accepted result”表示通过系统完整性约束后发布的正式 Experiment Result，不表示研究者人工认可。
5. 当前 `Strategy Product` 是“模型 + 策略 + Universe + 执行规则”的研究身份，不是 v0.21 需要持续观察、暂停和退役的 `Product Release`。
6. 当前没有产品监控快照、人工复核、Warning Event 和发布后表现轨道。
7. 仓库仍保留部分 v0.1 旧命名空间，例如复数形式的 `factors`、`signals`、`backtest`、旧 `web` 与 `persistence`。v0.21 不应把新功能接到这些旧入口上。

## 3. 阶段 0：建议冻结的架构决策

以下结论已由双方确认。D0.2 的前端落位按项目所有者的补充意见冻结。

### D0.1 继续使用模块化单体

v0.21 不拆微服务。FastAPI、后台 Worker、领域服务和 React 继续位于同一仓库、共享同一 PostgreSQL，但以进程边界隔离 Web 请求和长时间计算。

原因：现有不可变发布和数据库约束已经是系统最有价值的底座；拆服务不会缩短回测时间，反而会增加分布式事务、部署和调试成本。

### D0.2 新增 Workspace 与 Product 两个正式模块

建议把后端正式边界从九个扩展为十一个：

- `workspace`：Research Draft、选择上下文、兼容性矩阵、Compiled Research Spec、规模估算和运行提交；
- `product`：Product Release、Monitoring Snapshot、Warning Event、Review Decision 和生命周期。

`workspace` 只编排并引用各研究层的已发布版本，不复制 Factor、Signal、Model 或 Strategy 算法。`product` 位于 Experiment Result 下游，不取代 `Strategy Product`。

前端落位冻结为：

- `Workspace` 替换当前顶层 `Research desk`，成为研究选择、兼容性预检、任务状态和结果入口；
- `Products` 替换当前独立 `Compare` 导航，承载产品发布、发布后监控、产品间比较和复核；
- `Data` 移除独立前端导航与页面入口；数据覆盖、质量、版本和 Eligibility 摘要分别进入 `Workspace` 与 `Assets`，完整血缘仍可从 `Artifacts` 查看；
- 现有 Compare 后端能力不删除，实验结果比较放入 `Experiments`，产品版本比较放入 `Products`，避免保留第三个重复入口。

### D0.3 Mutable Draft 与 Immutable Spec 分离

- Research Draft 是可修改、可自动保存、可复制的工作对象，不作为正式研究证据；
- 每次重要修改增加 revision，并使用乐观锁防止覆盖；
- Compile 成功后发布不可变 `Compiled Research Spec` Artifact；
- Run 只能引用 Compiled Spec，不能直接引用仍可变化的 Draft；
- 相同语义配置复用同一指纹和既有结果。

这样既保留前端编辑体验，也不破坏 v0.2 的不可变研究链。

### D0.4 系统结果与人工选择分离

建议统一术语：

| 对象 | 含义 |
| --- | --- |
| Accepted Experiment Result | 系统计算完成、质量约束通过并已不可变发布；Accepted不是人工点赞 |
| Promotion Decision | 研究者从Formal Result详情手动选择升级Product的审计事件 |
| Product Version / Enrollment | 从同一Qualification Context的6/6结果和Promotion Decision原子创建 |

v0.2 数据库中的 `accepted_run_attempt_id` 可暂时作为内部兼容字段保留，但 v0.21 API、页面和新表不再把它解释成人工接受。

### D0.5 使用数据库持久队列与独立 Worker

建议不引入 Redis/Celery。API 只完成校验、写入 queued Run/Command 并立即返回 Run ID；单独的 `style-rotation worker` 进程从 PostgreSQL 领取任务并调用现有 Service/Publication Service。

要求：

- 使用数据库锁保证同一任务不会被两个 Worker 同时领取；
- Run Attempt 继续保留每次失败和重试；
- 刷新页面或重启 API 不丢任务；
- Worker 中止后可识别长期无心跳任务并人工重试；
- 首版支持单机 1～N 个 Worker，不承诺分布式集群。

### D0.6 保留 GET 只读原则，新增受控 Command API

“浏览器不计算金融结果、GET 不改变状态”继续保留。v0.21 在 `/api/v2` 下增加显式 POST Command 接口，API 只做权限/输入/状态校验和命令提交，不包含金融算法。

所有关键写操作使用 Idempotency Key、审计事件和明确状态机。已发布 Artifact 仍不能通过 API 修改。

### D0.7 v0.21 继续定位为本地单用户内部研究系统

建议 v0.21 继续只监听 loopback，不在本版引入账号、角色和公网部署。审计操作者使用本地配置的稳定 `researcher_id`；未来若增加客户视图，应建立独立的只读展示权限，而不是直接暴露研究写接口。

### D0.8 不进行 v0.1 遗留代码的大爆炸清理

v0.21 新代码只接入正式的单数领域模块和 v0.2 Schema。对旧模块建立弃用清单与依赖守卫；仅在旧依赖阻塞动态 Universe、参数扩展或测试隔离时做小范围迁移，不把仓库清理变成 v0.21 的主目标。

## 5. 阶段 1：Asset / Catalog / Data——代码事实

### 5.1 当前真实规模与对象

当前正式数据库只有：

- 5 个 ETF Asset：IWF、IWD、IWO、IWN、SPY；
- 1 个静态 Universe Version，其中 4 个 candidate、1 个 benchmark；
- 2 个单值分类方案：`asset_class`、`style_exposure`；
- 市场数据来源为 Yahoo/yfinance OHLCV，利率来源为 FRED DGS3MO；
- canonical 数据约 6.3 万行，derived 数据约 0.6 万行；
- Eligibility 要求固定 Universe 的每个成员在整个请求区间内完整可用。

当前 Asset/Universe 基础并非从零开始：Asset、时效性 Identifier、Listing、Symbol 历史、分类、Universe Definition/Version、Data Requirement、Bundle 和 Eligibility 均已有不可变发布与数据库约束。

### 5.2 无法直接承载 v0.21 的部分

1. 当前 `asset` 没有独立 `issuer`，无法按发行人去重双重股权类别。
2. 当前 Universe Version 只有一张固定成员表，没有 rank date、effective date、季度快照、候选排名输入和排除原因。
3. 当前 Eligibility 每个资产只有一个总体可用区间，并要求所有成员完整覆盖全历史；新上市、退市、季度进出和临时不可交易股票会让整池失败。
4. Factor 与 Strategy 发布代码把 Universe candidates 读取成一个贯穿全历史的固定集合，并要求每个决策日都存在全部 candidate 的模型输出。
5. Catalog 分类在同一 Scheme/时点只允许一个值，不能直接表达一个资产同时具有多个防御角色或搜索标签。
6. 当前数据契约和质量规则仍包含“5 个 ETF 日期集合一致”、`us_etf_daily_market`、固定 symbols 等 v0.2 假设。
7. Yahoo快照明确声明它不是历史 vendor vintage；当前数据没有 point-in-time shares outstanding、可靠退市证券母表和发行人映射，因此不能据此声称完成了正式 `US Liquid Large-Cap 300 PIT` 历史研究。
8. SGOV 成立于 2020-05-26，不能作为从 2007 年开始的防御篮子成分回填历史。

## 6. 阶段 1：建议冻结的设计

### D1.1 Asset Identity 扩展

保留现有 Asset/Listing/Identifier 结构，并新增：

- `issuer`：稳定发行人身份；
- `security_issuer_assignment`：Security 到 Issuer 的时效映射；
- `asset_alias`：公司简称、英文名称、旧名称、常见搜索词和规范化搜索文本；
- `asset_tag`：允许同一资产同时拥有多个用途、暴露和防御角色标签；
- `asset_capability_snapshot`：Cataloged → Reference Data → Canonical Ready → Research Ready → Strategy Ready → Product Ready，并记录缺失门槛与证据 Artifact。

股票 Asset 表示可交易 Security，不把 Issuer 与 Ticker 当成同一个对象；Ticker 继续属于有时效的 Listing Symbol。

### D1.2 动态 Universe 使用“方法版本 + 历史发布 + 时点快照”

建议正式对象为：

```text
Universe Definition
→ Universe Methodology Version
→ Universe History Publication（固定 as-of 与覆盖区间）
→ Quarterly Universe Snapshot（rank/effective 时间）
→ Candidate Evaluation（输入值、排名、排除原因）
→ Membership（该快照选中的 Security 与 Issuer）
```

同一方法延伸到新季度时发布新的 History Version，不修改旧历史。策略引用完整 Universe History Publication，而不是把某一个季度的300只股票冻结到整个回测区间。

### D1.3 Eligibility 改为时点/区间语义

- Eligibility 只评价资产在其有效 Membership 区间内是否可研究；
- 每个决策日产生当期合法候选集合；
- 上市前、退出后不算缺失；
- Membership 生效后仍未完成 warmup 的资产暂时不可用，并显示原因；
- 停牌、数据断裂、退市和缺失模型分数按明确 reason code 处理；
- 不再要求300只股票全部覆盖整个历史，也不允许静默把有问题资产从整段历史删除。

对应的 Factor/Signal/Model/Strategy 如何消费逐时点集合，将在各自阶段确认；本阶段只冻结上游数据语义。

### D1.4 数据接口去 ETF 硬编码

- 将 `us_etf_daily_market` 泛化为有 Instrument/Series 语义的市场数据定义；
- 获取任务按 Dataset Partition / Asset Batch 执行，不再依赖固定 `REQUIRED_SYMBOLS`；
- 质量检查改为逐资产覆盖、交易日缺口、公司行动、身份映射和 Membership 区间一致性；
- Provider Adapter 保持可替换，Yahoo只能作为适合其能力的来源，不能承担不存在的PIT基本面与退市母表语义；
- 300只股票的OHLCV可继续存储于PostgreSQL；是否为下游数千万行Factor Value增加分区或列式Artifact，留到Factor性能阶段决定。

### D1.5 Data 页面移除后的信息归属

| 原 Data 页面内容 | v0.21 去向 |
| --- | --- |
| 当前选择的数据覆盖、Eligibility、阻塞原因 | Workspace 编译与预检摘要 |
| 单资产覆盖、成熟度、缺口、Listing/Identifier | Assets 卡片与详情 |
| Universe重构、候选排除、成员变化 | Assets / Universe 详情 |
| Dataset Bundle 与精确版本 | Workspace 运行清单、Experiment详情 |
| 原始快照、完整血缘、质量事件 | System / Artifacts |

后端 `data` 领域和只读查询继续存在；删除的只是重复的独立导航与页面。

### D1.6 防御篮子拆成两个不可混淆的版本

1. `Standard Defensive Basket – Long History v1`
   - Synthetic Reserve 40%
   - IEF 25%
   - TLT 10%
   - TIP 15%
   - IAU 10%
   - 用于覆盖 v0.2 长历史的研究基线；Synthetic Reserve 明确不是可成交证券。

2. `Standard Defensive Basket – Tradable v1`
   - SGOV 40%
   - IEF 25%
   - TLT 10%
   - TIP 15%
   - IAU 10%
   - 只能从所有成分真实可用且完成暖机后开始；不得把 SGOV 回填到 2020-05-26 之前。

二者是两个不同 Basket Definition，结果不可伪装成同一个全历史产品。

### D1.7 免费数据条件下的股票路径

正式 `US Liquid Large-Cap 300 PIT` 必须有可核验的历史证券母表、退市证券、point-in-time shares outstanding/market cap、公司行动和发行人映射。

在没有满足条件的数据源时，允许发布：

- `US Liquid Large-Cap 300 Current Snapshot`：用于界面、前瞻监控和工程演示；
- 或明确命名的 non-PIT / exploratory 历史股票池。

这类结果必须显示 Survivorship/PIT Warning，可运行探索性实验，但不能升级为 Product Release，也不能与正式PIT结果混排。系统接口仍按正式PIT能力设计，以后替换Provider而不是重写研究链。

### D1.8 Assets 前端必须整体重做

Assets 不是对现有五张卡片做增量修补，而是新的资产目录与数据入口：

1. 首屏展示 Asset Class / Instrument Type 分类信息卡；
2. 点击分类后进入该类资产卡片，并保留跨分类全局搜索；
3. 搜索同时匹配 symbol、当前/历史名称、英文名称、issuer、identifier、alias、资产类别、用途和标签；一个查询可以命中多个资产；
4. 资产详情显示身份、Listing、分类、能力成熟度、Universe历史、数据覆盖、质量与阻塞原因；
5. 提供清洗后数据的网页下载，下载必须绑定精确 Dataset Artifact/Version，不由前端重算；
6. 单资产默认提供复权价格、收益/回撤、成交量或ADV、覆盖与缺失等简单分析图表；
7. 小规模单资产下载默认支持 CSV；大Universe或长区间批量导出支持 Parquet 或压缩包，并附带版本、字段、时间范围、指纹和数据许可说明；
8. Workspace中的勾选状态与Assets详情跳转可以恢复，但Assets详情页本身不修改已发布数据。

## 7. 阶段 1 确认结果

1. **股票数据路径**：接受先实现正式PIT接口与规则；无合格数据源时仅以 Current Snapshot / Exploratory 身份演示并禁止升级产品。
2. **防御篮子**：接受拆成长历史 Synthetic Reserve 版本与 2020 年后 SGOV 可交易版本，禁止自动拼接。
3. **动态Universe模型**：接受方法版本、历史发布、季度快照、候选评价、成员关系和时点Eligibility的拆分。
4. **Assets前端**：确认按分类、搜索、清洗后数据下载和简单分析图表进行整体重做。

阶段 1 已完成，进入 Factor 阶段。

## 8. 阶段 2：Factor——代码事实

### 8.1 当前实现

v0.2 已发布：

- 12 个 Factor Definition、28 个固定 Factor Variant；
- 六个家族：return、trend、oscillator、tail distribution、risk、liquidity；
- 输入字段仅限 `close_adj`、`close_raw`、`volume_raw`；
- 12 个 canonical、13 个 horizon anchor、2 个 sensitivity、1 个 exploratory Variant；
- 当前正式诊断一次覆盖28个Dataset、5个资产、90,160个观测和378对相关性；
- Factor层已有定义、Variant、Dataset、Value、分布摘要、相关性、Issue、Artifact和血缘。

前端目前把每个 Factor Variant 展示为一张诊断卡，能显示公式、参数、分布、相关性和质量，但没有搜索、多选、Definition聚合、详情页、下载或Workspace选择状态。

### 8.2 动态资产池下的冲突

1. 当前 Calculator 要求所有资产在请求区间拥有完全相同的日期；任何不对齐都会让整个Variant失败。
2. coverage内任意一个因子值未定义或非有限，都会让整个Dataset失败。
3. Factor发布要求Universe全部成员Eligibility通过，再一次性计算Catalog中的全部28个Variant。
4. Factor Dataset直接绑定静态Universe Version；季度成员变化会导致重复物化，难以复用同一资产已经算好的Factor Value。
5. 相关性把所有 asset-date 观测混在一起计算一个Spearman值，可能混合时间序列差异和横截面差异；对300股横截面研究不够准确。
6. 当前 `missing_count` 实际恒为零，因为缺失在进入诊断前已经使发布失败。
7. 当前Catalog只有机器key、formula和参数，缺少适合搜索和信息卡的中英文名称、说明、用途标签与数据要求摘要。

## 9. 阶段 2：建议冻结的设计

### D2.1 Factor步骤选择Definition与已发布Variant，Signal反向验证依赖

Workspace的Factor卡片以12个 Factor Definition 为选择单位，而不是直接铺开28张Variant卡：

- 卡片复选框支持多选Definition；
- 选中Definition的作用是筛选其下游Signal候选；
- 卡片详情展开该Definition下的固定Variant、参数、诊断和血缘；
- 用户可在卡内单选或多选已发布Variant以主动缩小下游Signal范围，但不能编辑参数；
- 最终选择具体Signal后，Compiler仍从Signal Version反向验证并冻结精确Factor Variant与Dataset依赖。

这样“选择Factor”保持清晰的研究认知，同时最终运行精确到不可变Variant；勾选Definition不等于默认计算其全部参数版本。

### D2.2 v0.21冻结现有公式库，扩展契约而非扩充研究结论

- v0.21 首批继续使用现有12个Derived Factor Definition/28个Variant，并补充直接引用Canonical字段的Raw Factor Definition；
- 不在前端创建公式或修改参数；
- 新增中英文名称、说明、家族、输入序列、频率、单位、时间语义、用途和搜索标签；
- Factor Input Contract从三个硬编码字段改为版本化 `required_series`，为以后PIT基本面、宏观和多资产数据预留接口；
- 没有合格PIT基本面数据前，不在本版伪造估值、质量或财务因子。

Raw Factor首批至少包括 `open_raw`、`high_raw`、`low_raw`、`close_raw`、`close_adj`、`volume_raw`；可根据正式数据契约增加 `open_adj/high_adj/low_adj`、公司行动或参考序列。这里的“Raw”表示没有经过Factor公式变换，并不表示绕过清洗直接使用供应商脏数据。

Raw Factor通过版本化字段引用或统一读取视图指向Canonical Dataset，不为相同OHLCV再复制一份Factor Value；但它在Factor库中拥有卡片、单位、时点语义、覆盖、下载和血缘，并可被注册Signal显式引用。

### D2.3 局部可用性替代整批失败

每个预期Factor Observation具有明确状态：

| 状态 | 含义 |
| --- | --- |
| `valid` | 有有限数值，可供Signal消费 |
| `warming_up` | Membership已生效但历史观察数不足 |
| `input_missing` | 上游已声明缺失或交易中断 |
| `undefined` | 数学上不可定义，例如窗口内零方差 |
| `quality_blocked` | 输入存在阻断级质量问题 |

上市前、退出后和不属于当期Universe的日期不生成Factor缺失记录。局部不可用必须保留reason code与计数，不静默删除资产；只有实现不存在、参数契约错误、输出非法或系统性覆盖低于发布门槛时才阻止整个发布。

Signal阶段再声明各Signal是否允许哪些Factor状态以及如何处理，Factor本身不填充数值、不赋方向。

若某资产/指数在某时点缺少对应Canonical输入，则该时点Factor Observation也缺失并保留原因。缺失继续沿Signal与Model契约传播；若最终没有合法Model Score，该资产在该策略决策日不进入横截面排名。Strategy不越层读取Factor。当前持仓遇到Score缺失后的退出时点与替补规则留到Strategy阶段冻结。

### D2.4 Factor Value与研究装配分离

为避免季度Universe变化导致重复计算，建议分成：

```text
Factor Value Partition
= Factor Variant + 精确Data输入 + Engine + Coverage/Asset Partition

Factor Dataset Manifest
= Compiled Research Spec所需Partitions + Universe History + Eligibility
```

已存在的Value Partition可跨Universe和实验复用；新数据只计算增量分区。具体按年份、资产批次或二者组合分区，由300股性能基准决定，不在设计阶段硬编码。

### D2.5 定向计算

当前“发布Catalog全部Variant”保留为管理员批量命令，但Workspace运行只解析所选Signal真正需要的Factor Variant：

1. 查询已有精确Partition与Manifest；
2. 复用已发布部分；
3. 只计算缺失资产/日期/Variant分区；
4. 返回新增量、复用量、估计行数和耗时档位；
5. 编译时若只选择Factor、尚未选择Signal，不启动Factor计算。

### D2.6 诊断按研究形态拆分

保留现有基础分布，同时新增：

- 按资产与按日期的coverage、missing status和异常值摘要；
- 横截面有效资产数、median/IQR、离散度和极端值比例的时间序列；
- 股票Universe的Variant冗余以“逐日期横截面Spearman，再汇总时间分布”为主；
- 小ETF集合可同时显示逐资产时间序列相关性；
- pooled asset-date相关性只作补充并明确标签；
- Factor层不计算预测IC、收益Spread或看多/看空结论；所有依赖未来收益Target的诊断属于Experiment Predictive Diagnostic。

### D2.7 Factor前端

- 同一Factor Definition的参数Variant聚合为一张信息卡，例如Amihud w20/w60合并展示；同属一个大类但公式不同的Definition仍分别显示；
- Definition信息卡支持搜索、多标签过滤和多选；
- 搜索覆盖中英文名、key、family、formula说明、required series、频率、Variant参数和标签；
- 详情页展示固定Variant、参数、公式、数据覆盖、局部缺失、分布、横截面离散度、相关性和直接数据血缘；
- 支持下载精确版本的Factor Dataset或诊断摘要；大结果通过异步Export生成，不由浏览器拼接；
- 从Workspace跳转详情后保留草稿、搜索、过滤和勾选状态。

Factor页面按Raw Factor与Derived Factor明确分组，但使用统一搜索、勾选、下载和血缘交互。Raw Factor卡显示来源Canonical字段，Derived Factor卡显示公式与参数Variant。

## 10. 阶段 2 确认结果

1. **选择粒度**：Workspace勾选Factor Definition并可在卡内单选/多选已发布Variant；最终Signal Version反向验证并冻结精确依赖。
2. **版本范围**：保留现有12个Derived Definition/28个固定Variant，不增加无PIT数据支撑的基本面公式；补充Canonical OHLCV等Raw Factor。
3. **缺失与复用**：接受Factor局部状态，以及Factor Value Partition与研究Dataset Manifest分离。
4. **缺失传播**：Canonical输入缺失则对应Factor缺失；最终Model Score缺失的资产在该日不参与Strategy排序。
5. **Factor前端**：确认整体重做，按Definition聚合Variant，支持Raw/Derived分组、搜索、多选、数据导出、诊断和血缘追溯。

阶段 2 已完成，进入 Signal 阶段。

## 11. 阶段 3：Signal——代码事实与确认设计

> 状态：已确认。

### 11.1 当前实现事实

- v0.2 Signal Catalog 包含 27 个模板，按上游 Factor Variant 展开为 51 个固定 Signal Version；其中 continuous 39 个、threshold state 4 个、crossover event 8 个。
- 51 个版本中 canonical 33 个、exploratory 17 个、sensitivity 1 个；当前标记 product eligible 的版本为 41 个。
- 实际数据库已物化 102 个 Signal Dataset（51 个版本分别对应 weekly/monthly 上下文），合计 1,105,616 行；weekly/monthly 两套诊断各覆盖全部 51 个信号与 1,275 个信号对，当前共有 4 条诊断 Issue。
- 连续信号统一使用逐日横截面 centered rank `[-1, 1]`，方向为 `higher_is_better` 或 `lower_is_better`；离散信号不做横截面归一化。
- 当前唯一缺失策略为 `error_after_common_warmup`。Calculator 拒绝任何非有限输入，并要求所有资产拥有完全相同的日期集合、至少两个资产；因此任一资产局部缺失会阻断整个 Signal Dataset。
- Signal Dataset 与一个完整 Factor Dataset、静态 Universe Version、Data Bundle 和 Eligibility Snapshot 强绑定，不利于动态 Universe 下的分区复用。
- 当前诊断支持 weekly/monthly forward return、Rank IC、top-bottom spread、稳定性窗口、事件活跃度、Signal Pair 相关性和 Top-2 重合度。
- 诊断数据库契约把 `active_count`、`event_count` 写死为 0～4，并把换手、冗余重合度写死为 Top-2，明显只适用于当前四 ETF candidate universe。
- 当前前端按每个 Signal Dataset 平铺卡片，展示方向、输出类型、Factor Variant、IC、spread、IR、活跃度、Top-2 换手、稳定性和冗余；尚无搜索、多标签过滤、多选、聚合卡、下载或与 Workspace 联动的选择状态。

### 11.2 已由 Factor 阶段传入的约束

- Factor 不可用时，Signal 不得把缺失静默填成 0 或 neutral；必须产生局部不可用状态并保留上游 reason code。
- 只有合法数值才进入 Signal 变换。缺失沿 Signal → Model 传播；最终无合法 Model Score 的资产不参与当期 Strategy 横截面排序。
- Raw Factor 只代表清洗后的 Canonical 字段引用。Raw Factor 不自动生成 Signal；只有 Catalog 明确注册了经济方向、变换与适用范围的 Signal Version 才能进入下游。

### 11.3 冻结设计

1. **保留固定信号目录**：v0.21 首批保留现有 27 个模板/51 个版本，不允许前端编辑公式、阈值或方向；新增 Raw Factor 后也不自动批量制造“原始价格越高越好”一类无意义信号。
2. **局部缺失语义**：Signal Observation 增加 `valid`、`factor_missing`、`insufficient_cross_section`、`prior_observation_missing`、`quality_blocked` 等状态。连续信号只在当日合法资产横截面内排名；事件信号需要当前值和合法的上一观察值，否则该资产当日 Signal 缺失，而不是 neutral。
3. **计算可用与研究质量分离**：连续横截面信号只要当日至少有两个合法资产即可产生局部分数，不能因为少数资产缺失而阻断全日；同时记录 eligible count、valid count 与 coverage ratio。不同 universe/profile 再声明诊断与 Product Gate 的最低样本/覆盖门槛，低覆盖可以警告或阻止产品升级，但不应把探索性实验的全部可用分数删除。
4. **值分区与研究清单分离**：参考 Factor 层，将可复用的 Signal Value Partition 与具体 Compiled Research Spec 的 Signal Dataset Manifest 分开，支持按资产/日期增量计算和跨实验复用。
5. **动态诊断**：Rank IC、spread、turnover 和 redundancy 每个 decision date 只使用当日 PIT eligible 且 Signal/forward return 均有效的资产；记录当日 universe size、eligible count、valid count 与 coverage ratio。
6. **Signal层不写死排序指标**：Top-1/Top-20、分位Spread、Rank IC与换手均依赖Evaluation Target和Universe，统一进入Experiment Predictive Diagnostic；Signal目录只保留内生覆盖、分布、事件和冗余诊断。
7. **Signal 前端重做**：按 Signal Template 聚合其 Factor Variant 实例；支持搜索、多标签过滤、多选、展开固定版本、精确数据导出、诊断详情与完整血脉。卡片应显示上游 Factor、方向、输出类型、归一化、频率、适用 universe、缺失规则、有效覆盖、值稳定性和冗余摘要。上游 Factor/Asset 选择不合法的版本保留可见但置灰，并直接显示阻断原因；搜索仍可命中置灰项，避免用户误以为目录中不存在该信号。

上述第 7 项中的“诊断”进一步按是否依赖未来收益 Target 拆分：Signal 目录页只保留信号本体、数值覆盖、缺失、分布、事件频率、值稳定性、相关/冗余和血缘等内生诊断；Rank IC、未来收益、Top-Bottom Spread、评价区间、benchmark、候选 Universe 与调仓频率等目标依赖诊断进入 Experiment/研究结果上下文，不再作为 Signal 卡片的默认固定内容。

Signal Template 卡片使用三态总复选框，并允许在卡内独立勾选具体 Version：总复选框可一键选择当前全部合法 Version，部分选择时显示中间态。这样既能按模板聚合展示，也能在编译结果中精确还原实际 Signal Version。

### 11.4 结构合法与运行时缺失

- 结构合法性由选择血缘决定：只有其上游 Factor Definition 已被勾选的 Signal Version 才可勾选；未选 Factor 对应的 Signal 保持可搜索但置灰。
- 已选 Factor Definition 下的 Signal 属于合法候选，即使某资产某日的 Factor Observation 缺失，也不改变该配置的结构合法性；它只产生该资产当日的运行时 Signal 缺失。
- 连续信号在当日剩余合法资产中重新横截面排名；阈值信号不把缺失变成 neutral；事件信号缺少当前或紧邻上一预期观察时不跨缺口判断事件。
- 51 个现有版本全部保留且可搜索；33 个 canonical 与 1 个 sensitivity 默认展示，17 个 exploratory 放入可开启的探索分组。研究可选不等于自动具备 Product Release 资格。
- 股票池的研究质量与 Product Gate 最低横截面数量/覆盖比例留到 Strategy 与 Product 阶段结合 Universe 冻结；Signal 计算层不写死 300 股门槛。
- Signal相关性只作为研究者可见的冗余诊断，不作为硬互斥：系统可以展示相关系数、样本与上下文并给出高相关警告，但不会因相关性自动置灰或禁止共同选择，最终由研究者判断。

## 12. 阶段 3 确认结果

1. **选择结构**：接受 Signal Template 聚合卡、具体 Version 独立勾选和卡片三态全选；只有已勾选 Factor Definition 的下游 Signal 可用。
2. **缺失处理**：接受结构不兼容与运行时局部缺失分离；局部 Factor 缺失不让合法 Signal 配置失效，也不阻断其他资产。
3. **目录范围**：保留现有 27 个模板/51 个版本；canonical/sensitivity 默认展示，exploratory 置于探索分组；Raw Factor 不自动生成 Signal。
4. **前端边界**：Signal 页面整体重做，支持搜索、多选、导出、置灰原因和血缘；移除四 ETF、SPY、共同目标日期、未来收益区间、Rank IC、Top-Bottom 等与具体研究 Target/Strategy 上下文绑定的默认展示。
5. **诊断归属**：Signal 页面保留内生数据诊断；依赖未来收益 Target 的预测评价由 Experiment/研究结果持有精确 Universe、Target、频率、区间和 benchmark 上下文。

## 13. 阶段 4：Model——代码事实与确认设计

> 状态：已确认。以下保留代码事实、设计推导与最终确认。

### 13.1 当前实现事实

- v0.2 Model Catalog 预先展开为 86 个不可变 Model Specification：51 个 single-signal透传、31 个五维度非空子集等权模型、2 个固定维度权重模型、2 个方向投票模型。
- 86 个规格合计绑定331个固定Signal Component；84个输出`continuous_score`，2个输出`directional_score`。
- 五个代表维度为momentum/trend、reversal、tail distribution、volatility/risk、volume/liquidity，但每个维度只绑定Catalog中预先挑选的少量代表Signal，并不会接收用户当前勾选的全部合法Signal。
- 实际数据库已物化172个Model Dataset（weekly/monthly各86个），合计1,864,416行；两套评价各包含3,655个模型对，另有600条目标依赖的ablation comparison和4条Issue。
- Calculator要求收到Specification声明的精确Signal集合，并要求所有输入Signal拥有相同资产集合和共同区间内完全相同的asset-date身份；任一局部Signal缺失会使整个Model Dataset失败。
- 当前`confidence`只是`abs(model_score)`，是分数幅度而非统计置信度，不应继续用可能误导用户的confidence名称。
- Model Dataset与静态Universe、Data Bundle、Eligibility和完整Signal Dataset强绑定，尚不支持动态成员与分区复用。
- Model诊断与Signal诊断一样写死四个candidate、Top-2和共同未来收益Target；前端默认展示评价区间、Target、Rank IC、Top-Bottom、IR、Top-2换手、收益相关冗余及Target ablation，违反已确认的前置目录边界。
- `dgs3mo_cash_accrual_proxy`是防御/现金收益辅助模型，不属于普通用户选择的Signal聚合模型，应作为策略或防御资产链路的已封装辅助依赖处理。

### 13.2 当前实现与v0.21目标的结构冲突

用户选择语义是：Factor、Signal与Model Definition均可多选。每个被选Model必须接收全部已选Signal，不允许从中选择性接受子集；只要任一已选Signal不符合该Model/Preset的输入格式、维度、频率或数量契约，整个Model/Preset就置灰。若同时选择某个Model内部的多个已发布参数Preset，则分别形成多个Model Instance。下游可以把同一Strategy分别应用到这些Model Instance，但每条Strategy Instance始终只绑定一个精确Model Instance，不聚合多个模型输出。现有86个固定Specification不能直接表达该语义，因为其Signal Component在Catalog发布时已经冻结。

v0.21需要明确拆分：

```text
Model Definition
→ Model Preset Version（固定算法、权重规则、输入契约与缺失规则）
→ Compiled Model Branch（Preset + 本次精确合法Signal Version集合）
→ Model Dataset / Output Partition
```

Compiled Model Branch必须拥有独立语义指纹；同一Preset接受不同Signal集合时是不同Branch，不能只记录一个模型名称。

### 13.3 最终设计方向

1. Model前端不再把86个历史展开规格全部当作86个平级“模型”。Model Definition可以多选，每张卡内再单选或多选其已发布参数Preset；single-signal等固定展开规格保留为研究基线或迁移兼容对象。
2. 首批普通预设继续围绕：Signal等权、先维度等权再维度内等权、维度多数投票、固定经典维度权重投票；前端只能选择预设，不能改权重或阈值。
3. 每张Model候选卡都根据全部已选Signal独立预计算兼容性；只有全部已选Signal均可唯一分配到合法槽位且数量满足契约时，该Model/Preset才可选。任一Signal不兼容、输入不足或溢出都会使整个Model/Preset置灰；其他Model候选不受影响。
4. 运行时Signal缺失与结构不兼容分离。普通预设采用`complete_compiled_input_set`：任一编译输入缺失则该资产当日Model Score缺失；确定性聚合只在全部输入共同有效资产交集内做Branch-local归一化，不对单个资产的剩余输入重加权。
5. 输出契约以一个主`model_score`为核心，并声明higher-is-better、范围、时间语义、横截面可比性、输入覆盖和缺失原因；当前`confidence=abs(score)`改名为`score_magnitude`，真正confidence留给能给出校准置信度的未来模型。
6. Model目录页只展示组成、兼容输入、Preset、输出、数据覆盖、缺失、分数分布、维度贡献与血缘等内生内容。未来收益Target、Rank IC、Top-Bottom、收益ablation与benchmark进入Experiment/研究结果。
7. Model Output Value Partition与具体Compiled Branch的Dataset Manifest分离，支持对精确Signal Partition依赖做增量复用。

当前建议把普通选择整理为三个Model Definition、五个可选Preset Version；研究者可多选Definition，并在每张选中卡内部单选或多选参数Preset：

- `Single-Signal Pass-through`：只在全部已选Signal恰好为1个且格式合法时可选，作为基线/诊断使用；
- `Classical Score Aggregator`：`signal_equal_weight`、`dimension_balanced_equal_weight`、`fixed_dimension_weight_v1`；
- `Directional Voting`：`dimension_majority_vote`、`dimension_weighted_vote_v1`。

每个Signal Version需要冻结一个主要`model_dimension_key`，不能继续只依赖可含糊解释的`dimension_hint`。维度平衡预设按本次实际存在的合法维度等权，再在维度内等权；固定维度权重预设要求其声明的必要维度全部存在，否则结构不合法，不在运行时偷偷重归一化。

对于运行时局部缺失，当前推荐v0.21普通模型默认采用`complete_compiled_input_set`：某资产某日只要缺少该Compiled Branch中的任一Signal，便不生成该资产当日Model Score。原因是按资产对剩余Signal重归一化会使不同资产的分数由不同输入组成，破坏横截面可比性。neutral零值仍是合法输入，不等于missing。未来若新增容错模型，必须作为单独Preset明确声明最少输入、重归一化和可比性语义，不能成为隐式行为。

### 13.4 上游数量驱动的Model Input Slot Contract

Model Preset不只声明“支持哪些Signal”，还必须声明结构化输入槽位：

| 字段 | 含义 |
| --- | --- |
| `slot_key` | 稳定槽位身份，例如`momentum_input`、`volatility_input` |
| `accepted_dimensions/families` | 该槽位允许的Signal主要维度或家族 |
| `accepted_output_types` | continuous/state/event等允许格式及转换 |
| `frequency/comparability` | 频率、时点与横截面可比要求 |
| `min_count/max_count` | 合法输入数量范围；相等时即exact count |
| `duplicate_policy` | 是否允许同一Signal Template的多个参数Version同时进入 |
| `required` | 槽位是否必填 |

兼容判断覆盖全部已选Signal与该Preset的入槽结果：

- 合法输入少于`min_count`：Model Preset置灰，显示缺少的槽位/维度与数量；
- 合法输入多于`max_count`：Model Preset置灰，显示溢出的Signal，不自动丢弃也不自动枚举子集；
- 任一已选Signal无法进入该Model的合法槽位时，整个Model/Preset结构不兼容并置灰；模型不得忽略该Signal后继续运行；
- 所有槽位都满足后，该Model才可勾选；Compiled Branch精确冻结实际Signal→Slot分配。

这允许同一Model Family只显示一张聚合卡，在卡内提供“单动量”“单波动率”“多维度平衡”等已发布参数Preset，而不把每个Signal组合预先展开成大量模型卡。若一个Signal可被多个槽位标签命中，Catalog必须提供唯一主要`model_dimension_key`与确定性槽位优先级；同一Signal不能在一个Branch中被重复计权。

### 13.5 全链路参数只能选择已发布版本

Factor、Signal、Model、Strategy统一采用“选择版本，而不是在线调参”：

- Factor Definition卡内可对已发布Factor Variant进行单选或多选；被选Variant进一步限制合法Signal Version。此项修订阶段2中“完全由Signal反推Variant”的决定：Signal仍负责验证并反向绑定精确依赖，但用户可以先主动缩小Variant范围。
- Signal Template卡内可单选或多选已发布Signal Version；只显示Catalog中真实存在的Factor Variant×规则组合，不由前端自由做笛卡尔生成。
- Model Definition卡内可单选或多选已发布Model Preset Version；每个Preset独立接受上游合法Signal并形成Branch。
- Strategy Definition卡内可单选或多选已发布Strategy Preset Version；每个被选Preset独立进入实验展开。

所有多选都表示选择多个已发布Version，而不是把一个数组参数临时传入同一算法，但各层展开语义不同：Factor Variant多选扩大合法上游范围；Signal Version多选形成可被同一Model共同消费的输入集合；Model Preset多选形成多个独立Model Branch；Strategy Preset多选形成多个独立Strategy/Experiment Branch。任何新窗口、阈值、权重、K、频率或超参数都必须修改Catalog/底层代码、补测试并发布新Version；前端不提供数字输入、任意文本配置或自定义权重。

为避免参数多选重新制造意外全量搜索，Workspace必须实时显示每层选择数、下游合法数、最终Branch乘积、预计复用量/计算量、耗时与存储。允许研究者明确提交长任务；只在部署层可配置资源安全限制触发时阻止Compile，不进行隐式抽样。

### 13.6 该设计仍需防止的问题

1. **模型静默缩减上游输入**：每张Model候选卡必须验证全部已选Signal；任何一个无法入槽都使该Model/Preset置灰，不允许用兼容子集继续运行。
2. **独立参数选项产生非法组合**：Model/Strategy优先暴露经过测试的命名Preset，而不是让用户把每个权重字段分别排列组合；Preset详情只读展示内部参数。
3. **自动子集搜索造成过拟合与爆炸**：输入溢出时直接置灰，不自动生成“从N个信号任选K个”的全部模型。
4. **同一信息重复计权**：Slot Contract需声明同Template多Version是否允许；即使允许，也要在卡片显示冗余警告，但本版不自动替研究者删除。
5. **参数多选语义不清**：运行清单必须展开到精确Factor Variant、Signal Version、Model Preset/Compiled Branch与Strategy Preset，不能只显示卡片家族名。
6. **已选上游变化导致下游失效**：上游增删后，下游已选Model/Strategy保留在草稿中但标记`selection_invalidated`，要求研究者重新确认，不能静默取消或继续运行旧组合。

### 13.7 多Model的最终展开语义

Model Definition与其内部参数Preset均可多选，但多选只用于生成并行研究分支：

```text
Selected Signals
→ 每个Model独立做Slot兼容与不足/溢出检查
→ 每个合法Model × Model Preset生成一个Model Instance
→ 每个Model Instance × 每个合法Strategy × Strategy Preset分别回测
```

任何一条普通Strategy Instance始终只引用一个精确Model Instance/Output；选择两个Model表示同一策略逻辑分别使用两个模型输出回测，不表示策略把两个输出聚合。需要多模型集成的策略仍只能作为Packaged Strategy封装。

### 13.8 Model阶段仍需解决的问题

1. **Input Slot数量语义**：每个Preset需要冻结exact count或min/max range，并逐槽位计算；不能只检查总Signal数。
2. **溢出后的研究便利性**：坚持不自动枚举子集。选择三个动量Signal时，exact-one动量模型置灰；若要分别研究三个单信号模型，研究者需拆分草稿或使用未来显式注册的Sweep工具，普通Compiler不隐式搜索。
3. **维度归属**：每个Signal Version必须有唯一主要`model_dimension_key`；其他多标签只供搜索和解释，不能造成重复入槽。
4. **同Template多参数版本**：Preset必须声明w20/w40/w60等同Template Signal能否同时进入，以及是否占用多个count；允许时显示冗余提示。
5. **可变输入数下的权重**：接受范围输入的模型必须用确定规则，例如维度权重固定、维度内对实际合法Signal等权；实际输入集合进入Compiled Branch指纹。不得根据回测结果动态调权。
6. **运行时缺失**：建议默认仍为complete compiled input set，避免不同资产用不同Signal组合得分；容错重归一化必须是另一个显式Preset。
7. **输出统一性**：普通规则模型统一输出higher-is-better的单一`model_score`与coverage/status；当前`confidence=abs(score)`改名，不能冒充概率置信度。
8. **规则模型与未来机器学习模型分界**：LightGBM等训练型Model还需要Target Version、训练窗口、walk-forward、特征Schema、防泄漏和模型文件Artifact；不能套用只有静态加权参数的规则模型生命周期，但必须输出同一Strategy兼容契约。
9. **多选规模**：Model Definition×Model Preset×Strategy×Strategy Preset×Experiment Scenario形成乘积；Compile前必须显示分支树、复用比例、预计耗时、存储与部署层安全限制。
10. **前端与评价边界**：Model目录只显示结构、Preset、兼容性、覆盖、输出分布与血缘；未来收益、IC、Top-Bottom和收益消融继续留在Experiment上下文。
11. **v0.2迁移**：现有86个固定Specification需要分类为可迁移Preset基线、历史只读Artifact或淘汰的预展开组合，不能直接全部变成v0.21模型卡。

### 13.9 项目所有者本轮确认与必要拆分

1. **全量上游输入**：每个Model默认且必须消费全部已选Signal；不允许选择性排除。只有整个已选Signal集合满足Model/Preset契约，该项才不变灰。
2. **Signal相关性提示**：不实施经验相关性的硬互斥或自动置灰；高相关Signal可以共同选择，系统只显示冗余警告，全部已选Signal仍进入每个下游Model的完整兼容检查。
3. **权重参数**：权重属于已发布Model Preset参数，允许单选或多选；多选权重Preset生成多个Model Instance，不允许前端手输权重。
4. **单次使用**：同一Signal Version在一个Model Instance中只能分配到一个槽位并使用一次。Signal层只产生上下文化冗余提示、不做相关性互斥；Model层保留唯一性约束作为防御性校验。
5. **Model Family**：一个能够共享输入、参数、训练/推理、输出和生命周期契约的算法集合构成一个Model Family。当前主链路实质上可先归为确定性线性聚合与方向投票两个主要Family；single-signal是线性聚合退化基线，DGS3MO reserve accrual是策略辅助模型而非普通研究Model。
6. **长任务政策**：不因组合数量大设置过低的产品级硬上限；允许研究者主动提交很长的异步回测。系统仍必须提供运行规模、预计耗时/存储、取消和失败恢复，并保留防止意外失控的可配置运维上限。

#### Signal相关性只作上下文化提示

经验相关性依赖Universe、频率、数据版本和样本区间。若展示相关性，建议发布版本化`Signal Redundancy Snapshot`，至少冻结：

- universe/profile与候选资产语义；
- Signal Version对、方向对齐方式与Spearman等计算方法；
- 数据/诊断窗口、有效共同观察数和覆盖门槛；
- 使用`abs(correlation)`的提示阈值；
- 生成该互斥边的Artifact、Engine和时间。

提示阈值由Catalog/底层诊断政策发布，不允许用户在前端临时调整，但只影响徽标与说明，不影响选择合法性。没有足够共同样本时状态为`correlation_unknown`；继续允许选择，并明确没有可靠冗余结论。

#### Target必须拆成训练Target与评价Target

- `training_target_version`：只有训练型/拟合型Model（例如LightGBM、线性回归、Ranker）需要，是Model Preset/Trained Model Artifact的正式参数；选择多个Target会生成同一Family下多个独立训练Model Instance与Output。
- `evaluation_target_version`：用于评价规则模型、训练模型或策略的未来收益定义，属于Experiment/评价上下文。
- 确定性线性加权与投票Model可以在卡片显示声明性`intended_target/horizon`，但该字段不参与计算、不改变Model Output指纹，也不复制相同分数；其训练Target为`not_applicable`。

所有Family都必须声明Target Contract：训练型Family要求具体training target，确定性Family明确声明不训练；二者都可限制兼容的评价Target/Horizon。未来LLM调用Family还需冻结provider/model、prompt/template、tool/data cutoff、结构化输出Schema、采样参数、缓存/重放、费用与外部数据泄漏政策，不能只复用线性模型契约。

## 14. 阶段 4 确认结果

1. **全量Signal输入**：每个Model/Preset必须接受全部已选Signal；任一格式、维度、频率、唯一性或数量契约不满足时，该Model/Preset置灰，禁止选择性缩减输入。
2. **多Model展开**：Model Definition及内部参数Preset均可多选；每个合法Model×Preset生成独立Model Instance，同一Strategy分别对各实例回测，但每条Strategy Instance只绑定一个模型输出。
3. **参数治理**：权重等计算参数只能从已发布Preset单选/多选，前端不可手输；不同Preset生成不同Model Output。
4. **缺失与输出**：接受`complete_compiled_input_set`作为普通模型默认缺失语义；输出统一为higher-is-better的单一`model_score`，`abs(score)`不再称为confidence。
5. **相关性**：Signal相关性不做硬互斥，不影响选择合法性；只提供上下文化冗余提示，由研究者判断。
6. **Target**：训练型Model的Target是正式参数，不同Target形成同一Family下不同模型输出；确定性加权/投票Model的Target仅作声明性卡片信息，不参与计算或复制输出；实际评价Target由Experiment冻结。
7. **Family边界**：共享输入、参数、训练/推理、输出和生命周期契约的模型归为同一Family。当前普通主链路先整理为确定性线性聚合与方向投票，未来训练模型、Ranker、LLM等按各自契约新增Family。
8. **长任务**：允许研究者明确提交大规模、长时间异步回测；系统提供规模/耗时/存储估计、取消、恢复与复用，只保留可配置的运维安全限制。
9. **前端与迁移**：Model页面按Family卡与Preset选项重做；现有86个固定Specification分类迁移，不直接平铺为86张选择卡；Target收益评价继续属于Experiment。

阶段 4 已完成，进入 Strategy 阶段。

## 15. 阶段 5：Strategy——代码事实与待确认设计

> 状态：已确认。阶段5完成，进入Experiment阶段。

### 15.1 当前实现事实

- v0.2只有一个`cross_sectional_top_k_rotation` Strategy Definition。
- Catalog展开9个Strategy Variant：3种选择顺序（纯Top-K、先选后趋势过滤、先趋势过滤后选）× K=1/2/3；每个Variant再支持weekly/monthly两种Schedule。
- 当前Input Contract要求`complete_eligible_universe`和`fail_formal_run`：固定四只candidate任一缺少Model Score，整个正式Target Path失败。
- 普通策略直接读取`price_above_ma_state__moving_average_ratio__s1_l200`辅助Signal实现趋势过滤，绕过Model层。
- 决策使用最后共同交易日收盘信息，下一共同交易日`adjusted_open`执行；K个等权槽位，未使用槽位进入Synthetic Reserve。
- Top-K边界同分时不使用ticker打破，而把剩余槽位预算在全部并列资产间等分，因此实际持有证券数可以超过K。
- 数据库已有1个Definition、9个Variant、630个Strategy Product Version（35个非single-signal Model×9×2）、1,336个Target Path、412,123个Portfolio Decision和1,648,492条Asset Position；weekly/monthly Product各315个。
- 当前Strategy Product身份冻结Model Specification、Strategy Variant、静态Universe、Schedule和Execution Policy；尚不能引用动态Universe History、用户冻结Asset Set或v0.21 Compiled Model Branch。
- 当前前端把规则、630个Model×Rule×Universe×Schedule Product和已发布Target Path/逐日持仓放在同一页，没有搜索、多选、Family卡、参数选项或Workspace联动。特定模型、Universe、区间和逐日决策结果不应继续作为Strategy目录页的默认主体。

### 15.2 与已确认上游契约的冲突

1. Model Score局部缺失已经被定义为“该资产当日不参加排序”；当前完整四资产/任一缺失全失败契约必须改为逐决策日有效候选子集。
2. 普通Strategy只能消费一个Model Output；现有两个趋势Variant额外读取Signal，违反层级边界，应迁移为Packaged Strategy，或把趋势状态在上游编入唯一Model Output/已注册策略状态契约，不能原样保留。
3. v0.21需要ETF轮动与大盘股选股两个Strategy Family。二者可共享排序引擎，但动态Universe、K范围、buffer、sector cap、防御、benchmark建议和tie适用性不同，不能继续只用一个四ETF硬编码Contract。
4. 全链路参数只能选择已发布版本；旧草案中的“前端自由输入K/自定义Strategy Instance”作废。K、frequency、buffer、sector cap、defense budget、tie policy和execution policy均只能从Family已发布Preset单选或多选。
5. `confidence=abs(score)`已经在Model阶段废弃，Strategy Input不应继续依赖该字段。

### 15.3 建议的两个普通Strategy Family

1. `Multi-ETF Cross-sectional Top-K Rotation`
   - 默认Asset Set：IWF/IWD/IWO/IWN；
   - 接受Strategy Ready ETF自定义冻结集合；
   - 固定K、weekly/monthly、defense budget和tie policy Preset；
   - SPY等benchmark只作为Experiment默认建议，不进入Strategy排名候选。
2. `US Large-Cap Cross-sectional Top-K Selection`
   - 默认Universe：`US Liquid Large-Cap 300 PIT`或数据不足时明确的Exploratory Snapshot；
   - 固定K、frequency、selection buffer、PIT sector cap、defense budget和tie policy Preset；
   - 正式PIT门槛未满足时不能升级Product Release。

两者共享一个common rank/select/allocate engine，但发布不同Definition/Input Contract/Preset Schema。Strategy Definition与其内部Preset均可多选；每个合法Model Instance×Strategy Definition×Strategy Preset形成独立Strategy Product/实验分支。

### 15.4 待确认的关键决策

1. **Model Score缺失与补位**：该资产在当期直接不进入排名；若原本持有，则目标权重归零并在下一计划执行时点退出。Top-K从其余数百个合法候选中自然顺延补足，例如原第21名进入Top-20，不存在为单个缺失资产预留空槽，也不得沿用旧Score继续持有。
2. **可排名集合与数据质量门禁**：缺分资产由后续合法候选自然顺延，但若单个决策时点的`rankable_count < K`，说明数据、Model或Universe已经不足以执行该策略。该决策硬失败并记录`insufficient_rankable_candidates`，不得生成Target、不得用Synthetic Reserve伪装成功。即使`rankable_count >= K`，仍需按Family发布的最小Score覆盖率和最小候选冗余门槛判定数据质量；未达门槛的实验只能标记失败/诊断，不得产出可比较正式结果或升级Product。
3. **Tie Policy按Family/输出分开**：ETF小Universe可继续使用边界并列比例分摊；大盘股Family要求分辨率足够的continuous score。低分辨率方向投票输出会让Top-K退化为大量并列持仓，因此该Model→Stock Strategy边直接置灰；禁止ticker、市值等未声明字段秘密破坏并列。若未来需要兼容，应在Model Family内正式发布连续化输出。
4. **趋势过滤与内置防御控制器**：当前SMA200不是Model，而是Strategy绕过Model层直接读取的辅助Signal；原样实现不保留。纯Top-K作为两个普通Family主链路。固定防御比例可作为普通Preset；动态防御也可由Strategy/Packaged Strategy内部固定绑定一个版本化控制模型，研究者只能选择已发布的`defense_policy`，不能在上游选择或配置该辅助模型。其模型版本、输入、输出档位和血缘必须随Strategy Version冻结。
5. **权重**：首批维持Equal Slot Weight；分数比例、Softmax、风险平价等需新Strategy Family/Preset和可比较Score契约，不作为前端自由参数。
6. **执行价格**：建议策略契约使用下一合法执行Session的可成交raw open/正式execution price，并由会计引擎处理公司行动；不能在缺乏明确会计说明时把`adjusted_open`直接当真实成交价。具体需在Experiment/Accounting阶段对代码再核验。
7. **前端归属**：Strategy页按Family卡聚合Preset，支持搜索、多选、置灰原因、参数多选、详情和血缘。具体Model×Universe生成的Target Path、逐日持仓与收益结果进入Experiment详情，不在Strategy目录首页平铺。

### 15.5 第一轮确认结果

- 缺分资产直接退出当期候选排名，由后续合法候选自然顺延补足Top-K；若任一决策日可排名集合少于K则硬失败，不用Reserve掩盖模型或数据故障。
- ETF允许边界并列比例分摊；股票Top-K要求分辨率足够的连续模型分数，低分辨率投票模型与股票策略不兼容并置灰。
- 当前SMA200趋势逻辑是Strategy直接读取辅助Signal，并非独立Model；该越层实现不沿用。
- 防御策略允许绑定内部固定、不可由前端配置的控制模型。研究者只选择已发布Defense Policy；内部模型完整冻结在Packaged Strategy版本与血缘中。
- 两个Strategy Family、等槽位权重、选择式参数和Strategy前端重做方向均已确认。

## 16. 阶段6：Experiment——代码事实与确认边界

### 16.1 当前实现事实

- v0.2已经实现不可变`Experiment Suite → Cell/Specification → Run Attempt → Accepted Result`链路。每个Cell精确冻结Strategy Target、Benchmark、Cost Scenario、Metric Catalog、三类Engine、区间和as-of日期，并使用fingerprint复用相同计算。
- Accepted Result要求对应Run完成、没有failed quality check、输出链接唯一且所有上下文精确一致；事件、质量检查、依赖Artifact和Decision Path均可审计。这部分可作为v0.21底座保留。
- Formal Release对每个Strategy Target固定展开5个区间（全历史、10/5/3/1年）×3个线性单边成本（2/5/10bps），即每个Target 15个Cell。后端支持custom日期，但正式矩阵没有使用；初始化只实现`carry_in`，`fresh_start`尚未实现。
- 当前成本模型只按交易资产名义金额收取固定bps，不含初始资金、股数、成交量参与率、买卖价差或市场冲击。因此“选择大盘股以降低冲击成本”尚未真正反映到回测。
- 当前会计使用下一共同Session的`adjusted_open`成交，组合以权重/NAV计算，没有真实股数与现金取整；该实现适合相对收益研究，但不能直接宣称是真实可成交模拟。
- 当前Metric Catalog有14个绝对指标与8个相对指标，覆盖收益、波动、Sharpe/Sortino、回撤、Calmar、日/月胜率、Tracking Error、Information Ratio、Beta和Alpha，指标底座较完整。
- Benchmark Catalog已有SPY买入持有、四ETF等权买入持有、四ETF同频再平衡；后两者硬编码四ETF，尚不能针对任意ETF Asset Set或动态股票Universe生成上下文基准。
- Release可以使用1至16个本地Process Worker并复用中间Artifact，但由CLI同步组织，不是数据库持久任务队列；没有前端提交、取消、恢复或按失败Cell重试的写接口。
- 当前API只有Experiment Overview、Result Detail和Decision Explorer等GET接口；前端只能过滤并浏览预生成Cell，还把Product Ranking直接放在Experiment页顶端，不能从Workspace提交新实验。
- 目前Signal/Model的Target、IC、Top-Bottom等预测诊断仍在上游旧页面；按已确认分层，它们应迁入Experiment。现有Experiment只支持Portfolio Backtest，没有Predictive Diagnostic实验类型。

### 16.3 第一轮待确认边界

1. **Workspace与Experiment**：Workspace只保存可变研究Draft、合法性与分支估算；点击Run后编译为不可变Experiment Suite并进入持久队列。Experiment页负责队列状态、结果、比较、诊断和重试，不再修改上游选择。
2. **两类Experiment**：建议至少区分`Predictive Diagnostic`与`Portfolio Backtest`。前者承接Signal/Model相对已冻结Target的IC、分组收益、稳定性和冗余诊断；后者承接Strategy持仓、成本、NAV、benchmark和绩效。两类共享Suite、Cell、Run和血缘框架，但使用不同Cell Contract。
3. **执行生命周期**：建议状态为draft/compiled/queued/running/completed/failed/cancelled；允许取消未完成Cell、只重试失败Cell、复用相同fingerprint结果，并展示总分支、完成数、失败数、预计剩余量与资源消耗。
4. **实验配置归属**：区间、as-of、Benchmark、Cost Scenario、Metric Catalog和未来Initial Capital/Impact Scenario属于Experiment；K、frequency、buffer、sector cap、defense policy仍属于Strategy，不得在Experiment重复修改。
5. **排名与升级**：不设计额外多结果比较器，也不保留独立Compare页面。Experiment首页以严格可比结果排行榜为主体；点击单条记录进入完整详情，只有详情页提供显式“升级为Product”动作。升级实际冻结并提升该结果对应的精确Strategy/Model/Universe/Policy版本，并把Accepted Result作为资格证据，不是把一份收益表本身当成产品。
6. **数据质量**：Strategy/Model逐日硬门禁先决定Cell能否计算；Experiment汇总Score覆盖、无效决策、缺失原因和区间完整性。失败质量门禁的Cell可以显示诊断，但不能成为Accepted Result或Product候选。

### 16.6 第二轮：区间、资金、成本与执行会计确认结果

#### 回测区间与初始化

- v0.21正式矩阵只发布Full Common History、Trailing 3 Years、Trailing 1 Year三个区间；不在前端提供10/5年或Custom日期，减少实验分支并统一排名口径。
- 排行榜必须使用完全相同的resolved start/end；模板名称相同但实际有效日期不同的结果不得直接混排。
- 建议正式Portfolio Backtest固定采用`fresh_start`：在所选区间开始时以100%初始资金/Reserve启动，使用区间前数据完成Factor/Model warmup，在区间内第一个合法执行点建仓。旧`carry_in`保留为历史路径诊断或Product持续监控语义，不作为默认实验排名口径。

#### 初始资金

- 正式Portfolio Backtest统一使用USD 100M Initial Capital，不提供资金选项，也不因资金形成额外分支。
- 100M必须实际参与Order Notional、ADV参与率和Liquidity Impact计算；若仍采用纯固定bps权重回测，100M没有数学作用，禁止把它作为虚假“真实性”标签展示。

#### 成本情景

- 正式矩阵只发布两个100M Liquidity-Aware情景：`base_5bps_plus_impact`与`base_10bps_plus_impact`。5/10bps是基础摩擦，实际单笔成本还叠加版本化Liquidity Impact；界面不得只写成“固定5/10bps”。
- 每笔交易使用决策时已经可得的raw price、Trailing 20 Session Median Dollar Volume与波动率；成本由基础bps加公开、版本化的square-root impact组成。
- 参与率必须使用决策日前可得的ADV，不能偷看执行日最终成交量。若单笔Order Notional超过发布的最大ADV参与率（建议首版5%），Cell硬失败或标记Capacity Rejected，不假设可以在开盘瞬间无限成交。
- Liquidity-aware结果是压力情景估计而不是真实券商成交回放；公式、系数、cap、输入日期和缺失原因全部进入Cost Model Version与血缘。
- Strategy与Benchmark使用同一Cost Model/Capital/Execution Policy；Synthetic Reserve不收交易成本，真实防御ETF正常计费。

#### 执行与收益会计

- 当前数据已有`open_raw/high_raw/low_raw/close_raw`、adjusted OHLC、`volume_raw`、cash dividend与split ratio。
- v0.21建议采用Capacity-aware hybrid accounting：raw open用于展示成交价、计算Order Notional、ADV参与率和成本；adjusted open/close ratio用于总回报和权重漂移，避免首版重复实现逐股数拆股/分红会计。
- NAV同时保存Currency NAV与归一化Wealth Index；绩效和排名使用归一化收益，资金容量和绝对成本使用Currency NAV。
- 首版继续使用连续Notional/允许分数股，不模拟整数股取整。该限制必须在结果详情披露；真正Broker/Order级执行模拟不属于v0.21。
- 执行仍为决策后下一合法共同Session开盘；若raw open、当时可用ADV或公司行动调整数据缺失，正式Cell失败，不使用前值或adjusted price静默替代。

#### 固定实验矩阵

- 每个Compiled Strategy Instance自动生成`3 intervals × 2 cost scenarios = 6`个Portfolio Backtest Cell，不让用户逐项勾选，也不展开其他组合。
- USD 100M固定值不增加分支；Strategy的weekly/monthly frequency已经冻结在Strategy Instance中，Experiment只把它作为排行榜独立筛选字段，不再次复制Cell。
- Ranking Metric只改变排行榜查询与排序，不触发任何新回测。
- 因此Workspace显示的Portfolio Backtest规模为`合法Strategy Instance数 × 6`；Predictive Diagnostic使用自己的Cell Contract与复用规则，不与这6个结果重复计算。

### 16.7 第三轮：Benchmark与Predictive Diagnostic确认结果

#### Portfolio Benchmark

- Benchmark不作为前端自由参数，不再为每个Benchmark复制一套Strategy Backtest Cell。每个Family发布固定Benchmark Set；同一个Portfolio Cell计算一次Strategy Path，并在结果内附带多个可复用Benchmark Path与相对指标。
- 两个Strategy Family均以`SPY Buy-and-Hold`作为Primary Ranking Benchmark，使跨Model/Strategy结果的相对指标有统一口径。
- Multi-ETF Family额外提供`Selected ETF Set Equal-Weight Same-Schedule Rebalanced`作为Research Benchmark，用来判断收益来自横截面选择还是所选资产集合本身；它必须基于该Cell冻结的Asset Set动态生成，不能继续硬编码四ETF。
- US Large-Cap Family额外提供`PIT Eligible Universe Equal-Weight Same-Schedule Rebalanced`作为Research Benchmark，用来区分模型选股能力与股票池整体表现。Universe成员与重构日期必须和Strategy使用同一PIT版本。
- 所有Benchmark与Strategy使用相同fresh-start、100M Capital、execution、5/10bps+impact和有效日期。排行榜默认相对指标指向SPY；Research Benchmark指标只在详情页展示，不产生额外排名分支。

#### Predictive Target

- v0.21首版只发布两个经济评价Target：weekly与monthly的`next_execution_open_to_next_execution_open_total_return`。底层可继续用adjusted open ratio表达含公司行动总回报，但名称不得暗示adjusted price是真实成交价。
- Standard Flow不提供Target下拉框：weekly Model/Strategy分支自动使用weekly Target，monthly分支自动使用monthly Target。Target、decision cutoff、execution lag、calendar与Data Version冻结进Diagnostic Cell。
- 训练型Model的training target仍是Model参数并决定独立Model Instance；Predictive Diagnostic Target是统一的事后经济评价口径，两者必须同时显示，不能混称。Family可以要求训练Target与输出frequency兼容。
- Predictive Diagnostic不按每个Strategy及其6格矩阵重复运行。相同`Signal/Model Instance + Asset Set/Universe + frequency + target + data version`只生成一个基础预测评价Artifact，并从同一时间序列切出Full/3Y/1Y窗口指标。

#### 诊断指标与大小Universe适配

- Common指标：Score/Target覆盖率、有效决策期数、Mean/Median Rank IC、Positive IC Ratio、IC Information Ratio、Score Dispersion和年度/滚动稳定性。
- ETF小横截面：使用Top-1 minus Bottom-1、Top-1命中率与Top-1换手，不再固定Top-2。只有2只ETF时Rank IC每期会退化为±1/undefined，只能视作顺序命中信息，不能作为主要强度指标；资产数足够时才重点展示Rank IC。
- 股票大横截面：使用Top Decile minus Bottom Decile、默认Top-20命中/换手和横截面Rank IC；分位边界使用公开tie policy，不通过ticker排序。
- Signal事件类补充Event Rate与资产集中度；Model可显示输入贡献/Family允许时的Ablation；训练型Model另显示walk-forward、train/validation/test、Target、特征重要性与泄漏检查。
- 相关性仅作为所选Signal/Model之间的冗余提示，不置灰、不阻止实验；避免默认计算全目录O(n²)组合，优先对当前Workspace选中集合计算并复用。

#### 前端归属

- Experiment使用Portfolio Ranking、Predictive Diagnostics、Runs三个清晰视图/入口；收益排行榜只包含Accepted Portfolio Result，预测指标不与策略收益混排。
- Predictive页面可按对象类型（Signal/Model）、Full/3Y/1Y、weekly/monthly和指标筛选；点击记录查看时间稳定性、分组表现、覆盖、数据质量和血缘。

第三轮确认通过：SPY作为两个Family的Primary Ranking Benchmark；ETF与股票分别附带动态Research Benchmark；Predictive Target按weekly/monthly自动绑定；Predictive Diagnostic独立去重并复用，不进入每个Strategy Instance的6格Portfolio矩阵。

### 16.8 第四轮：运行队列、验收与结果交付确认结果

#### 持久任务队列

- 用数据库持久队列替换当前CLI同步ProcessPool编排。Workspace Compile发布不可变Suite/Cell后提交Run Request；Worker通过lease/heartbeat安全领取Cell，进程崩溃或租约过期后可恢复，不能因关闭浏览器丢失任务。
- Cell状态使用`queued/running/completed/failed/cancelled/reused`；Suite状态由Cell汇总为`queued/running/completed/completed_with_failures/cancelled`。Cancelled不是Failed，已经完成的Accepted Result继续保留。
- 允许取消尚未开始的Cell；运行中Cell在确定性阶段检查点协作取消。只对infrastructure/interrupted等可恢复失败提供同Specification重试，新Attempt不修改输入；data_quality、capacity与contract失败不可通过原样重试解决，修复数据/代码或选择后必须形成新Dependency/Engine Version与新Specification。相同fingerprint已有Accepted Result时直接`reused`。
- Worker并发与资源上限属于部署配置，不作为研究参数。界面在提交前显示Portfolio Cell数（Strategy Instance×6）、去重后的Predictive Cell数、复用数和预计存储；不设置任意很小的产品上限。
- 每个Cell按可观察阶段记录进度与事件：input validation、predictive/model reuse、strategy target、gross accounting、cost/impact、benchmark、metrics、quality acceptance。预计剩余时间只能标注为估算。

#### 自动验收

- `Accepted`是系统质量门禁结果，不是研究者手动点赞；研究者的手动动作只有后续“升级为Product”。
- Portfolio Cell至少要求：Compiled依赖全部发布且fingerprint一致；无未来数据；每个决策通过Universe/Score覆盖与K门禁；100M容量未被拒绝；raw execution/ADV/公司行动数据完整；Strategy与Benchmark共享区间、成本、资金和会计版本；NAV、权重、成本与指标对账通过；Run完整结束且无failed quality check。
- Predictive Cell至少要求：Target/Score时间对齐且无泄漏；Family最小资产数、Score/Target覆盖、有效期数与非退化横截面通过；指标均带value status/reason。短样本可以Accepted with Warning，不伪造未定义指标。
- 单个Cell失败不抹掉同一Suite其他Accepted Result。失败按`data_quality/capacity/contract/calculation/infrastructure/cancelled`分类并提供稳定reason code、首个失败阶段和可下载诊断。
- Full/3Y/1Y与5/10bps+impact各自独立验收；排行榜只读取Accepted Cell，并严格按筛选器与可比上下文形成结果集。

#### Runs与Result Detail

- Runs视图展示Suite名称/ID、创建时间、来源Workspace、总数、queued/running/accepted/failed/cancelled/reused、当前阶段、耗时与取消/失败重试操作；支持搜索和状态筛选。
- Result Detail沿用已确认图表和完整指标，并补充精确Experiment Specification、实际resolved日期、100M与成本公式版本、容量最大参与率、复用来源、运行耗时和Quality Gate摘要。
- 提供版本化导出：Summary JSON、Metrics CSV、Daily NAV/Benchmark/Excess CSV、Trades/Turnover/Costs CSV、Holdings/Weights CSV、Quality/Lineage JSON。导出读取不可变Result Artifact，不在浏览器重新计算。
- 长时间序列图使用服务端降采样，但下载保留完整精度；图表和CSV必须来自同一Artifact与相同日期口径。
- “升级为Product”只在Accepted、Formal、非Exploratory的Portfolio Result详情页出现；创建动作、确认窗口与撤销规则留到Product阶段冻结。

第四轮确认通过：Workspace一次“运行实验”自动生成所选Signal/Model去重后的Predictive Diagnostic Cell，并为每个Compiled Strategy Instance生成固定6个Portfolio Cell；数据库持久队列、自动质量验收、分类失败/重试、Runs视图、完整Result Detail与版本化导出均按本节冻结。阶段6完成，进入Product阶段。

## 17. 阶段7：Product与Monitoring

> 状态：已确认。

### 17.1 当前代码事实

- v0.2的`strategy_product_definition/version`只是Model Specification＋Strategy Variant＋Universe＋Schedule＋Execution Policy的不可变可执行组合，不是“被研究者选中后开始样本外监控的产品”。v0.21语义上应称为`Compiled Strategy Version`，可暂时兼容旧表名但API/UI不能继续混称。
- 当前Product Ranking实际对Accepted Experiment Result做历史排名；Compare页也是2至6个历史结果的指标并排。两者没有Product激活时间、监控起点、样本外路径、健康状态、预警、人工复核或退出记录。
- 当前没有Product专属写API、生命周期表、Monitoring Snapshot、Warning Event、Review Decision或持续增量任务。已有通用Artifact的retired/invalidated状态不能替代业务Product生命周期。
- 因此Products替换Compare不能只改导航名称，必须新增正式`product`后端模块与前端页面；旧历史排名归Experiment，旧Compare页面移除。

### 17.2 第一轮生命周期确认结果

#### 升级资格

- “升级为Product”实际提升精确Compiled Strategy Version，而不是一张收益表。Product冻结Model、Strategy、Asset Set/Universe、Schedule、Defense/Execution Policy及全部依赖版本。
- 入口仍位于单个Accepted Portfolio Result详情页，但系统自动聚合同一Compiled Strategy Instance的固定6个正式Cell作为Qualification Bundle；必须6/6均Accepted/Formal且没有Product阻断项，避免只挑最好看的1Y/5bps结果升级。
- Qualification Bundle保留Full/3Y/1Y×5/10bps+impact全部证据。Product发布后以5bps+impact作为Primary Monitoring Path，10bps+impact作为Stress Monitoring Path；两者均以固定100M计算。
- Exploratory/non-PIT、Capacity Rejected、数据质量失败、未完成6格矩阵或被invalidated/tainted的依赖均使升级按钮置灰并显示原因。
- 同一Compiled Strategy Fingerprint同一时刻只允许一个Active Product，防止重复监控；退役后重新选择会创建新的Product Enrollment与新的样本外起点，不复活旧记录。

#### 创建确认窗口

- 点击升级打开明确确认Modal，展示产品名、Model/Strategy/Universe、6/6资格、100M、Primary/Stress成本、Primary Benchmark、监控起点规则与不可修改声明。
- 研究者填写产品显示名与可选研究备注，勾选确认后原子创建并激活Product；不再增加一个长期悬置的Product Draft步骤。操作写入actor、timestamp、来源Result、Qualification Bundle与审计事件，并使用idempotency key防重复提交。
- `monitoring_start_at`固定为激活后第一个合法Strategy Decision/Execution周期；发布前历史不得回填进Out-of-Sample轨道。

#### 生命周期与取消确认窗口

- 生命周期首版收敛为`active / suspended / retired / invalidated`。Health另设`healthy / watch / warning / data_interrupted`，不能把表现警告等同于生命周期退出。
- Product永不物理删除。手动“取消”在后端记录为`retired`；历史资格、监控快照、预警和人工操作永久保留，默认列表可隐藏Retired但可搜索/恢复查看。
- 取消操作必须打开二次确认Modal：展示停止官方监控的影响，要求选择固定Reason Category（performance/data/model/capacity/replaced/other）、填写说明并确认Product名称。记录`retirement_requested_at`与下一个合法决策时点`retirement_effective_at`，不得回填到已知表现之前。
- 数据损坏、上游Artifact invalidated、模型/执行契约错误等可立即`invalidated`；需要暂时停止但尚未做永久判断时可随时`suspended`。Suspended/Retired均不删除既有样本外轨道。
- 不强制“满12个月才允许退役”。研究者可随时手动退役；若样本外不足12个月且原因是performance，状态记录`early_manual_retirement`与`evidence_insufficient`，不能把该日期宣称为统计确认的策略失效时间。
- 失效研究至少分开记录`first_warning_at`、`review_required_at`、`retirement_requested_at`和`retirement_effective_at`；系统发现证据但不自动因收益不佳退役产品。

第一轮确认通过：6/6 Qualification Bundle、Primary/Stress双成本轨道、升级与取消二次确认、样本外起点、生命周期/健康分离、不可删除、允许随时退役但不足证据时明确标记等规则全部冻结。

### 17.3 第二轮：Product监控、健康与界面确认结果

#### 增量监控与三条轨道

- 每次新的正式市场数据Bundle发布后，Active Product进入持久监控队列，使用当时实际可得的数据Vintage增量计算；不得用后来修订的数据回写当时决策。
- 日常Session追加Primary 5bps+impact与Stress 10bps+impact的NAV、Benchmark、持仓、成本和容量；到Strategy决策日再追加Model Score、排名、Target与Decision Explanation。数据未就绪时保留Gap/Reason，不事后补成“当时成功”。
- Product详情严格分开：`Qualification Backtest`（发布时6格证据，永久冻结）、`Extended Frozen-Definition History`（冻结定义延伸全历史，辅助观察）、`Post-Activation OOS`（从monitoring_start_at开始，判断研究筛选与退化的主要轨道）。三者不得拼成一条无边界净值曲线。
- Monitoring Snapshot只追加不覆盖，至少冻结as-of/data vintage、Product Version、Primary/Stress路径、Benchmark、指标、健康分项、Warning Event、最新Decision与运行血缘。

#### 监控指标分组

1. **Data/Operational**：数据最新日期与延迟、Universe/Asset可用数、Factor/Signal/Model Score覆盖、Target生成状态、缺失原因、任务状态和上游Artifact健康。
2. **Execution/Capacity**：100M订单金额、最大/分位ADV参与率、Primary/Stress交易成本、换手、无法执行资产、现金/防御袖套与容量breach。
3. **Absolute Performance**：OOS累计收益、Currency NAV/Wealth Index、波动率、Sharpe/Sortino、最大/当前回撤、回撤持续时间、Calmar与日/月胜率；样本不足则undefined并给reason。
4. **Relative Performance**：相对SPY的Excess Wealth、CAGR Spread、Tracking Error、Information Ratio、Beta/Alpha；Research Benchmark相对指标作为辅助。
5. **Predictive/Structural**：ETF Top-1命中/Spread/换手；股票Rank IC、Top-Decile Spread、Top-20命中/换手；Score分布、行业/资产集中度、输入贡献和分布漂移。

#### 健康状态与预警原则

- Overall Health首版使用`observing / healthy / watch / warning / data_interrupted`。新Product在最小样本前为observing，不能因几个交易日上涨就标Healthy。
- Health由Data、Capacity、Performance、Predictive/Structural四个分项组成，Overall取最严重且显示触发依据；Lifecycle仍独立，不因Warning自动Retire。
- Data/contract硬异常使用确定性门禁：错过预期数据、Score覆盖低于Family正式门槛、rankable<K、Target无法生成或上游invalidated分别触发watch/data_interrupted/invalidated路径，不用收益表现掩盖运维故障。
- Capacity以已发布5% ADV上限为硬边界；接近边界可watch，超过边界产生Warning/Review Required且不假设100M订单已完整成交。
- Performance/Predictive不使用随意固定收益率阈值。Promotion时把历史同长度滚动窗口分布冻结为Monitoring Reference；月度复核把OOS相对收益、回撤、命中/IC等与该参考分位比较。建议连续2次月度复核落入历史后10%进入watch，连续3次落入后5%或两个独立分项同时显著恶化进入warning/review required。
- 阈值、最小样本、持续次数、Reference Artifact和触发reason均进入不可变Monitoring Policy Version；系统记录`first_warning_at`但只提示人工判断，不自动宣布“策略已失效”。

#### Products卡片页

- Products替换Compare导航，首页为Product卡片目录，不是研究排行榜，也没有勾选功能。支持产品名/Model/Strategy/Universe搜索，以及Lifecycle、Health、Family筛选和最近更新/激活时间/关键OOS指标排序。
- 卡片摘要展示：Product名称与版本、Strategy/Model Family、Universe/Asset Set、Lifecycle与Health、激活日期/OOS年龄、最新数据日期、Primary OOS累计收益、相对SPY Excess Wealth、当前/最大回撤、未关闭Warning数、下一决策/复核日期。
- Retired/Suspended/Invalidated卡片默认折叠到历史筛选中但永久可访问；卡片状态必须说明是生命周期还是健康，不用单一颜色混淆。

#### Product详情页

- 顶部冻结身份、Lifecycle/Health、最新数据、监控年龄、下一Decision/Review、暂停/退役操作；操作均使用已确认二次确认Modal。
- 详情按`Overview / OOS Performance / Decisions & Holdings / Health & Alerts / Qualification / Lineage & Exports`组织。
- 核心图表：Primary/Stress OOS NAV与SPY、Excess Wealth、Drawdown、换手/成本/ADV参与率、持仓/行业暴露、Predictive指标与Health Timeline；Qualification与OOS边界必须视觉明确。
- Alert详情显示首次触发、持续次数、指标/阈值/参考分位、当前状态、Acknowledgement与人工Review记录；关闭Alert只改变处理状态，不删除触发历史。
- 导出Product身份、Qualification Bundle、全部Monitoring Snapshot、OOS NAV/Benchmark、Decisions/Holdings、Warnings/Reviews与Lineage；图表降采样但导出保留完整数据。

第二轮确认通过：正式数据发布后增量监控、Qualification/Extended/OOS三轨分离、五组指标、observing与四分项Health、历史参考分位持续预警、Products卡片目录及完整详情/Alert/导出设计均冻结。

### 17.4 第三轮：暂停、恢复、替代与异常处理确认结果

#### 暂停与恢复

- `suspended`是可恢复的人工生命周期状态，不等同于Retired。暂停从确认后的下一个合法决策时点生效；停止生成和模拟执行新Target，但在行情数据可得时继续估值最后一组官方持仓并明确标记`held_during_suspension`。
- 严重数据/契约问题可以选择Immediate Suspension；记录请求/生效时间、原因、操作者和当时持仓。系统因数据中断只自动触发Health/Alert并拒绝错误Decision，不因收益或一般缺失自动改变Lifecycle；上游Artifact被正式invalidated时才传播为Product invalidated。
- Resume需要二次确认并通过当前Data/Contract/Capacity预检。恢复在下一个合法决策时点重新生成Target，不补做暂停期间错过的决策，也不把后来数据回填成当时交易。暂停区间、持仓漂移和恢复交易成本永久保留在OOS路径。
- `retired`与`invalidated`不可恢复；再次使用相同策略必须新建Product Enrollment和新的monitoring_start_at。

#### 新版本替代

- Model、Strategy、Universe方法、Defense、Execution或Monitoring Policy有任何语义变化，都必须形成新Compiled Strategy、重新完成固定6格Qualification并创建新Product；现有Product不得原地换版本。
- Replace操作在新Product具备升级资格后使用确认Modal，冻结`replacement_of/replaced_by`链接。旧Product在共同的下一个合法决策时点Retired，新Product同一时点Active，防止无解释重叠或空窗；两条OOS轨道保持独立。
- 训练型Model不得在Active Product中静默换权重/版本。v0.21若没有已冻结、可审计的Retraining Contract，则新训练Artifact只能作为Replacement Candidate重新实验与升级；自动滚动换模型后置。

#### 数据迟到、修订与任务异常

- 交易日/节假日由发布Calendar判断，不把正常休市当数据延迟。每个预期数据截止时间后才计算freshness SLA。
- Monitoring Worker使用持久lease/heartbeat、幂等Snapshot fingerprint和阶段事件。Infrastructure失败自动有限重试并告警；确定性data/contract/capacity失败不原样重试，等待新Data/Dependency Version或人工处理。
- 数据迟到时，官方OOS轨道保留`late_data_gap`，可以在数据到达后生成`late_diagnostic`说明“如果当时可得会怎样”，但不得补写成准时Decision/Trade。
- 数据修订发布新Vintage。原As-Known OOS Snapshot不可覆盖；可另生成Corrected Counterfactual轨道并显示差异，Product Health与失效时间仍以当时可得轨道为准，除非原数据被判定严重错误并正式invalidated。
- 如果执行日raw price/ADV缺失、rankable<K或100M容量超限，则该次官方Decision/Execution失败，继续估值上一官方持仓（数据允许时）并触发Review Required；不把目标仓位假定为已成交。

#### Alert与人工复核

- Warning Event状态为`open/acknowledged/resolved/superseded`；Acknowledged/Resolved只追加处理记录，不删除触发历史。条件再次出现可Reopen或产生新Event，按Monitoring Policy冻结规则处理。
- 月度Review记录固定Decision：`continue / suspend / retire / replace`，并保存当时Snapshot、开放Alert、理由与操作者。无Warning也可以提交Review；逾期只提醒，不自动替研究者做决策。
- v0.21只实现Products页面内通知、Badge和Review Queue，不扩展邮件、短信或外部工单系统。

#### 受控写API与审计

### 18.2 无需重新确认、直接进入最终方案的修订

1. `Accepted Result`只表示系统质量门禁通过；删除Experiment层强制人工Accepted/Rejected状态、`POST .../accept`和Completed→Reviewed→Accepted流程。研究者的选择动作是从Result Detail手动升级Product，Promotion事件本身记录选择。
2. Product提升的是`Compiled Strategy Version`，资格证据是同一Qualification Context中的固定6格；不建立长期Product Draft，确认后原子创建并激活。
3. Product前向对象统一命名为`Compiled Strategy Version → Experiment Result → Product Version/Enrollment`。旧`strategy_product_*`只作为v0.2历史表名和只读兼容映射保留，不修改既有Artifact指纹。
4. Product拆成不可变`Product Version`与一次激活周期的可变`Product Enrollment`；Lifecycle Event、Monitoring Snapshot、Alert Transition和Review均append-only。
5. Product冻结规则图、方法与资格时历史Bundle；动态Universe冻结`Universe Methodology Version`而不是有限成员名单，后续PIT Snapshot和As-Known Data Vintage逐次追加到Monitoring Materialization中。
6. Factor Variant允许用户在Family卡内单选/多选已发布版本；Signal仍反向验证并冻结精确Factor Variant依赖。
7. Sector Cap、Buffer及其他硬约束处理后若不足K，正式Decision硬失败；Reserve不能掩盖数据、模型或约束故障。
8. 股票Buffer与Sector Cap顺序冻结为：先按最新Score判断可保留持仓且保留项也必须满足Sector Cap，再按Score补位；最终不足K失败。
9. 普通防御Preset只含`none/fixed_20`；`internal_timing_v1`是Packaged Strategy内部不可配置控制器，固定使用决策时可得的SPY相对SMA200：高于`+2%`为0%防御、位于`±2%`为20%、低于`-2%`为40%；缺失时Decision失败，不回退到固定比例。
10. 正式Benchmark Set只有SPY Primary，以及ETF Selected Asset Set或股票PIT Eligible Universe的同频等权再平衡Research Benchmark。QQQ/IWB/RSP等保留为资产/参考对象，不增加正式Cell。
11. 每个Portfolio Result Bundle冻结同一Suite、Compile Submission、Compiled Strategy、as-of、Data/Universe History、Engine Set、Benchmark Set、Metric Catalog、100M与Impact Model；禁止从全库拼接不同上下文的6条结果。
12. Full/3Y/1Y分别生成带`state_reset_at`的fresh-start Strategy Simulation。它们可复用区间前Factor/Signal/Model warmup，但不能从一条含Selection Buffer的全历史持仓路径裁切；每个区间的Gross Path再由5/10bps两条Cost Path复用。
13. 100M是每条成本路径的初始Currency Capital；之后订单金额基于各自演化后的pre-trade NAV，不在每期重置100M。Currency NAV与归一化Wealth同时保存。
14. `Full Common History`在Compile时解析为不可变Comparison Context；相同模板但resolved start/end不同不得混排。以后新增候选形成新Context，不改写旧结果。
15. Compiled Model Output Schedule是模型实例身份的一部分。相同Model选择若被weekly与monthly策略使用，编译为两个可复用但独立的Model Output分支；Predictive Diagnostic按frequency/target去重。
16. ETF Predictive Top-1 Hit定义为预测Top-1与实现收益Top-1一致；股票Top-20 Hit定义为`precision@20`；同时报告随机基线、Top-Bottom realized spread和集合换手。Predictive指标基于原始Model排序，不混入Strategy Buffer/Sector Cap。
17. Canonical PIT股票数据必须支持退市、现金收购、换股合并、破产归零等terminal event与terminal total return；不能把没有下一开盘的失败公司静默删出Target。不可核验事件阻断Formal状态并给出原因。
18. 迟到数据不补写成准时Decision/Trade；但允许以`market_session + known_at`追加迟到估值事件。历史Monitoring Snapshot保持不变，查询必须显式区分As-Known Gap、Late Valuation与Corrected Counterfactual。
19. Replace不要求两个不同Schedule恰好同日决策。冻结显式`cutover_session`：新Product在自己的首个合法执行Session激活，旧Product同Session退役，两条OOS轨道独立。
20. v0.21是“复用v0.2不可变发布底座的跨层契约升级”，不是单纯前端改版。动态PIT Universe、稀疏局部缺失、Compiled Branch、fresh-start、100M冲击成本、持久Worker、两类Experiment和Product监控均是正式后端工作。

### 18.4 确认记录

1. **Q1确认**：Product只是进入样本外观察的研究候选。真正策略必须经过独立实盘验证；v0.21不得把Product称为已验证、可推荐或可实盘策略。
2. **Q4确认**：首版所有横截面排序Strategy暂时禁止使用投票/方向等低分辨率Model；这些Model仍可进入Predictive Diagnostic。未来若发布连续且可横截面比较的投票强度输出，再作为新Model Version重新审查兼容性。
3. **Q6确认**：ETF与股票Formal Score Coverage均采用逐Decision不低于90%的Versioned Quality Policy，并叠加各Family绝对数量门槛。
4. **Q7确认**：Performance/Weekly/Monthly最小观察样本分别提高至126 Sessions、26 Decisions、12 Decisions；此前只展示，不离开observing。Data/Capacity硬异常仍即时生效。
5. **Q2确认**：保留100M初始资本与5% ADV硬门槛。超限结果保留Gross与容量诊断，但不是100M Formal Accepted Result，不能进入正式排名或Product资格；四ETF Sample不保证Product Eligible。
6. **Q3确认**：训练模型不因类型被排除。只有策略回测优秀且全部系统门禁通过后才可人工升级；历史资格冻结Training & Deployment Policy并以rolling-origin、每折固定OOS部署验证，Promotion生成并冻结最终Activation Model Artifact。v0.21不自动重训；新Artifact必须重新实验并作为Replacement Candidate。
7. **Q5确认**：当前确定性聚合Family在每个Branch/Decision先取全部输入共同有效资产交集，再对连续Signal进行交集内归一化并聚合；原Signal值、模型实际归一化输入、交集规模与Policy分别保存。未来训练Model使用自己冻结的预处理Pipeline。
