# 候鸟 v0.21 开发成果审计与问题清单

审计日期：2026-08-09
审计范围：资产 → 因子 → 信号 → 模型 → 策略 → 实验 → Product、Workspace、API、Worker、PostgreSQL、血脉、缓存、前端与测试。
审计性质：只读检查；本轮没有清理正式数据，也没有修改业务逻辑。

## 1. 结论

v0.21 的主要研究链路已经能够运行，现有默认配置可以完成资产选择、信号物化、模型评分、Top-K 回测、实验展示、升级 Product 和最新建议仓位展示。核心回测的历史数据截断、周/月完成边界及下一交易时点执行结构中，本轮没有发现直接的前视错误。大盘股当前样本存在幸存者偏差，但系统已经把它标记为 exploratory warning，不属于隐藏问题。

当前版本还不适合立即冻结为“无需再改”的发布版本。最高优先级风险集中在：

1. 旧实验的完整血脉 Manifest 没有真正清除，热库中约 1.4GB 都是这类数据。
2. 一个 Product 会锁住整个来源 Suite，而不是只锁住被选中的精确证据。
3. 新实验提交后会立即删除旧 Suite，可能与仍在运行的 Worker 竞争。
4. 实验 Worker 和 Product 监控尚未成为可靠的常驻后台服务。
5. Workspace 草稿并发、保存与提交之间存在提交旧配置的可能。

## 2. 关于“实验数据是否只保留 Product”的最终建议

方向基本正确，但不能理解为“数据库里只剩 Product，其他全部立即删除”。推荐合同如下：

| 数据 | 建议留存 |
|---|---|
| 当前正在运行或正在查看的最新非 Product 实验 | 临时保留，直到下一次实验成功提交 |
| 更早的非 Product 实验结果 | 终态后删除大型结果；热库只留紧凑审计墓碑 |
| Product 资格六格 Portfolio Result | 永久保留或归档 |
| Product 真正依赖的 Predictive Result | 永久保留或归档 |
| Product 未选择的同 Suite 兄弟分支 | Product 归档成功后删除 |
| Product OOS Snapshot、Decision、Alert、Review、Lifecycle | 永久追加保留 |
| Product 引用的 Data Bundle、日历、基准、模型、信号等精确版本 | 保留或可靠冷归档 |
| canonical 行情、共享资产/因子/信号定义 | 不属于实验垃圾，不能随实验删除 |
| Workspace 按需物化缓存 | TTL + LRU 删除，不需要 Product pin |
| 非 Product 失败 Work Item/Event | 下次实验清理，但应先保留最小错误摘要 |
| 大型非 Product Manifest | 压缩冷归档；热库只保留 ID、类型、hash、时间和归档 URI |

推荐生命周期：

1. 新 Suite 成功提交后，将旧非 Product Suite 标记为 `superseded/pruning`，立即从实验页面隐藏。
2. 请求取消旧 Suite 的 queued 工作，等待 claimed/leased 工作安全结束。
3. 取得 Suite 级锁，只删除已经进入终态且不被 Product 精确引用的结果与队列记录。
4. Product 仅 pin 精确证据子图，不再 pin 整套 Suite。
5. 大序列移入可校验的 Zstd Parquet 归档；PostgreSQL 仅保留指标、hash、URI 和小型审计信息。

## 3. 当前真实存储快照

`style_rotation` 数据库当前约 **2,948MB**：

| Schema | 大小 |
|---|---:|
| `lineage` | 1,476MB |
| `strategy` | 363MB |
| `model` | 351MB |
| `data` | 263MB |
| `signal` | 193MB |
| `factor` | 129MB |
| `experiment` | 122MB |
| 其余 | 约 49MB |

关键事实：

- `lineage.lineage_manifest`：38,128 行，物理大小约 **1,395MB**，JSON 正文约 **1,313MB**。
- 旧 v0.2 业务实验表已经清空，但仍保留 9,826 个 `experiment_specification`、9,661 个 `experiment_result`、9,661 个 `interval_performance_result` 完整 Manifest；仅这三类约 **1.02GB**。
- 当前 v0.21 只有 1 个业务 Suite：1 个 Predictive Cell + 12 个 Portfolio Cell + 13 个 Result。
- `experiment.cell_result` 只有 13 行，却占约 **120MB**：Predictive series 约 22MB，12 个 Portfolio series 共约 94MB。
- 当前 Product 只需 6 个 Portfolio Result（约 47MB）及共享 Predictive Result（约 22MB）；未被 Product 选择的兄弟策略 6 个 Result（约 47MB）仍因整 Suite 保护而保留。
- 当前还有 12 个无 Suite 链接、无 Result 的失败 Work Item；血脉中残留 120 个孤立 Portfolio Cell、11 个孤立 Predictive Cell、11 个孤立 Suite 和 26 个无业务 Result 行的 v0.21 Result Artifact。
- `artifacts/` 约 2.1GB，其中约 2.07GB 是一个 v0.2 数据库 dump；研究物化缓存目前只有约 8.75MB，但没有 TTL 或容量上限。

## 4. P0：必须优先修复

### P0-1 旧实验清理保留了完整 Manifest，并非紧凑墓碑

证据：

- `scripts/purge-local-experiment-history.sql:88-90` 声称保留 artifact tombstone。
- `migrations/versions/20260802_02_v02_lineage.py:52-60` 把完整血脉树写入 JSONB。
- 同迁移约 `239` 行起禁止修改或删除已发布 Manifest。

影响：旧实验业务行虽已删除，最昂贵的完整血脉副本仍永久停留在热库；继续研究会线性或更快增长。

建议：新增真正的紧凑 `artifact_tombstone`/冷归档合同。完整 Manifest 压缩归档到带 content hash 的文件，热库只保留 artifact ID、类型、fingerprint、content hash、时间、归档 URI 和归档 hash。先做 restore-test，再用专用迁移处理现有约 1.3GB Manifest，不能直接手工删表。

### P0-2 Product 保护粒度是整 Suite，而非精确证据子图

证据：

- `src/style_rotation/experiment/history.py:20-31`：任一 Product 引用 Suite 时，整个 Suite 跳过清理。
- `src/style_rotation/product/promotion.py:127-315`：Qualification 实际冻结所选策略分支的六格结果。

影响：大型实验只升级一个策略，也会把其他模型、策略、结果和 Work Item 一并永久保留。当前已经额外保留约 47MB；未来 9,000+ Cell Suite 会更严重。

建议：建立 Product Evidence Pin 表或递归依赖闭包，只 pin：六格 Portfolio Result、对应 Predictive Result、Compiled Strategy/Model、Signal/Factor/Asset/Data Bundle、日历、Comparison Context、Benchmark、执行政策、Qualification 与 Product/OOS 记录。归档完成后，允许同 Suite 未被引用的兄弟分支回收。

### P0-3 新实验清理与运行中 Worker 存在竞争

证据：

- `src/style_rotation/api/commands.py:135-149`：新 Suite 入队后立即清理旧 Suite。
- `src/style_rotation/experiment/history.py:15-139`：未检查 queued/claimed/lease 状态便删除 Result、Cell、Suite 链接及可能的 Work Item/Event。
- `src/style_rotation/ops/worker.py:111-165`：旧 Worker 随后仍可能尝试锁定和发布结果。

影响：在途任务可能写入已删除的 Suite，失败或产生孤立 Artifact；现有库中的失败/孤立记录与这一风险一致。

建议：采用 `cancel → wait lease → suite advisory lock → terminal-only GC` 两阶段清理；增加 Suite generation fence，禁止旧 Worker 向被 supersede 的代际发布结果；补充“清理与 leased Worker 并发”集成测试。

## 5. P1：发布前应完成

### P1-1 实验 Worker 依附 API 进程，重启后不会自动续跑

- `src/style_rotation/api/app.py:1018-1040` 只在提交响应后安排 BackgroundTask。
- `src/style_rotation/api/commands.py:265-272` 单次最多消费 10,000 项。
- `scripts/start-v021-api.ps1` 只启动 Uvicorn。

影响：API 重启会留下 queued 项；超过 10,000 的实验也会留下无人领取的尾部任务，页面长期停留在 running。

建议：独立常驻 Experiment Worker，启动即恢复并持续 drain；API 只负责 enqueue；增加 queue depth、oldest queued age 和 stalled suite 告警。

### P1-2 Product 监控可能被一个失败的旧日期永久阻塞

- `src/style_rotation/ops/work_queue.py:138-152` 要求更早 monitoring work 全部 completed 才允许后续任务 claim。
- `src/style_rotation/product/monitoring_service.py:161-172` 在首项仅入队时就写 monitoring 起点。

影响：早期任务重试耗尽成为 failed/cancelled 后，所有未来日期都不能执行；OOS 起点也可能不准确。

建议：失败时原子写 `data_interrupted` Snapshot 或显式 supersede，再推进严格序列游标；`monitoring_start_at/first_decision_at` 应在首个成功 Snapshot 时落库；启动配置加入常驻 Monitoring Worker。

### P1-3 Product 预测健康基线可能混入同 Suite 其他模型

- `src/style_rotation/product/promotion.py:395-438` 查询来源 Suite 内全部 accepted Predictive Result，没有限定 Product 使用的 compiled model 与 target。

影响：多模型实验时，Product 的 warning/watch 阈值会被其他模型分布污染。

建议：Qualification 明确 pin 被升级模型+target 的 Predictive Result ID，健康阈值只使用该结果。

### P1-4 实验大型 Series 重复塞入 JSONB

- `src/style_rotation/ops/worker.py:76-83,129-152` 保存完整 metrics/series/diagnostics。
- `src/style_rotation/ops/v021_execution.py:346` 保存全部模型分数和输入审计。
- 同文件约 `611` 行起保存 NAV、Decision、Trade Capacity、Benchmark 等完整序列。

影响：单个 Predictive Result 约 22MB；单个 Portfolio Result 平均约 8MB、最大约 20MB。PostgreSQL TOAST 会快速膨胀，GC 和备份都变慢。

建议：数据库仅存小指标、状态、日期范围、行数、hash 和 URI；大序列统一为 content-addressed Zstd Parquet。Product 升级时生成独立 `Product Backtest Archive`。

### P1-5 Workspace 草稿冲突无法恢复，并可能持续重试

- `frontend/src/workspace/WorkspaceSelectionContext.tsx:73-129,156-161`：autosave 不对 409 revision conflict 进入停止/恢复状态。
- `frontend/src/pages/WorkspacePage.tsx:140`：“重新加载”实际仍调用 save，而不是 refetch/merge。

影响：多标签页或用户与自动化同时操作时，本地版本落后后可能持续重试旧 revision。浏览器审计已观察到 `Draft revision conflict`。

建议：409 后停止 autosave，GET 服务端最新草稿，提供“载入服务端 / 另存副本 / 显式合并”；同浏览器标签页使用 BroadcastChannel 同步。

### P1-6 脏草稿可以提交上一版实验配置

- autosave 有约 900ms debounce：`WorkspaceSelectionContext.tsx:123-129`。
- `WorkspacePage.tsx:51-60,137` 提交使用当前已保存 revision，未检查 dirty/saving/error。

影响：用户修改选择后立即点击“运行探索性实验”，可能提交服务端上一版配置。

建议：提交操作必须原子执行 `save → 使用 save 返回 revision submit`；dirty、saving 或 conflict 时禁用提交按钮并显示明确状态。

### P1-7 调仓频率存在 URL 与 Workspace 两套状态源

- `frontend/src/pages/SignalsPage.tsx:17-30`、`ModelsPage.tsx:17-25` 从 URL 独立读取 frequency。
- `frontend/src/components/AppShell.tsx:47` 侧栏只保留 lang。

影响：页面可能按 monthly 显示合法性，但写回的服务端草稿仍是 weekly，造成研究配置与视觉状态不一致。

建议：Workspace frequency 为唯一事实源；URL 只作为镜像/深链参数，并在 mount 与 URL 变化时统一规范化。

### P1-8 当前 CI/回归测试是红色

本轮结果：

- 后端单元测试：267 passed，1 failed。
- 后端集成测试：24 passed，3 failed。
- 四个失败均为新增迁移 `20260808_45_v021_candidate` 后，测试仍断言旧 migration head。
- 全仓 Ruff：`tests/unit/test_product_qualification.py` 有 1 个 import-order 错误。
- strict Mypy：通过（185 个源码文件）。
- 前端 typecheck、lint、build：通过；Vitest 14/14 通过。

建议：更新 migration head 断言、修正 import 排序，并将全套检查放入一次固定 CI 命令。虽然这些失败目前不是业务逻辑错误，但会阻止可靠发布。

## 6. P2：重要但可分批推进

### 后端与数据链

1. **按需信号物化的血脉角色不真实。** `src/style_rotation/ops/v021_execution.py:1553-1558` 用 Signal Version Artifact 冒充 Signal Dataset；`ops/worker.py:87-98` 又以 dataset/target role 发布。建议新增 materialization manifest Artifact，准确区分 signal version、materialized signal dataset 与 computed target。
2. **研究缓存没有 TTL/LRU/quota。** `workspace/materialization.py:398-512` 只有 last_accessed_at。建议默认 TTL 14 天、容量上限、LRU 和删除一致性检查。
3. **资产级数据输入选择尚未进入契约。** Draft 只有 asset IDs（`api/schemas.py:352-361`）；物化与 FactorBar 只加载 close/volume（`workspace/materialization.py:277-309`、`factor/calculator.py:13-20`）；前端 checkbox 仍 disabled。建议先新增 versioned `DataSeriesSelection` 和 PIT known_at/effective_at，再扩 OHLC、PE、ROE。
4. **Product 推荐日历未绑定冻结 Bundle。** `product/recommendation.py:278-351` 从所有 published calendar version 取 DISTINCT session。建议只使用 Product Data Bundle 中确切的 calendar version。
5. **信号总导出与首次 Product 推荐均为同步全内存 HTTP。** `signal/research_export.py:71-184`、`api/app.py:1268-1284`、`product/recommendation.py:25-166`。建议导出改成持久 Work Item + Artifact + 流式下载；推荐在新 Bundle 发布时预计算，GET 只读缓存。
6. **Work Queue enqueue 有 TOCTOU。** `ops/work_queue.py:67-109` 先 SELECT 再 INSERT，并发相同 fingerprint 时 loser 可能 IntegrityError。建议 `INSERT ... ON CONFLICT` 后重查。
7. **幂等命令存在成功后响应未落库的 crash window。** `ops/idempotency.py:58-94` 的业务操作与 command response 分事务。建议提供审计修复/重建 response 的管理入口。
8. **market bundle member 依赖 ordinal 偶然正确。** `ops/v021_execution.py:1124-1135` 取第一个含 daily_bar 的 member。建议要求显式 role=`canonical_market`。

### 前端与产品体验

1. **初次草稿 GET 失败没有用户可见错误或重试。** `WorkspaceSelectionContext.tsx:92-120,156-159`。
2. **Product 详情错误恢复请求不正确，命令失败静默。** `ProductsPage.tsx:51-55,112-129,159-168`。不同 query/mutation 应各自显示 pending/success/error 并重试正确请求。
3. **Product recommendation 在任何 tab 都每 60 秒轮询。** `ProductsPage.tsx:106-111`。建议只在“持仓决策”tab 启用，或基于 Bundle version 条件刷新。
4. **英文界面仍有大量中文，`html.lang` 初始值错误。** `ProductsPage.tsx:61-261`、`ExperimentsPage.tsx:165-245`、`i18n.ts:53-69`。建议全部进入 i18n，并修改当前固化中文的测试。
5. **运行记录页仍是 M7 空壳。** `App.tsx:40`；离开带 `?suite=` 的实验页后难以找回活动进度。建议增加 Suite/WorkItem 列表 API 和 Recent/Active Runs 页面。
6. **移动端主导航完全隐藏。** `styles.css:512-516` 在 <=700px 隐藏 nav，却没有菜单入口。建议可访问的抽屉/折叠菜单。
7. **模态框没有焦点管理、Escape 与焦点恢复。** `AssetsPage.tsx:187-215`、`ExperimentsPage.tsx:208-245`、`ProductsPage.tsx:168`。建议统一标准 Dialog 组件。
8. **工作台组合数忽略 target 维度，无效选择只统计 model/strategy。** `WorkspacePage.tsx:99-118`。建议直接使用 compile preview 的精确计数与全层 blockers。
9. **实验 status 筛选不重置页码。** `ExperimentsPage.tsx:183-187`。建议统一 filter setter 并 `setPage(1)`。

## 8. 推荐实施顺序

### 阶段 A：先保证不丢、不乱、不堵

1. 修复草稿 `save → submit` 原子链及 revision conflict。
2. 将实验清理改为 cancel/wait/lock/terminal-only GC。
3. 独立常驻 Experiment Worker 与 Monitoring Worker，加入重启恢复。
4. 修复 monitoring failed head-of-line 与 Product predictive 基线过滤。
5. 修复 migration 测试和 Ruff，使 CI 恢复全绿。

### 阶段 B：建立正确留存合同

1. 新增只读 Retention Dry Run：列出删除对象、Product pin 原因和预计节省空间。
2. 建立 Product Evidence 精确 pin/递归依赖闭包。
3. 建立可校验的 Product Backtest Archive。
4. 大型 Result Series 转 Zstd Parquet，数据库只留小元数据。
5. 对当前 Product Suite 清理未选择的兄弟分支。

### 阶段 C：回收历史膨胀

1. 创建新备份并完成 restore-test。
2. 将旧 v0.2 完整 Manifest 压缩冷归档。
3. 热库替换为紧凑墓碑，预计可释放约 1.3GB。
4. 增加缓存 TTL/LRU 与备份轮换。

### 阶段 D：补齐研究契约和前端

1. DataSeriesSelection、OHLC 与 PIT 基本面数据契约。
2. 统一 frequency 单一事实源。
3. 完善 Runs、Product 错误态、i18n、移动端与 Dialog 可访问性。
4. 补齐高风险状态机和端到端测试。

## 9. 首次真实清理前的验收条件

- Retention Dry Run 能解释每个保留/删除对象。
- Product 六格、Predictive、配置链、OOS 数据均有精确 pin。
- 新实验与运行中 Worker 的并发测试通过。
- 新旧备份至少一次 restore-test 通过。
- 清理前后 Product 页面、冻结回测、血脉和最新建议仓位完全一致。
- 数据库行数、文件数和磁盘空间的清理结果可核对。
- 所有单元、集成、前端、Ruff、Mypy 检查全绿。

当前不建议直接执行 `scripts/purge-local-experiment-history.sql`：已有 Product 时它会整体拒绝，而且即使执行也解决不了最大的完整 Manifest 膨胀问题。

### Product 精确留存的最终语义

“只保留 Product 的实验数据”不等于只保留 Product 表，也不等于保留整个来源 Suite。系统长期保留的是可复现、可解释、可继续生成建议的精确证据子图：六格 Portfolio、唯一对应 Predictive、Asset→Factor→Signal→Model→Strategy、Data Bundle、Universe、Calendar、执行/成本/基准政策、Qualification/Product 身份以及全部 OOS、Decision、Alert、Review 与 Lifecycle。来源 Suite 根身份只作为审计锚点；无关兄弟分支可以删除。

Qualification Artifact 的不可变 dependency 是权威证据，必须恰好包含六个 `qualification_result` 和一个 `qualification_predictive_result`，并逐项核对 Result 类型、来源 Suite、模型和策略。数组字段仅作一致性校验；任何不一致均对整套清理 fail-closed。
