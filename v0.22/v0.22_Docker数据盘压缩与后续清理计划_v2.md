## 1. 新结论：主要问题不是活数据，而是 VHDX 未回收空闲块

### 1.1 直接证据

- Windows 文件：`%LOCALAPPDATA%\Docker\wsl\disk\docker_data.vhdx`
- 文件实际占用：`488,493,809,664 B`，约 **454.95 GiB**。
- Docker 内部 `/dev/sdd` EXT4：逻辑容量约 1006.9 GiB，实际已用约 **49.2 GiB**，可用约 906.5 GiB。
- Windows 文件高水位与 EXT4 当前已用量相差约 **405.8 GiB**。
- 审计时 C 盘可用约 **218 GiB**。

因此，约 406 GiB 是动态 VHDX 曾经扩张后没有返还给 NTFS 的空闲块。它是 C 盘压力的主要来源。删除候鸟的几个测试卷只能减少 EXT4 内部已用量，不能自动让 455 GiB 文件显著变小。

### 1.2 当前真实 Docker 对象

`docker system df`：

| 类别 | 当前量 | Docker 可直接判定可回收 |
|---|---:|---:|
| Images | 25.74 GB | 2.052 GB |
| Containers | 1.218 GB | 1.165 GB |
| Local Volumes | 22.63 GB | 3.853 GB |
| Build Cache | 24.88 GB | 4.309 GB private cache |

这些分类存在共享层和口径重叠，不能直接相加为物理占用。BuildKit 还报告约 20.57 GB shared cache 与现有镜像层共享；删除缓存不等于额外释放同等物理空间。

Docker 根目录只读统计：

- `overlay2`：约 36.1 GiB；
- `volumes`：约 16.9 GiB 已分配块；
- `containers`：约 99.6 MiB；
- 其余元数据很小。

最终应以 EXT4 的 49.2 GiB 和 Windows VHDX 的 454.95 GiB为主口径，而不是把各类逻辑统计相加。

## 4. 新的首选路线：精确清理 + TRIM + 冷 compact

### C0：保护其他活跃项目（只读与备份阶段）

前置批准：允许为其他项目做 Docker 外逻辑备份；不删除任何资源。

1. 保存全部容器、镜像 digest、Compose project/config、mount、volume、network 和健康状态清单。
2. 对 SafeCapitAI PostgreSQL、Capstone PostgreSQL 分别生成 Docker 外 dump，并执行可解析性校验。
3. 根据实际用途备份 Redis、chart artifacts 和两个 frontend 匿名卷；明确哪些只是可重建缓存。
4. 对停止的 CS50 Kafka 4.672 GB、旧 ontology 1.148 GB 先联系对应任务确认保留/删除；不把“停止”当成“无用”。
5. 记录操作前的 VHDX 大小、C 盘空闲、EXT4 用量、Docker 对象数量和 13 个运行容器状态。

任一活跃数据库无法备份时，不进入 compact。

### C1：候鸟范围内的精确低风险清理（独立批准）

仅在用户批准精确 ID 清单后：

1. 删除候鸟测试容器和 535.3 MB 测试卷；
2. 经标签、Compose 路径和内容核验后，删除重复 `postgres-test` 两容器及约 242.3 MB 两卷；
3. 可另批处理候鸟 Object Store 的精确孤儿对象约 3.93 MB；
4. 不碰 9.466 GB 候鸟 blue 主卷、v4、旧 Product 或现有血缘。

预计仅减少约 0.78 GB Docker 活数据；它不是本次主要空间回收手段。测试资源可通过 Compose + migration 重建。

### C2：其他项目的可选清理（按所有者逐项批准）

- 停止容器可写层：理论可回收约 1.165 GB；
- 无链接卷：理论约 3.79 GiB；
- Docker 当前明确私有 BuildKit cache：约 4.309 GB；
- 未使用镜像：Docker 估计约 2.052 GB。

这些数字不能简单相加，也不要求在 compact 前全部删除。规则：

- 禁止 `docker system prune -a --volumes`；
- 禁止无范围 `docker volume prune`；
- 每个卷必须记录项目、用途、备份、重建方式和精确名称；
- 构建缓存按项目/时间窗口处理，接受下次构建变慢的代价；
- 正在运行或有容器引用的镜像、卷默认保留。

### C3：全局短暂停机、TRIM 与 VHDX compact（核心阶段，单独批准）

前置条件：C0 完成、候鸟 R2 已验证、用户批准全局短停机。

1. 记录操作前快照和既有 unhealthy 服务；
2. 用各项目 Compose 优雅停止全部 13 个运行容器；
3. 确认没有数据库或容器进程仍写入 Docker 数据盘；
4. 对精确 Docker 数据挂载执行 `fstrim`，让 EXT4 把空闲块告知底层动态 VHDX；
5. 完全退出 Docker Desktop；
6. 执行 `wsl --shutdown`，确认 VHDX 已分离且没有打开句柄；
7. 本机没有 Hyper-V `Optimize-VHD` cmdlet，因此使用 Windows 管理员权限下的官方 `diskpart`：选择精确 VHDX 后执行 `compact vdisk`；
8. compact 只执行一次；期间不得并行删除、移动、重建或改写 VHDX；
9. 启动 Docker Desktop，逐项目恢复原容器；
10. 验证 Docker/EXT4 日志无新 I/O、journal、read-only 错误；验证所有卷挂载、数据库健康、容器数量和操作前状态；
11. 候鸟额外核对 v5/v6 行数、关键 hash、Alembic head 和只读 closure；
12. 记录 VHDX 新大小与 C 盘实际回收量。

预期而非承诺：

- 理论回收上限约 405.8 GiB；
- 保守目标为 compact 后 VHDX 约 55-90 GiB；
- 预计 C 盘实际释放约 365-400 GiB。

如果一次 compact 后 VHDX 仍大于约 150-200 GiB，或出现任何新文件系统/数据库错误，立即停止，不做反复 compact，转入后备路线评审。

操作目标必须是当前用户配置下精确解析的 `%LOCALAPPDATA%\Docker\wsl\disk\docker_data.vhdx`。当前 Docker Desktop 没有单独的 `docker-desktop-data` WSL 发行版；禁止把约 136 MB 的 Docker 系统盘误当作数据盘。禁止用 `dd` 或写零填满 EXT4 来“辅助压缩”，也禁止盲目执行 `wsl --manage docker-desktop --set-sparse true`；前者可能再次撑爆 C 盘，后者可能作用于错误的系统盘。任何 compact 都不得在 Docker Desktop 或 WSL 仍持有该 VHDX 时运行。

Microsoft 明确说明，动态 VHD/VHDX 会随写入扩张，但删除内部文件后不会自动缩小；`compact vdisk` 要求磁盘已分离或只读。Docker 官方也确认 WSL 2 数据默认位于用户 LocalAppData，且可通过 Docker Desktop 设置迁移 Disk image location。

## 5. compact 成功后的候鸟 clean green

compact 只解决物理空间，不改变此前已冻结的数据治理目标。随后在同一已压缩 Docker 数据盘中：

1. 创建独立 green PostgreSQL 卷和非 OneDrive Object Store；
2. 从空库运行 migration/Catalog bootstrap；
3. 只导入 R2 v5/v6 transfer package，不导入旧 Product、Draft、Round、Suite、Result、Evidence 或 cache；
4. 发布 v5-native Gate5、Cohort/Runtime11 weekly/monthly、Registry 0.22.4；
5. 周频/月频各完成一个 deterministic smoke；
6. 证明 green 中旧 Product、v4 和旧实验 UUID 为 0；
7. green 验收并经过回滚窗口后，再独立批准删除 9.466 GB blue 主卷和旧 Object Store；
8. 如 blue 删除后产生新的较大 VHDX 空洞，再安排下一次维护窗口 compact，而不是与 green cutover 混在同一次操作中。

## 6. 后备路线：仅在 compact 失败时 clean VHDX

只有以下任一条件成立才评审全盘重建：

- `compact vdisk` 明显无效；
- VHDX 仍大于约 150-200 GiB；
- 再次出现 EXT4 journal、I/O、WAL 或关系损坏；
- Docker 数据盘无法稳定挂载。

全盘重建会影响全部 154 个镜像、68 个卷、30 个容器以及当前 13 个运行容器。它必须有所有项目的恢复证明和单独的系统级 wipe 批准。推荐将旧盘隔离为短期 blue quarantine，创建空盘并只恢复活跃项目；全部验收后才另批永久删除旧盘。

相比 compact，clean VHDX 预计最多只额外节省约 10-50 GiB，却有更长停机和更高漏备份风险，因此不再作为首选。

## 7. 长期防复发

1. 每周记录 VHDX 文件大小、EXT4 used 和 `docker system df`；当 VHDX 与 EXT4 used 差值超过 50 GiB 时告警。
2. 候鸟测试数据库使用 opt-in profile，测试结束后按精确 Compose project 销毁。
3. 不长期保留失败 E2E 的匿名卷、停止容器和重复构建缓存；清理仍需项目 allowlist。
4. 为 BuildKit 设置按时间/空间的项目级维护窗口，禁止全局自动 prune volumes。
5. Docker/数据库日志设置轮转上限。
6. C 盘剩余少于 100 GiB、VHDX/EXT4 差值异常增长或日志出现 I/O/read-only 时，拒绝启动长实验。
7. 如果存在非 C 盘高速本地磁盘，优先使用 Docker Desktop `Settings -> Resources -> Advanced -> Disk image location` 迁移数据盘；不要把大 VHDX 放入 OneDrive。
8. 保持 Docker Desktop/WSL 更新；Resource Saver 只解决空闲 CPU/内存，不会替代磁盘 compact。
