# v0.22 本地运行与前端验收手册

## 标准启动

在项目根目录执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start-v022-services.ps1
```

脚本会依次构建前端、升级数据库，并默认启动四个持久服务：API、Suite Worker、Asset-export Worker 与 Research-round GC Worker。启动脚本只在所有必需记录进程均存活、API 健康、Suite Worker 心跳就绪且 v0.22 创建门禁开放后返回成功。成功后访问：

```text
http://127.0.0.1:8000
```

实验确认页只有在 Suite Worker 心跳有效时才允许“启动实验”。提交后关闭浏览器不会停止回测；进度来自数据库中的持久 Suite 状态。

Product Worker 不属于默认研究运行剖面。只在需要运行已激活 Product Enrollment 时显式启用：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start-v022-services.ps1 -EnableProductWorker
```

启用后，Product Worker 会持续检查已激活 Enrollment 的冻结计划日。尚未到达 `first_eligible_decision_session` 时没有 Product Decision 是正常状态；Product 页面会展示频率、首个可执行日期和下一个待处理日期。不得为了演示而回填未来决策。

Product Worker 不联网抓取行情，也不从多个 Dataset 中猜测“最新”输入。计划日收盘数据、历史成员、日历和 Dataset Gate 全部发布后，先查看待准备输入：

长期运行的 Product Worker 会在每次决策前先执行同一准备流程：它仅会选择同一冻结方法、完整覆盖决策区间，且在决策截止后、本次观察时间前发布的**最早合格 Gate**。这是确定性选择，不是 latest lookup；无合格 Gate 时保持 `waiting_for_input`，不会联网或回退到历史 Dataset。以下 CLI 保留为运维检查与人工补发入口：

```powershell
python -m style_rotation.cli.v022_product_input pending --observed-at 2026-08-17T21:00:00+08:00
```

再用输出中的 Enrollment、Decision Session 与经过人工/自动数据治理确认的精确 Dataset Gate 发布 Product Input Snapshot：

```powershell
python -m style_rotation.cli.v022_product_input prepare `
  --product-enrollment-id <ENROLLMENT_UUID> `
  --decision-session-id <SESSION_UUID> `
  --dataset-gate-assessment-id <GATE_UUID> `
  --actor-key local_product_operator
```

只有该 Snapshot 发布成功后，Product Worker 才执行加工、聚合、策略、防御与合并。未准备时状态为 `waiting_for_input`，不会偷用推广时的历史 Dataset，也不会提前发布 missing Decision。输入准备命令可安全重放；同一 Enrollment × Session 的不同语义会被不可变身份拒绝。

## 停止

```powershell
powershell -ExecutionPolicy Bypass -File scripts/stop-v022-services.ps1
```

停止脚本只处理 `services.json` 中记录且进程启动时间吻合的 PID，不扫描或停止其他项目进程。

## 日志与就绪状态

运行日志和状态文件位于：

```text
%LOCALAPPDATA%\style-rotation\v022-services
```

API 就绪检查：

```text
GET /api/v2/workspace/graph-suite-runtime/readiness
```

`ready=true` 表示本地 Suite Worker 正在轮询或执行工作；`stale`、`stopped`、`unavailable`、`error` 均禁止创建新实验。

本地进程清单保存在 `services.json`，标准启动后的名称必须恰好包含：

```text
api
suite-worker
asset-export-worker
gc-worker
```

Asset-export Worker 处理资产批量导出；GC Worker 清理已关闭且不再被 Product/Evidence 强根引用的普通研究轮次对象。两者的标准输出与错误日志位于同一运行目录。

使用 `-EnableProductWorker` 启动时，`services.json` 还必须包含 `product-worker`。Product Worker 的标准输出与错误日志分别为 `product-worker.stdout.log` 和 `product-worker.stderr.log`。它当前没有独立 HTTP readiness 端点，因此启动脚本以受控 PID/启动时间匹配验证其存活；Product 的实际进度仍以数据库中的冻结 Schedule 与不可变 Decision 为准。

## 备份恢复与环境迁移

长期备份不要写入 OneDrive 项目目录。先在非同步磁盘建立受控备份根，再执行：

```powershell
style-rotation backup create --output C:\ProjectBackups\style-rotation\v022.dump --git-commit <GIT_COMMIT> --docker-service postgres
style-rotation backup object-create `
  --backup-record-id <BACKUP_RECORD_ID> `
  --bundle-root C:\ProjectBackups\style-rotation\v022-strong-objects
style-rotation backup restore-joint `
  --backup-record-id <BACKUP_RECORD_ID> `
  --docker-service postgres `
  --bundle-root C:\ProjectBackups\style-rotation\v022-strong-objects `
  --restored-object-root C:\ProjectRestoreDrill\style-rotation\v022-objects
```

备份与恢复过程采用文件流，可处理大于可用内存的数据库和 Object Store。对象包只包含已发布、已物化
且 retention class 为 `product | evidence | export | legal_hold` 的强根闭包；缓存对象可重新物化，不纳入长期
备份。`restore-joint` 会验证 schema revision、项目 schema、受限 search path 下的 canonical fingerprint、
恢复数据库中的 Manifest 闭包以及每个对象的 hash/大小，并自动发布联合 Restore Evidence。

数据库 dump 与对象包必须在同一个维护只读窗口创建，备份根和恢复演练根都应位于非 OneDrive 目录。
恢复目标必须是空的独立目录，不会覆盖生产 `artifacts/v022_payloads`。只通过数据库 `restore-test` 或只复制
对象目录都不是完整恢复点；详见 [`M8_RELEASE_RUNBOOK.md`](m8/M8_RELEASE_RUNBOOK.md)。
