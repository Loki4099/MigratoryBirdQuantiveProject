# 候鸟 v0.22：异构 Payload、端口兼容、存储导出与加工模型契约

> 文档等级：`historical/non-normative`  
> `superseded_by`：[`候鸟v0.22最终开发计划.md`](候鸟v0.22最终开发计划.md) 第 4、7.3、7.4、14 节；Run Output、增量、Export Intent、GC 和备份契约以 RC1 为准。

> 状态：设计讨论稿  
> 目标：允许三个加工层处理数值、表格、向量、文本、事件、Pattern 和模型状态，同时保持 PIT、缓存、血缘、导出和最终聚合边界可验证。

## 1. 设计原则

v0.22 不追求“所有中间数据长得一样”，而追求所有中间数据都能回答同一组治理问题：

1. 这是什么语义和结构的数据？
2. 它属于哪些资产、实体和时间？
3. 在什么时间之后才允许被模型使用？
4. 谁生产了它，使用了哪些输入和代码/模型？
5. 它是否完整、缺失、无事件或不适用？
6. 下游端口为什么可以或不可以接收它？
7. 它的逻辑身份和物理文件是否完整、未被篡改？
8. 是否允许导出，应该以什么格式导出？

系统只统一 Envelope、索引语义和血缘，不统一具体 payload body。

## 2. 三层契约分离

```text
Logical Payload Contract
    数据的语义、轴、字段、PIT、缺失和兼容规则
                 ↓
Physical Encoding Contract
    Parquet / Arrow / JSONL / tensor bundle / model bundle 的写法
                 ↓
Payload Manifest / Instance
    某次运行实际生成的分片、哈希、覆盖和质量
```

### 2.1 Logical Payload Contract

回答“这份数据是什么”。更换压缩算法或文件分片不应改变它。

### 2.2 Physical Encoding Contract

回答“这份数据如何存储和读取”。同一逻辑契约可以拥有多个受支持编码，例如数值表既可用 Parquet，也可在导出时附 CSV。

### 2.3 Payload Manifest

回答“这一次运行具体产生了什么”。它引用精确逻辑契约、编码版本、分片字节哈希、覆盖范围和 Producer Artifact。

## 3. Payload 基础类型

顶层 `payload_kind` 使用有限集合，具体结构由 schema document 扩展：

| payload_kind | 用途示例 |
|---|---|
| `scalar_series` | 收益率、波动率、方向分数、最终信号 |
| `vector_series` | 新闻 embedding、资产特征向量 |
| `tabular_records` | OHLCV、基本面、统计摘要 |
| `event_set` | crossover、公告、新闻事件、形态出现 |
| `document_collection` | 新闻正文、公告文本、研究材料 |
| `structured_pattern` | candle body/range/shadow、Pattern candidate/quality |
| `tensor_series` | 图像、序列张量、深度模型输入 |
| `model_state` | 已训练模型、tokenizer、词表、校准器 |
| `mapping_table` | ticker/issuer/entity link、分类映射 |
| `opaque_bundle` | 暂未标准化但有严格 reader/version 的二进制对象 |

`opaque_bundle` 不能作为逃避契约的默认类型；必须声明 owner、reader implementation、hash、PIT 和禁止哪些下游。正式聚合器默认不接受它。

## 4. Logical Payload Contract Version

建议把前一轮暂放在 `processing.payload_contract_version` 的表提升到共享 `data` schema：

```text
data.payload_contract_family
data.payload_contract_version
data.physical_encoding_version
```

原因是 Raw Input、Processing、Aggregation、Experiment 和 Export 都会消费同一套契约，它不属于某一个加工层。

### 4.1 `data.payload_contract_family`

- `payload_contract_family_id`
- `contract_key` UNIQUE
- `name`
- `semantic_role`
- `description`

### 4.2 `data.payload_contract_version`

- `payload_contract_version_id`
- `payload_contract_family_id`
- `version_number`
- `artifact_id`
- `payload_kind`
- `schema_document JSONB`
- `entity_axis JSONB`
- `time_axis JSONB`
- `observation_grain JSONB`
- `primary_key_fields JSONB`
- `ordering_contract JSONB`
- `missingness_contract JSONB`
- `pit_contract JSONB`
- `quality_contract JSONB`
- `aggregation_role`
- `export_policy`
- `schema_fingerprint`
- `compatibility_class`

UNIQUE：`(family_id, version_number)`；Artifact 和 fingerprint 唯一。

### 4.3 Schema evolution

每个新版本声明与前版关系：

- `backward_compatible`：旧 reader/port 可以安全消费；
- `forward_compatible`：新 reader 可消费旧数据；
- `breaking`：必须通过显式 adapter node；
- `semantic_change`：即使字段结构相同，也必须建立新的 Contract Family 或明确新语义。

“新增一个 nullable 字段”不自动视为兼容；必须由 Catalog publisher 运行兼容检查并写入声明。

## 5. Entity Axis

所有 Payload 必须明确自己是否带实体轴：

```text
entity_axis.kind = none | asset | security | issuer | document | event | portfolio | custom
```

主要字段：

- `identity_field`；
- `identity_namespace`；
- `mapping_artifact_id`（需要 ticker/issuer/entity resolution 时）；
- `cardinality`：one_per_time / many_per_time / fixed_set / variable_set；
- `membership_semantics`；
- `duplicate_policy`。

### 5.1 资产与证券不可静默混用

Security、Issuer 和研究 Asset 是不同身份。端口若要求 asset-level 数据，而新闻 payload 是 issuer-level，必须经过已发布 entity-link/aggregation node；不能按 ticker 字符串隐式 join。

Entity mapping 自身必须是 Artifact，并带有效期和 known-at 语义。

## 6. Time Axis 与 PIT

### 6.1 最小双时间要求

任何可能随时间到达或修订的数据至少区分：

- `event_time / observation_time`：经济事件发生或数据描述的时间；
- `available_at / known_at`：系统允许研究和交易使用的最早时间。

对修订数据再增加：

- `revision_id / vintage`；
- `valid_from / valid_to`；
- `supersedes`。

### 6.2 不同数据示例

#### 市场数据

```text
session_date
observation_time = session close/open
available_at = provider/source contract 声明的可用时刻
calendar = XNYS
```

#### 基本面

```text
fiscal_period_end
filing_time
available_at
revision/vintage
```

#### 新闻

```text
published_at
ingested_at
available_at = max(published_at, ingested_at, source delay policy)
source_document_id
```

#### Pattern

```text
pattern_window_end
available_at = 最后一个必需输入已知时间 + declared processing latency
```

### 6.3 输出时间不得倒退

Node Runtime 验证：

```text
output.available_at >= max(all consumed input available_at) + declared_latency
```

如果 Node 执行 cross-sectional 或 rolling 计算，输出还必须继承真正参与计算的所有输入时点。不得只复制主输入的 known_at 来隐藏辅助数据更晚到达。

### 6.4 频率不是简单字符串

`frequency_semantics` 至少区分：

- session periodic；
- calendar periodic；
- irregular event；
- continuous timestamp；
- static/versioned；
- model-state as-of。

周频、月频采样、event-to-session aggregation、forward fill 和 timezone conversion 必须由显式 Node 完成。Runtime 不做隐式 resample。

## 7. Observation Grain 与主键

Contract 必须声明一条记录代表什么，例如：

```text
one scalar per asset per session
many news documents per issuer per timestamp
one fixed-size vector per document
many detected patterns per asset per window
one model state per training cutoff/fold
```

主键字段和稳定排序是强制项。Payload 发布前验证：

- 主键唯一；
- 排序符合 Contract；
- 字段、dtype、shape、unit 合法；
- NaN/Inf/非法 UTF-8 等被明确处理；
- 实际 coverage 与 Manifest 一致。

无稳定主键的 payload 不能获得正式可缓存身份。

## 8. Missingness：缺失不等于零、Neutral 或无事件

统一区分：

- `observed`：有实际值；
- `explicit_null`：记录存在但值缺失；
- `absent_record`：预期主键没有记录；
- `not_yet_available`：当时尚不可用；
- `not_applicable`：该实体/时点不适用；
- `masked_by_policy`：因质量、许可或研究政策屏蔽；
- `no_event`：事件型输出确认没有事件；
- `neutral`：信号明确输出零方向。

其中：

```text
no_event ≠ absent_record
neutral ≠ missing
not_yet_available ≠ observed later and backfilled
```

Contract 决定行级如何编码，Manifest 必须给出各状态计数。下游 Node 的 missing policy 必须显式声明：fail、preserve、drop with rule、impute by explicit algorithm。禁止 Runtime 自动填零或 forward fill。

## 9. Aggregation Role

Feature 到达 Stage 3 只表示可成为聚合候选，不代表所有 Aggregator 都接受。Contract 增加：

- `directional_rank_signal`：已有方向和横截面排序意义；
- `numeric_feature`：数字型特征，方向可由监督模型学习；
- `vector_feature`：固定或声明维度的向量；
- `event_feature`：事件/状态型数值表达；
- `not_aggregation_ready`：虽可投影到 Stage 3，但没有聚合器可直接使用。

确定性加权/投票 Aggregator 通常只接受 `directional_rank_signal` 或明确事件信号。初版 LightGBM 可以接受已声明的普通 `numeric_feature`，但仍不自动接受价格字符串、文档或任意表格。

最终 Aggregation Output 使用更严格契约：

- asset × decision time；
- numeric scalar 或明确 vector；
- higher-is-better；
- 横截面可比；
- missing policy 明确；
- 可直接被 Strategy 接收。

## 10. Physical Encoding Contract

### 10.1 推荐编码

| Payload kind | 主存储格式 |
|---|---|
| scalar/tabular/event/pattern | Parquet + Zstandard |
| vector_series | Arrow/Parquet fixed-size list |
| tensor_series | safetensors 或受版本控制的 tensor bundle |
| document_collection | UTF-8 JSONL 或 Parquet binary/string |
| model_state | safetensors/booster file + metadata bundle |
| opaque_bundle | 明确 MIME、reader 和文件清单 |

Pickle、joblib 任意对象和 Python marshal 不允许作为长期正式交换格式，因为可执行风险、跨版本不稳定且难以验证。

LightGBM 模型建议保存原生 booster text/binary 及独立 JSON metadata；若使用 binary，必须固定 LightGBM version 和读取验证。

### 10.2 编码版本字段

- `encoding_key / version_number`；
- `media_type`；
- `file_extension`；
- `compression`；
- `writer_version`；
- `reader_min/max_version`；
- `canonicalization_policy`；
- `partition_policy`；
- `encryption_policy`；
- `verification_implementation`。

## 11. Payload Manifest 与分片

建议新增共享表：

```text
data.payload_manifest
data.payload_partition
data.payload_manifest_partition
data.payload_quality_summary
```

### 11.1 `data.payload_manifest`

- `payload_manifest_id`
- `artifact_id`
- `payload_contract_version_id`
- `physical_encoding_version_id`
- `producer_artifact_id`
- `producer_output_port_key`
- `logical_payload_fingerprint`
- `manifest_hash`
- `partition_count`
- `byte_size`
- `row_or_item_count`
- `coverage_document JSONB`
- `quality_summary JSONB`
- `created_at`

### 11.2 `data.payload_partition`

- `payload_partition_id`
- `object_content_hash`：真实文件字节 SHA-256；
- `storage_uri`；
- `byte_size`；
- `row_or_item_count`；
- `partition_key JSONB`；
- `coverage_document JSONB`；
- `statistics JSONB`；
- `created_at`。

同一个字节对象可以被多个 Manifest 引用。

### 11.3 两类 Hash

必须区分：

1. `logical_payload_fingerprint`：逻辑契约、Producer、输入身份、覆盖和规范化内容身份；用于节点缓存和研究身份。
2. `object_content_hash`：每个实际文件的字节哈希；用于完整性校验和去重。

`manifest_hash` 覆盖按稳定顺序排列的全部 partition descriptor。

改变 Parquet row group、压缩级别或分片大小可能改变 object hash，但如果逻辑数据和 Contract 未变，可以保持相同 logical fingerprint，产生新的 encoding/manifest 表示。正式运行仍固定引用具体 Manifest，不能在背后替换文件。

## 12. 存储 URI 与 Object Store

Artifact 和数据库不保存宿主机绝对路径，使用逻辑 URI：

```text
payload-object://sha256/{hash}.{extension}
payload-manifest://sha256/{manifest_hash}
```

`PayloadObjectStore` 将逻辑 URI 映射到：

- 当前本地内容寻址目录；
- 将来的 S3/MinIO/object storage；
- 只读归档层。

所有路径解析必须验证 hash、扩展名、目标位于配置 storage root 内，不接受用户提交的任意文件路径。

### 12.1 原子发布

复用 v0.21 Cell Payload 的安全模式并扩展到多分片：

1. 写 temporary objects；
2. 逐个计算并回读验证 object hash；
3. 建立 pending publication lease；
4. 在数据库事务中发布 Node Run Artifact、Payload Manifest、Partitions 和端口引用；
5. commit 后清除 pending marker；
6. rollback 后未引用对象由安全 sweeper 延迟清理。

多输出 Node 必须所有端口 Manifest 都准备完成后一次提交。

## 13. Port Compatibility

兼容性分三次判断。

### 13.1 Catalog publish time

检查固定人工 binding：

- payload kind；
- Contract version compatibility；
- entity axis；
- time/frequency semantics；
- required fields/shape/dtype/unit；
- aggregation role；
- PIT level；
- stage adjacency；
- 明确的 input count/choice group。

Catalog 本身不合法则禁止发布。

### 13.2 Workspace compile time

结合当前研究上下文检查：

- 资产域和 identity mapping；
- 数据源/许可可用性；
- frequency/calendar；
- 最小历史和 warm-up；
- Aggregator 的完整输入政策；
- training target/fold policy；
- export policy。

### 13.3 Node run time

对实际 Payload 检查：

- Manifest 和 partition hash；
- schema conformance；
- coverage、主键和排序；
- missingness/quality 阈值；
- available_at 不倒退；
- 输入间实际对齐；
- model state/reader 版本。

### 13.4 Compatibility Result

```json
{
  "compatible": false,
  "phase": "compile_time",
  "reason_codes": ["entity_axis_mismatch"],
  "source_contract_id": "...",
  "target_port": "news_by_asset",
  "path": [],
  "details": {}
}
```

Reason code 稳定、可本地化；不能只返回自由文本。

## 14. 禁止隐式转换

Runtime 不自动执行：

- 字段重命名；
- dtype coercion；
- 单位转换；
- ticker/issuer/asset join；
- resample；
- forward fill/impute；
- text embedding；
- vector flatten；
- table-to-signal；
- timezone/calendar 对齐。

这些行为都必须是人工 Catalog 中的显式 Processing Node，并在血缘中出现。

唯一无需新计算节点的传递是已经确认的 Layer Projection：它不改变 Contract、内容、时间、实体或值，只改变 Feature 在下一层的可见 occurrence。

Reader 将物理编码解码为同一逻辑结构不算数据转换，但 reader/version 必须由 Encoding Contract 固定。

## 15. 对齐与多输入 Node

一个 Node 可以接受多个上一层输入，但必须声明 alignment contract：

- join keys；
- inner/left/exact-set；
- timestamp/session matching；
- tolerance window；
- latest-known-as-of；
- revision/vintage policy；
- duplicate resolution；
- missing result policy。

默认策略是 `exact_declared_key_set`，不是 pandas 默认 inner join。

Pattern 示例：

```text
Stage 1 inputs:
open, high, low, close

alignment:
exact asset + session_date
same calendar
same known-at class
any missing OHLC → output absent with reason input_missing

outputs:
body, range, upper_shadow, lower_shadow
```

News 示例：

```text
documents + entity links
→ explicit as-of join
→ asset/session news set
→ sentiment/event/vector feature
```

## 16. 加工层模型

加工层使用模型时必须把“训练”和“推断”分开，不能把一个模糊 `model node` 同时解释为二者。

### 16.1 Frozen Inference Node

适合：预训练 embedding、固定新闻分类器、已经发布的 Pattern detector。

依赖：

- Model State Artifact；
- tokenizer/preprocessor Artifact；
- inference implementation/environment；
- 上一层数据 Payload；
- calibration/threshold Artifact（如有）。

Model State 是 Node Version 的冻结 Artifact dependency，不由 Workspace 用户选择或训练。

### 16.2 Fit/Transform Processing Node

适合未来需要在研究上下文内训练的 Pattern/representation 模型。必须拆为：

```text
Training Run → Model State Payload
Model State + Feature Payload → Inference Run → Feature Output
```

Training Contract 必须包含：

- training feature/label contracts；
- cutoff and available-at；
- rolling/expanding/fixed window；
- fold schedule；
- purge/embargo；
- random seed；
- deterministic/nondeterministic declaration；
- library/environment Artifact；
- hyperparameters；
- training dataset manifests；
- metrics and acceptance gate。

每个 fold 的 Model State 和输出必须独立追溯，不能用全样本训练状态回填历史 Feature。

### 16.3 建议的 v0.22 首发范围

物理 Contract 和表结构同时支持 Frozen Inference 与 Fit/Transform，但首个可用版本只启用 Frozen Inference Processing Node。Fit/Transform 先标记 planned，等 Pattern/news 研究明确训练设计后再打开，避免在主架构迁移中同时引入第二套 walk-forward 训练系统。

Aggregation LightGBM 不受此限制，因为它本来就在实验分支中以 Target Variant 和训练时序为核心身份，使用 aggregation 专属训练流程。

## 17. 分层导出

### 17.1 Export Request 身份

导出请求必须引用：

- Compiled Graph Artifact；
- Feature Occurrence ID / visible stage；
- 精确 Payload Manifest；
- 选择的资产/时间范围；
- export encoding；
- redaction/license policy；
- export implementation version。

不能只用 Feature key 查询 latest 数据。

### 17.2 Export Policy

Contract 声明：

- `full_allowed`
- `derived_only`
- `metadata_only`
- `redacted`
- `denied`

例如新闻正文可能因许可只能 metadata/derived export，但其情绪分数或 embedding 是否允许导出由独立 Contract 决定。

### 17.3 Export Package

包含：

```text
manifest.json
README.md
lineage.json
schema/
data/
quality/
```

`manifest.json` 列出 Contract、Manifest、Producer、输入 Artifact、stage occurrence、PIT、hash 和格式。每个文件下载前后均可验证 SHA-256。

Export Package 本身发布为 `layer_export_package` Artifact，依赖被导出的 Payload Manifest 和 Compiled Graph。下载文件可以按 retention 过期，但 Export Artifact 和请求身份保留；需要时可按同一 fingerprint 重建。

### 17.4 尚未物化的输出

导出接口不能在 Web 请求中同步计算。它创建 export job，并通过 Graph Scheduler 先物化所需祖先/节点，再打包。UI 明确显示：

```text
等待加工节点 → 正在物化 → 正在打包 → 可下载
```

## 18. 数据质量与发布状态

每个 Payload Manifest 记录：

- schema validation；
- primary-key uniqueness；
- row/item count；
- entity/time coverage；
- missingness breakdown；
- finite/shape/encoding checks；
- PIT checks；
- input/output alignment checks；
- domain-specific diagnostics；
- warning/error reason codes。

状态建议：

- `staged`
- `validated`
- `published`
- `quarantined`
- `invalidated`

只有 Published 且未 invalidated 的 Payload 可被正式运行复用。Quarantined 文件保留用于审计，不进入下游。

## 19. 安全与资源限制

- 文本和压缩包读取设置大小、行数、嵌套深度和解压比限制；
- 不执行来自 Payload 的代码、宏、pickle 或 notebook；
- Model State reader 采用 allowlist；
- 文档正文和导出执行许可策略；
- URI resolver 禁止目录穿越和任意 scheme；
- vector/tensor shape 在分配内存前验证；
- 每个 Node Version 声明 CPU/GPU/memory/time 预算；
- 超预算失败归类为 capacity，不无限重试；
- 日志不得写入完整新闻正文、凭证或受限数据。

## 20. 测试门槛

### Contract

- Schema evolution compatibility；
- entity/time/PIT 完整；
- 无主键、无 stable ordering 拒绝发布；
- Contract/Encoding 分离；
- Aggregation role 校验。

### Storage

- 多分片 hash 和 manifest hash；
- 临时写入、崩溃、rollback、pending marker；
- byte corruption 被发现；
- 同内容去重；
- logical fingerprint 不因合法重编码变化；
- GC 不删除 pending 或被引用对象。

### Runtime

- 禁止隐式 resample/coercion/join；
- available_at 不倒退；
- multi-input alignment；
- missing/no-event/neutral 不混淆；
- multi-output 原子发布；
- Frozen Model State 精确血缘；
- training fold 无未来数据。

### Export

- 各 payload kind 的导出格式；
- license denied/redacted；
- 未物化时正确排队；
- manifest 和文件 hash 可验证；
- Layer Projection 不复制身份。

## 21. 本轮需要确认的问题

### Q1：Payload Contract 的 schema 归属（已确认）

已确认将其从此前暂定的 `processing` 提升到共享 `data` schema，因为 Raw、Processing、Aggregation、Experiment 和 Export 都需要使用同一套 Payload Contract/Manifest 基础设施。后续物理迁移与代码实现均以 `data.payload_contract`、`data.payload_manifest` 及其共享子表/引用为准；`processing` 只保留加工目录与运行语义。

### Q2：逻辑身份与物理文件使用两类 Hash（已确认）

已确认同时保留 logical payload fingerprint 和每个 object 的 byte hash。合法重编码可以不改变逻辑身份，但任何正式运行仍固定引用具体 Manifest，不能静默替换文件。

### Q3：是否完全禁止隐式数据转换（已确认）

已确认。除了纯 Layer Projection 和按 Encoding Contract 解码之外，单位、频率、entity join、缺失填充、embedding、字段转换等全部必须是人工发布的显式 Processing Node。

### Q4：加工层模型的首发范围（已确认）

已确认 Schema 同时支持 Frozen Inference 与 Fit/Transform，但 v0.22 首发只开放冻结模型推断；加工层训练先保持 planned，等 Pattern/news 研究形成明确的 walk-forward 与标签契约后再启用。Aggregation LightGBM 仍按本轮计划独立实现训练。
