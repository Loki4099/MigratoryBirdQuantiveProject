# 候鸟 v0.22：实施架构、Catalog 发布与 v0.21 迁移验收方案

> 文档等级：`historical/non-normative`  
> `superseded_by`：[`候鸟v0.22最终开发计划.md`](候鸟v0.22最终开发计划.md) 第 6、7、12—15 节；Run/Graph binding、DAG ready gate、86-model parity 与里程碑顺序以 RC1 为准。

> 状态：详细实施参考；总范围与顺序以 [`候鸟v0.22最终开发计划.md`](候鸟v0.22最终开发计划.md) 为准  
> 前置决定：核心拓扑、身份、物理 Schema、编译契约和 Workspace API 已冻结。  
> 本文目标：确定如何在不破坏 v0.21 的前提下实现 v0.22，并逐一迁移现有 51 个信号。

## 1. 现状盘点

v0.21 当前 Catalog 的准确规模是：

| 对象 | 数量 |
|---|---:|
| Raw market inputs | 9 |
| Factor definitions | 12 |
| Factor variants | 28 |
| Signal templates / families | 27 |
| Concrete signal versions | 51 |
| Product-eligible signal versions | 41 |
| Research-only signal versions | 10 |
| Available deterministic model families | 3 |
| Planned model families | 1（LightGBM） |
| Cross-sectional strategy families | 2 |

51 个信号按当前输出形式分布：

| v0.21 form | Template 数 | 具体信号数 |
|---|---:|---:|
| continuous | 18 | 39 |
| threshold_state | 3 | 4 |
| crossover_event | 6 | 8 |

现有 `WorkspaceSignalMaterializer` 把以下职责集中在一个服务内：

```text
选择 Signal
→ 查询其 Factor Variant
→ 读取固定 market bars
→ 调用 Factor IMPLEMENTATIONS
→ 调用统一 Signal calculator
→ 一次性缓存全部最终 Signal
```

可保留的能力：

- Data Bundle 冻结；
- Artifact recipe；
- 内容寻址 fingerprint；
- Parquet 外部存储和原子替换；
- 缓存复用；
- 缺失值、PIT、资产和日期身份；
- Worker lease、heartbeat、retry、cancel、failure class。

必须拆除的耦合：

- 运行器只认识 Factor → Signal 两层；
- 输入只认识 market bars；
- 一个缓存覆盖整组最终 Signal，而不是节点输出；
- 输出结构固定为数值 Signal；
- Work Queue 把 Predictive → Portfolio 等待关系写死在 SQL；
- Catalog 由三个大文件拼成一个文档，无法独立发布任意加工节点。

### 2.1 `processing`

负责：

- Processing Catalog 契约和发布；
- Payload Envelope；
- Node executor registry；
- 节点执行 fingerprint；
- Node Run Artifact 和多端口输出；
- 节点级缓存。

不负责：

- Workspace 当前选了什么；
- 聚合模型训练；
- 实验分支展开；
- Product 生命周期。

### 2.2 `aggregation`

负责：

- Aggregation Family/Version/Target/Preset；
- 输入政策和 slot assignment；
- 训练集构造、训练和推断；
- Aggregation Run Artifact；
- 最终 Signal 输出契约。

加工层内部即使使用 ML/NLP 模型，也仍归 `processing`；只有消费 Stage 3 最终输入并输出统一最终信号的节点归 `aggregation`。

### 2.3 `workspace.graph_*`

负责：

- Draft Intent 事件；
- 正向合法性和反向祖先闭包；
- 锁与级联影响；
- Catalog Rebase diff；
- Compiled Graph；
- Aggregation × Strategy × Defense 分支展开。

`graph_solver` 必须是纯函数式领域层：给定 Draft、Catalog 和 Context Snapshot，返回相同 Derived View，不直接写数据库。

`graph_compiler` 在 solver 结果通过后规范化并生成 Artifact payload；持久化由 service/repository 在事务中完成。

### 2.4 `compatibility`

兼容层不是永久的新事实源。它只承担：

- 把 v0.21 Catalog 映射成 v0.22 parity manifests；
- 在 v0.22 Node Executor 中复用已验证的旧 calculator；
- 对同一个 Data Bundle 双跑 v0.21/v0.22；
- 发布 Parity Evidence Artifact。

不得让新原生 Node 反向依赖 v0.21 Factor/Signal 数据表。兼容适配器可以调用旧纯计算函数，但新运行身份和输出必须使用 v0.22 Artifact。

## 3. Node Executor 协议

### 3.1 通用接口

```python
class ProcessingNodeExecutor(Protocol):
    def execute(
        self,
        *,
        context: NodeExecutionContext,
        inputs: Mapping[str, tuple[PayloadRef, ...]],
        parameters: Mapping[str, JsonValue],
    ) -> Mapping[str, ProducedPayload]: ...
```

输入和输出都按 port key 组织，不要求是 DataFrame。

### 3.2 `PayloadRef`

至少包含：

- owner Artifact ID；
- output port key；
- payload kind；
- schema/payload contract fingerprint；
- storage URI；
- content hash；
- asset/time scope；
- frequency/event-time semantics；
- PIT policy；
- row/item count。

### 3.3 `ProducedPayload`

Executor 返回暂存输出，不直接发布 Artifact：

- temporary storage lease；
- output port key；
- content hash；
- schema fingerprint；
- coverage and counts；
- diagnostics；
- quality status。

Runtime 在同一 Node Run 的全部输出成功后原子发布 Node Run Artifact 和端口记录，再 finalize temporary lease。任一输出失败，整次多输出 Node Run 不得部分发布。

### 3.4 Executor Registry

Registry 只根据 Catalog 中冻结的 `implementation_ref` 找实现：

```text
python:style_rotation.compatibility.v021_execution_adapter:factor_v1
python:style_rotation.compatibility.v021_execution_adapter:signal_v1
python:style_rotation.processing.patterns:candlestick_components_v1
model-artifact:{artifact_id}
container:{image_digest}
```

禁止根据 Family 名称猜测执行器，禁止动态执行 Catalog 中的任意公式字符串。

前端仍不能书写或上传公式；新的实现只能通过代码审查和 Catalog 发布进入系统。

## 4. 节点级内容寻址缓存

v0.21 缓存 key 覆盖整组 Signal；v0.22 改为每个 Node Run 独立 fingerprint：

```text
node_execution_fingerprint = hash(
    node_version_artifact_id,
    exact input artifact + output port + content hash,
    frozen parameters,
    asset context snapshot,
    time range,
    frequency,
    PIT/alignment policy,
    executor environment artifact
)
```

好处：

- 两个下游信号共享 Stage 1/2 祖先时只计算一次；
- 新增一个聚合器不需要重算加工层；
- 同一 Node 的多个输出一起命中缓存；
- 单个节点版本升级只使其自身和后代失效；
- 不同实验可以复用相同 Payload Artifact。

缓存记录只是对已发布 Node Run 的快速索引；Artifact 和 output content hash 才是身份。缓存文件缺失时可以重建，不能伪装为仍然可用。

## 5. 通用 DAG 调度

### 5.1 扩展现有 Work Queue，而不是另造队列

保留：

- partial unique active work；
- lease/heartbeat/reclaim；
- retry budget；
- cancellation；
- typed failure class；
- persistent work item event。

新增 work types：

- `processing_node`
- `aggregation_train`
- `aggregation_score`

### 5.2 `ops.work_item_dependency`

```text
work_item_id
depends_on_work_item_id
required_terminal_status = completed|reused
dependency_role
ordinal
```

PK：`(work_item_id, depends_on_work_item_id, dependency_role)`。

Claim 的通用条件增加：

```sql
NOT EXISTS (
  dependency whose upstream work item is not completed/reused
)
```

同时检测 dependency cycle。这样 Stage 2 等待 Stage 1、Stage 3 等待 Stage 2、Aggregation 等待全部输入，不再增加新的硬编码 SQL 分支。

### 5.3 Graph Scheduler

1. 读取 Compiled Graph；
2. 按 occurrence/node fingerprint 查找可复用的 Published Run；
3. 缓存命中则直接绑定 Artifact；
4. 未命中则为 Node 创建 Work Item；
5. 根据编译边创建通用 Work Item dependencies；
6. Aggregation train/score 等待所有 Stage 3 输入；
7. Predictive/Portfolio 实验 Cell 只等待所需 Aggregation output；
8. Suite 状态聚合全部节点、聚合和实验 Cell 的状态。

取消 Suite 时，只取消没有被其他活跃 Suite 共享的待执行工作；共享的内容寻址 Node Work Item 继续运行。Suite 与 Work Item 必须通过引用关系而不是所有权假设连接。

Release manifest 只列出允许进入该发布的组件及精确版本。目录中存在草稿文件不代表用户可见或可执行。

### 6.2 一个配置节点是否需要一个文件

不强制每个 Variant 一个手写文件。一个 Feature Family 文件可以声明多个 Variant，并为每个 Variant 引用唯一 Processing Node recipe。发布器展开后仍为独立 Artifact。

这兼顾：

- 用户端 Family 归纳；
- 研究者同时审查同公式的参数组；
- 数据库和血缘中的精确 Variant/Version；
- 避免为 51 个信号制造 51 份大量重复的 JSON。

### 6.3 Catalog CLI

建议提供：

```text
python -m style_rotation.cli.v022_catalog lint <release-manifest>
python -m style_rotation.cli.v022_catalog diff <old-release> <new-release>
python -m style_rotation.cli.v022_catalog plan <release-manifest>
python -m style_rotation.cli.v022_catalog publish <release-manifest>
python -m style_rotation.cli.v022_catalog verify <catalog-artifact-id>
```

- `lint`：纯文件和图校验，不写库；
- `diff`：按 Family/Variant/Version/edge/contract 展示语义变化；
- `plan`：展示将创建/复用的 Artifact 和依赖；
- `publish`：单事务发布；
- `verify`：从数据库重建 canonical document，检查 hash、成员和依赖。

Publish 不提供“自动修复”。非法图必须修改源文件后重新 lint。

## 7. v0.21 Parity 拓扑

第一阶段迁移不重新发明 51 个信号的计算逻辑。采用最小等价映射：

```text
Raw Input
    ↓
Stage 1：v0.21 Factor Variant calculator（28 个具体输出）
    ↓
Stage 2：v0.21 Signal transform（51 个具体输出）
    ↓
Stage 3：zero-copy Layer Projection
    ↓
Aggregation
```

其中：

- 12 个 Factor definition 映射为 12 个 Feature Family；
- 28 个 Factor variant 映射为 28 个 Stage 1 Feature Variant；
- 27 个 Signal template 映射为 27 个 Feature Family；
- 51 个具体 Signal 映射为 51 个 Stage 2 Feature Variant；
- Stage 3 不增加伪计算节点，只投影用户选择的 Stage 2 或更早 Feature；
- 旧 calculator 通过 compatibility executor 调用，输出重新包装为 v0.22 Payload。

这是 parity topology，不代表永远保持两次计算。完成一致性迁移后，pattern、新闻、技术形态以及值得拆解的复杂因子再按 v0.22 原生语义重新设计三层节点。

### 7.1 为什么不在迁移时强行填满三层

强行把旧公式拆成三个计算节点会同时改变：

- 浮点运算顺序；
- warm-up 和 missingness；
- 时间对齐；
- 缓存边界；
- Feature Family 身份；
- 现有 Signal 的经济解释。

这会使“架构迁移”和“研究逻辑变化”无法区分。Stage 3 projection 是正式能力，不是临时作弊；先保证结果等价，再通过新的 Catalog Release 做原生重构。

## 8. Migration Registry

`v0.22/catalogs/migration/v021_signal_mapping.json` 为每个旧对象记录：

- v0.21 factor/signal key；
- v0.21 definition/version Artifact ID 或稳定定位规则；
- v0.22 Family、Variant、Version；
- Stage 1 Node；
- Stage 2 Node；
- Stage 3 projection policy；
- product eligibility；
- migration status；
- parity evidence Artifact ID；
- reviewer and review timestamp；
- approved Catalog Release。

状态机：

```text
unmapped
→ mapped
→ catalog_validated
→ executable
→ parity_passed
→ research_reviewed
→ release_approved
```

任何信号都不能因为同 Family 的另一个 Variant 通过而自动跳过自己的 parity。Family 级校验降低重复工作，但 51 个具体 Variant 都必须有结果证据。

## 9. 分批迁移顺序

### Wave 0：基础设施

- 新 Schema、Catalog Publisher、Graph Solver/Compiler；
- Payload Envelope、Node Runtime、节点缓存；
- Work Item dependency；
- 9 个 Raw Input；
- v0.21 adapter 和 parity harness。

不开放给正式实验。

### Wave 1：三条代表链路

迁移已经设计过的：

- `return_continuation`；
- `price_cross_above_ma`；
- `low_illiquidity_quality`。

三条链覆盖：连续横截面排名、需要前一期状态的 crossover、价格和成交量共同输入。通过后证明框架可以承载主要 v0.21 语义。

### Wave 2：全部 Stage 1 Factor

- 12 个 Family；
- 28 个 Variant；
- 每个输出与旧 Factor calculator 比较；
- 完成共享祖先缓存验证。

### Wave 3：39 个 Continuous Signal

- 18 个 Family；
- 验证 cross-sectional centered rank、average tie、方向和 missingness；
- 首先迁移 41 个 product-eligible 集合中属于 continuous 的部分。

### Wave 4：4 个 Threshold + 8 个 Crossover

- 阈值状态精确分数/状态；
- crossover 必须使用紧邻的上一公共观察日期，且该资产在上一期确有观测；不得跨过缺口寻找更早值；
- 新上市/暂时缺失资产不得伪造事件；
- 事件与非事件 neutral 语义完全一致。

### Wave 5：Deterministic Aggregation 与策略

- single_signal；
- signal_equal；
- dimension_equal；
- directional_vote；
- multi_etf_top_k；
- us_large_cap_top_k；
- none/fixed_20/internal_timing_v1 防御设置先保持兼容。

### Wave 6：LightGBM Continuous Cross-Section Rank Regression

- 作为第一个 v0.22 新聚合能力，不属于 v0.21 parity；
- 首版 family 为 `lightgbm_cross_section_rank_regression`，连续回归中心化横截面排名；LambdaRank 保持独立 planned family；
- 首版先复用 weekly/monthly 的下一计划调仓执行开盘 Target；严格 H5/H21/H63 固定 session horizon 后续作为同 Target Family 的不同 Variant；
- 首发只开放 `conservative_v1`；其他超参数为同 Family 的 planned Preset；
- 必须单独完成训练时序、PIT、walk-forward 和可复现性验收。

### Wave 7：默认切换与旧路径冻结

- v0.22 Workspace 成为新草稿默认；
- v0.21 Workspace 保持历史只读和必要重跑；
- 不删除 v0.21 Artifact、表、calculator 和 Product 查询；
- 停止向旧 Catalog 添加新研究信号。

## 10. Parity Evidence

### 10.1 固定 Golden Context

至少包含：

- ETF 和美股两类资产域；
- weekly、monthly；
- 足够覆盖 252 日 warm-up 的历史；
- corporate action 调整前后；
- ties；
- 暂时缺失；
- 新上市资产；
-成交量为零或极低；
- crossover 正、负和 neutral 情形。

Golden Context 必须引用冻结 Data Bundle Artifact，不能每次读取 latest。

### 10.2 比较规则

#### Stage 1 数值 Feature

- asset/date coverage 完全一致；
- missingness 完全一致；
- 非离散浮点值：默认 `abs_error <= 1e-12` 或 `relative_error <= 1e-12`；
- 如果兼容 executor 复用完全相同实现，应同时记录 exact-match 比率；
- 不能通过填充、截断或重新对齐掩盖差异。

#### Stage 2 / Stage 3 最终 Signal

- asset/date coverage 完全一致；
- Decimal score 在当前 `1e-18` quantization 下完全一致；
- state/event 完全一致；
- direction、tie、neutral、missing policy 完全一致；
- Stage 3 projection 的 content hash 应与 Stage 2 payload 相同，不复制数据。

#### Aggregation 和 Strategy

- model score 和 missingness 完全一致；
- rank、selected assets、tie allocation 完全一致；
- target weights、risk budget、defense budget 完全一致；
- Portfolio metrics 在同一回测引擎下完全一致。

### 10.3 `v022_parity_evidence` Artifact

每个具体信号生成不可变证据：

- old/new component Artifact IDs；
- Data Bundle 和资产上下文；
- comparison code version；
- coverage counts；
- max/mean absolute and relative error；
- mismatch examples；
- status：passed/failed/waived；
- reviewer decision。

`waived` 只允许明确的研究语义修正，并且这时不能称为 parity migration；必须作为新 Feature Variant/Version 和变更说明发布。

## 11. Shadow、启用与回退

建议三个执行阶段：

```text
shadow：v0.22 双跑但不驱动正式结果
eligible：允许显式创建 v0.22 实验，默认仍是 v0.21
default：新草稿默认 v0.22，历史继续可读
```

开关以数据库 Release Gate/feature policy 为权威，不依赖只存在某台进程上的环境变量。

回退只改变“新提交走哪条路径”，不删除任何已经发布的 v0.22 Catalog、Graph、Run 或 Result Artifact。

## 12. Product/Experiment 展示迁移

统一详情模型至少返回：

- `contract_version`；
- Aggregation Family/Version；
- Target Variant；
- Hyperparameter Preset；
- 直接 Stage 3 输入 Family/Variant；
- Strategy；
- Defense；
- Compiled Graph / full lineage link。

v0.21 结果通过 compatibility view 映射：

- Model preset → Aggregation identity；
- Signal versions → direct inputs；
- target_key → Target Variant 展示；
- strategy preset/parameters → Strategy + Defense。

历史页面不伪造不存在的三层血缘；应标注为 `legacy_v0.21_factor_signal_lineage`。

## 13. 实施完成定义

v0.22 核心迁移完成必须同时满足：

1. 51/51 Concrete Signal 有 Migration Registry 记录；
2. 51/51 有通过的 Parity Evidence；
3. 9 个 Raw、28 个 Stage 1、51 个 Stage 2 可由 v0.22 Runtime 独立物化；
4. Stage 3 只由显式选择决定聚合输入；
5. 四个 deterministic Aggregation Family 完成严格身份拆分并与 v0.21 输出一致；
6. 两个横截面 Strategy 及现有 Defense 设置一致；
7. Draft/Compiled Graph/Run/Experiment 全链路 Artifact 可追溯；
8. 每层输出可导出；
9. v0.21 历史实验和 Product 可读；

## 14. 本轮需要确认的问题

### Q1：v0.21 的首次迁移拓扑

建议使用 `Raw → Stage 1 旧 Factor → Stage 2 旧 Signal → Stage 3 Projection` 做严格 parity；完成后再以新 Catalog Release 原生拆解复杂因子，而不是迁移时强行把旧公式拆满三层。
