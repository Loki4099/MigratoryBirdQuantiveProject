# 候鸟 v0.22 防御择时、资金分层与暂行基线契约（设计讨论稿）

> 文档等级：`historical/non-normative`  
> `superseded_by`：[`候鸟v0.22最终开发计划.md`](候鸟v0.22最终开发计划.md) 第 1.3、9、14 节；RV20 已移至 v0.22.2，并改为 SPY 代理风险预算语义。

> 日期：2026-08-10  
> 状态：核心决定已于 2026-08-10 确认  
> 目标：在不改变横截面排名与选股逻辑的前提下，让每个横截面 Strategy 可选一个可追溯的 Defense Policy，并给出一个可研究、暂不宣称有效的波动率防御 baseline。

## 1. 本轮边界

Defense 不是第四加工层，也不是 Aggregation Node，更不是横截面选股过滤器。它位于横截面策略之后、最终组合 Target 之前：

```text
Final Signal
  → Cross-Section Strategy
  → normalized Risk Sleeve weights（内部合计 1）
  + Defense Timing Policy（只决定 risk / defense budget）
  + Defensive Allocation Policy（只决定 defense sleeve 内部分配）
  → Final Portfolio Target
  → next-common-session open execution
```

这保持了已经确认的核心语义：

- 横截面策略只回答“风险资产内部买谁、各占多少”；
- Defense Timing 只回答“风险资产组合总体投入多少”；
- Defensive Allocation 只回答“剩余资金放到哪里”；
- 三者均通过人工发布的 Catalog 版本组合，不自动搜索策略结构。

## 2. v0.21 现状审计

### 2.1 全局 `internal_timing_v1`

当前实现使用决策日可得的 SPY adjusted close 与最近 200 个 session 的简单均线：

```text
SPY / SMA200 - 1 > +2%  → defense_budget = 0%
位于 [-2%, +2%]         → defense_budget = 20%
SPY / SMA200 - 1 < -2%  → defense_budget = 40%
```

缺少 SPY 或 200 个 session 时硬失败；它不改变 Top-K 排名，也不改变防御篮子内部权重。

这个策略作为 parity baseline 有价值，但其保护有限：最弱状态仍保持 60% 风险预算，只读取慢速趋势，不感知短期波动抬升，且没有独立的恢复/换手控制。

### 2.2 逐资产 MA200 过滤不是 Defense Overlay

v0.21 另有：

```text
rank_select_then_filter
filter_then_rank_select
```

它们使用每个候选资产自己的趋势状态改变可选池或空槽，属于 Cross-Section Strategy Family 的选股语义。即使最终空槽流入 reserve，也不能重命名成全局 Defense Timing。v0.22 必须继续区分：

```text
per-asset trend filter  ≠ market-level defense overlay
```

### 2.3 当前防御篮子

现有两种篮子：

```text
standard_defensive_basket_long_history_v1
  synthetic reserve 40% / IEF 25% / TLT 10% / TIP 15% / IAU 10%

standard_defensive_basket_tradable_v1
  SGOV 40% / IEF 25% / TLT 10% / TIP 15% / IAU 10%
```

权重是 defense sleeve 内部权重。例如 `defense_budget=20%` 时，Tradable Basket 对总组合贡献 SGOV 8%、IEF 5%、TLT 2%、TIP 3%、IAU 2%。

当前 Catalog 将两个篮子都标记为 `formal_eligible=false`，因此 v0.22 不能仅因实现存在就宣称其可用于正式 Product。缺失成分时的 reserve fallback 只能作为单独的 exploratory allocation policy，不能在 formal run 中静默发生。

## 3. 四类不可混淆的对象

### 3.1 Defense Signal

是人工发布的市场状态数据产品，例如：

- SPY / SMA200 deviation；
- SPY 20-session realized volatility；
- 市场换手率或流动性压力；
- 未来研究形成的复合风险状态。

它具有自己的 Raw/Processing 血缘，但不进入 Aggregation 的 Stage 3 输入集合，不改变 Final Signal。用户选择的是 Defense Policy；Policy 的输入信号由 Catalog 固定，用户不能临时替换为任意 Feature。

### 3.2 Defense Timing Policy

将一个或多个冻结 Defense Signal 映射为：

```text
risk_budget ∈ [0, 1]
defense_budget = 1 - risk_budget
```

它不产生资产权重。

### 3.3 Defensive Allocation Policy

把单位 defense sleeve 分配给防守资产和/或 reserve：

```text
sum(defensive_asset_sleeve_weights) + reserve_sleeve_weight = 1
```

它不读取 Final Signal，也不决定 risk budget。

### 3.4 Defense Package

前端为了降低操作难度，建议让用户选择一个已发布 Package：

```text
Defense Package
  = one Timing Policy Version
  + one Defensive Allocation Policy Version
  + compatibility / data / execution requirements
```

内部仍保留两个独立 Artifact，UI 只显示一个选择项并允许展开。这样不会让用户面对 `Timing × Basket` 的无意义大矩阵，也保留未来研究同一 Timing 配不同 Allocation 的能力。

`none` 是显式 Null Package，不引用篮子，不制造虚假的 0% defense allocation run。

## 4. 资金组合公式

横截面策略先生成风险袖套内部权重：

```text
Σ risk_sleeve_weight_i = 1
```

防御分配策略生成防御袖套内部权重：

```text
Σ defense_sleeve_weight_j + reserve_sleeve_weight = 1
```

最终目标：

```text
final_risk_weight_i
  = risk_budget × risk_sleeve_weight_i

final_defense_weight_j
  = defense_budget × defense_sleeve_weight_j

final_reserve_weight
  = defense_budget × reserve_sleeve_weight
    + explicit_unfilled_risk_slot_reserve
```

必须满足：

```text
Σ final_risk + Σ final_defense + final_reserve = 1
```

`defense_budget` 和 `reserve_weight` 不是同义词。防御预算可以被 IEF、IAU 等实际资产占用；reserve 还可能来自 Top-K 空槽。数据库和 API 不应再用单一 `reserve_target_weight` 代替这三个概念。

## 5. 同一资产跨袖套重叠

如果风险 Top-K 恰好选中 IEF，而防御篮子也包含 IEF：

- 决策层保留两个 sleeve contribution，以便解释“为何持有”；
- 执行层按 `asset_id` 合并成一个最终交易目标权重；
- 成本和成交只按净目标变化计算一次；
- Product 详情同时展示 risk attribution 与 defense attribution；
- 不能因为资产重叠就把它从某个 sleeve 静默删除。

## 6. Family 与 Variant 边界

### 6.1 Timing Family

建议建立：

```text
fixed_defense_budget
  formula: defense_budget = constant
  variants/presets: fixed_20 等

market_trend_tiered_budget
  formula: market / moving_average deviation → published discrete budget tiers
  variants: window、band、budget tiers 不同

market_realized_volatility_budget
  formula: target volatility / lagged realized volatility → clipped risk budget
  variants: window、target vol、floor/cap 不同

trend_volatility_composite_budget
  formula: published combination of trend and volatility budgets
  status: planned
```

复合公式不是前两个 Family 的普通参数，应单独成 Family。

`none` 作为 Null Package，而不是 `fixed_defense_budget(defense=0)`，因为它不要求 Defensive Allocation Policy 或防守资产数据。

### 6.2 Allocation Family

```text
reserve_only_allocation
standard_fixed_defensive_basket
```

未来若引入风险平价、动态久期或根据市场状态改变防守资产比例，应建立新的 Allocation Family；不能藏在 Timing Policy 中。

## 7. Defense Decision Contract

每个决策日输出：

```text
decision_date
decision_cutoff
execution_policy_version
risk_budget
defense_budget
regime_key
reason_code
timing_policy_version_id
timing_signal_payload_manifest_ids[]
input_values JSON
previous_decision_ref nullable
quality_status
known_at
```

约束：

- budget 使用固定 decimal scale，并且精确互补；
- `known_at <= decision_cutoff`；
- regime 与 reason 由 Policy Version 枚举声明；
- 只允许读取 Policy Catalog 固定的输入 port；
- 缺失、过期或非有限值按 Policy 的失败规则处理；
- 决策不能读取同期开盘后的价格或未来波动。

## 8. v0.22 候选 Package

### 8.1 `none`

```text
risk_budget    = 1
defense_budget = 0
allocation     = none
```

它是所有研究不可缺少的基准。

### 8.2 `fixed_20_standard_basket_v1`

```text
risk_budget    = 0.8
defense_budget = 0.2
allocation     = current Standard Defensive Basket
```

用于 v0.21 parity 和检验长期持有防御篮子的收益、成本与风险影响；不属于择时有效性的证据。

### 8.3 `ma200_tiered_standard_basket_v1`

保留 v0.21 的 `internal_timing_v1` 原公式和 0/20/40% 档位，仅重构为独立 Timing Policy + Allocation Policy，用作 parity baseline。它不作为 v0.22 推荐防御策略，也不改变参数。

### 8.4 暂行新增：`spy_rv20_target15_reserve_v1`

建议首个新增防御 baseline 使用单一、可解释、无训练的市场波动率规则，并先配 reserve-only allocation，以隔离“择时是否有效”和“防守篮子选得是否有效”两个问题。

#### 输入

```text
market_proxy           = SPY
price_field            = adjusted close
return                 = daily log return
lookback_returns       = 20 complete common sessions
decision_cutoff        = scheduled decision session close
execution              = next common session adjusted open
```

#### 波动率

```text
rv20 = sample_std(last 20 daily log returns) × sqrt(252)
```

只使用决策截止前已经完成的 20 个收益观测，不年内插值、不读取 VIX、不使用未来 realized volatility。

#### 风险预算

```text
target_volatility = 15%
minimum_risk_budget = 25%
maximum_risk_budget = 100%

raw_risk_budget = target_volatility / rv20
risk_budget = clip(raw_risk_budget, 25%, 100%)
defense_budget = 1 - risk_budget
```

首版不加杠杆：低波动时最高风险预算仍为 100%。首版也不加入额外移动平均、档位、回升限速或人为平滑；这些都会形成新的公式判断并妨碍判断基础波动率预算本身的作用。20 日窗口本身已经带来有限平滑，真实换手由成本模型如实记录。

#### 分配

```text
allocation_policy = reserve_only_allocation_v1
```

长历史研究读取现有 PIT reserve accrual；若未来用于实盘 Product，应绑定可交易短久期资产版本及其数据、成本和容量证据，不能把 Synthetic Reserve 当作可交易资产。

#### 状态

```text
rv20 <= 15%              → full_risk
15% < rv20 < 60%         → volatility_scaled
rv20 >= 60%              → minimum_risk
```

60% 是由 `15% / 25%` 数学推导出的 floor 边界，不是额外调参阈值。

### 8.5 为什么首版暂不加入换手率

“市场换手率”至少存在成交量/流通股、成交额/市值、全市场中位数、指数成分加权等不同定义；其高低在投机升温、流动性扩张、抛售压力和流动性枯竭中可能具有不同方向。当前又需要 PIT shares outstanding、成分历史和异常成交处理。

因此建议：

- v0.22 Schema 和 Defense Signal Catalog 为 turnover/liquidity signal 保留位置；
- 本轮不把未经研究的换手率方向硬编码进可用 Package；
- 后续先作为独立 Defense Signal 做状态分布、危机前导性和增量解释研究；
- 只有相对 MA/vol baseline 有稳定样本外增益后，才进入新的 Timing 或 Composite Family。

## 9. 为什么选择趋势和波动率作为 baseline，而非结论

长周期移动平均/趋势规则是可解释的战术配置基线；Faber 的公开研究讨论了简单移动平均式战术配置。时间序列动量研究也记录了多类资产中 1—12 个月收益延续。波动率管理研究则讨论了在波动率较高时减少风险暴露的机制。

参考：

- [Faber, A Quantitative Approach to Tactical Asset Allocation](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=962461)
- [Moskowitz, Ooi and Pedersen, Time Series Momentum](https://w4.stern.nyu.edu/facdir/lpederse/papers/TimeSeriesMomentum.pdf)
- [Moreira and Muir, Volatility Managed Portfolios](https://www.nber.org/papers/w22208)

这些研究不能证明候鸟的具体资产池、成本、长仓限制和防守篮子中一定有效。尤其波动率管理的后续研究对实时样本外效果提出了更谨慎的结果。因此本轮只把 MA 与 realized-vol 作为版本化 baseline，不作为 Product 推荐结论。

## 10. PIT、日历和执行

### 10.1 决策时序

首版与 v0.21 一致：

```text
decision_time = last common scheduled session close
decision_data_policy = may include that completed close
execution = next common session adjusted open
```

Defense Signal 的最后一个观测必须在 decision cutoff 前已知。若供应商数据只能在收盘后延迟发布，则由真实 `available_at` 决定能否进入本次决策，不能仅比较 observation date。

### 10.2 频率

- weekly/monthly Strategy 在自己的计划决策日计算 Defense；
- 同一个 Timing Policy 可声明支持多个频率，但每个 Package/分支冻结 frequency；
- 不能在日频计算预算后只挑选对回测有利的周/月观察；
- 若未来允许 Defense 独立于 Top-K 进行日频紧急去风险，这是新的 Execution/Strategy Family，会产生非计划交易，首版不支持。

### 10.3 Warm-up 与缺失

- MA200 需要 200 个合法 close；
- RV20 需要 21 个价格以形成 20 个 return；
- 中间缺口、非正价格、stale observation 或 calendar mismatch 均硬失败；
- formal run 不使用固定 20%、前值或 reserve-only 静默回退；
- exploratory fallback 若存在，必须是另一个 Package Version，并在结果中清晰标注。

## 11. Defensive Allocation 的数据与执行门禁

一个 Allocation Policy 正式可用前必须冻结：

- 精确资产 ID、份额和舍入规则；
- 长历史与可交易版本的映射；
- 每个成分的 PIT 价格、eligibility、交易日历和 currency；
- 执行价与缺失执行政策；
- 交易成本、冲击和容量；
- reserve accrual model；
- 再平衡规则；
- corporate action 与退市处理。

正式运行中任何需要持有的篮子成分缺失均失败。将全部 defense budget 转入 reserve 会改变策略经济语义，必须作为显式 fallback package，而不是错误恢复。

## 12. 交易成本与换手

- 风险袖套减仓、防御资产买入、防御篮子内部再平衡均计入 turnover；
- 同一资产跨袖套重叠后按净交易计成本，但保留 sleeve attribution；
- Synthetic Reserve 不收虚构交易冲击，但使用冻结 accrual model；
- 可交易短债/债券/黄金按各自成本和容量计算；
- Defense 不能因为目标是降低风险就免除成本门禁；
- 防御策略的价值必须同时报告 gross 与 net，尤其关注频繁 risk-budget 变化。

## 13. Artifact 与血缘

建议新增：

```text
defense.signal_definition / version
defense.signal_payload_manifest
defense.timing_family / version / preset
defense.allocation_family / version
defense.package_version
defense.decision_run
defense.sleeve_target
strategy.final_portfolio_target
```

完整血缘：

```text
Market Raw / Calendar
  → Defense Processing Node(s)
  → Defense Signal Payload
  → Timing Policy Version
  → Defense Decision

Defensive Asset Set + Allocation Policy
  → Defense Sleeve Target

Final Signal → Cross-Section Strategy → Risk Sleeve Target

Risk Sleeve + Defense Decision + Defense Sleeve
  → Final Portfolio Target
  → Execution / Cost / NAV / Metrics
```

Defense 输入虽通过加工节点生成，但不计入 Aggregation Stage 3 输入；它通过独立 policy dependency 出现在完整血缘中。

## 14. 实验分支

用户在每个 Strategy 配置中选择零个或多个 Package 进行比较；编译后每个实验只有一个 Package：

```text
Aggregation Instance
× Strategy Variant
× Defense Package
× Experiment Window
× Cost Scenario
```

`none` 也形成明确基准分支。Package 已封装 Timing + Allocation，因此默认不额外展开 Timing × Allocation 笛卡尔积。

所有 Defense 比较必须匹配同一：

- Final Signal / Aggregation Instance；
- Strategy Variant；
- Asset/Universe/PIT Data Bundle；
- frequency、execution、window、cost；
- benchmark 和初始资本。

否则不能把差异归因于 Defense。

## 15. 评价指标与研究门禁

Defense 的目标不是单独最大化总收益。至少比较：

### 收益与参与度

- CAGR / annualized return；
- bull-period upside capture；
- risk-on 平均预算；
- 因防御放弃的收益。

### 下行风险

- maximum drawdown；
- drawdown duration / time under water；
- downside deviation；
- VaR/CVaR 或 expected shortfall；
- bear-period downside capture；
- 最差月/周。

### 风险调整

- annualized volatility；
- Sharpe、Sortino、Calmar；
- market beta 与 tail beta；
- 与 `none`、`fixed_20`、MA200 parity 的增量。

### 实施代价与稳定性

- risk-budget turnover；
- total portfolio turnover；
- gross/net 差异；
- defense 状态切换次数；
- 不同年份、牛熊段和资产域稳定性；
- 参数邻域敏感性，但不通过邻域回测选最优点。

暂行波动率 Package 只能先标记 `exploratory_available`。升级 Product 需要预先冻结研究窗口、真正 OOS/forward 证据、成本、篮子 formal eligibility 与 Acceptance Policy。

### Workspace

### Experiment / Product

直接显示：

- Package / Timing / Allocation 精确版本；
- 本期 risk budget / defense budget；
- regime、reason 和输入值；
- risk/defense/reserve sleeve attribution；
- 最终合并资产权重；
- 防御带来的收益、回撤、换手和成本差异；
- 完整 Defense lineage 入口。

## 18. 本轮建议冻结的决定

1. Defense 位于横截面策略之后，只缩放 Risk Sleeve，不改变排名或选股。
2. Timing Policy 与 Defensive Allocation Policy 内部分离，前端通过人工发布的 Defense Package 选择。
3. `none` 是 Null Package；不制造虚假 0% allocation run。
4. per-asset MA200 filter 继续属于 Cross-Section Strategy，不属于 Defense Timing。
5. `risk_budget`、`defense_budget`、`reserve_weight` 分列存储并分别追溯。
6. 同一资产跨 risk/defense sleeve 保留归因，执行时净额合并。
7. `internal_timing_v1` 原样保留为 MA200 parity baseline，不作为推荐方案。
8. 新增 `spy_rv20_target15_reserve_v1` 作为首个 exploratory baseline：20 日年化实现波动率、15% target、25%—100% 无杠杆风险预算、reserve-only allocation。
9. 换手率信号本轮只预留契约，不在研究前硬编码方向或阈值。
10. 防御篮子缺失或不具备 formal eligibility 时正式运行失败，不静默转 reserve。
11. Defense 研究必须使用与 `none` 匹配的实验 cell，并同时评价收益参与度、回撤持续时间、尾部风险、换手和净成本。

## 19. 本轮确认结果

### Q1：Timing 与 Allocation 是否内部拆分、前端打包（已确认）

已确认后端把两者建成独立 Artifact，但前端默认选择已发布 Defense Package，既避免组合爆炸，也不牺牲研究扩展性。

### Q2：首个新增 baseline（已确认）

已确认先发布 `spy_rv20_target15_reserve_v1` 为 exploratory，不直接发布 MA+波动率复合规则。单变量 baseline 用于先判断波动率预算本身的效果，复合策略随后建立新 Family。

### Q3：暂行参数（已确认）

已确认采用 RV20、15% target、25% minimum risk、100% maximum risk，且不加杠杆、不加平滑。这些参数是冻结的起始研究点，不代表最优。

### Q4：首个新增 baseline 使用 Reserve-only（已确认）

已确认先用 reserve-only 隔离 Timing 效果，同时把现有 Standard Defensive Basket 留作独立 parity 对照，避免把 Timing 与债券/黄金篮子的效果混在一起。

## 20. 后续轮次

本轮确认后，下一轮建议设计“实验与 Product 详细展示及比较协议”，把已经确认的 Aggregation、直接输入信号、Strategy、Defense、逐 fold 模型状态和 matched baseline 统一呈现在 Experiment/Product 页面，并明确版本升级和 Product 再评估规则。
