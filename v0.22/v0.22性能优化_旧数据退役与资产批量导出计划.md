## 1. 本轮目标与安全边界

本计划解决三个问题：

1. 降低完整 S&P 500 研究运行的内存、耗时与失败恢复风险。
2. 用干净 v5 green 环境替换当前 blue 环境，并最终彻底删除旧 Product、v4 和旧研究运行记录。
3. 在资产页增加“导出已选资产数据”，以可审计、可恢复、适合大数据量的 Parquet 研究包交付。

本文件本身不授权立即执行物理删除。最终目标已调整为：新建完全独立的 v5 green 环境并重跑生成新血缘；验收和切换完成后，整体删除旧数据库、旧 Object Store、旧 Product、v4 及旧研究记录。最终删除仍需用户查看 zero-residual/dry-run 报告后明确批准。

green 重建过程中不得删除或改写 blue 中的 Security、Identifier、历史 S&P 500 成员事件、生命周期/并购/退市证据、v5/Gate4/Cohort10/Runtime10、迁移、契约、计划文档和用户原始资料。它们只有在 green 等价身份、数据 hash 和新血缘全部验收后，才随整个 blue 环境一并删除；Security/Universe/生命周期等必要内容必须已在 green 等价重发。

## 3. 性能问题总结

### 3.1 P0：Processing 内存结构错误

当前约 8.2 GB 峰值并非单纯由 300 万行行情造成，而是同一数据被多次 Python 对象化：

- 数据库查询使用 `.mappings().all()` 一次载入完整历史；
- 每行又展开为 adjusted close、raw close、volume 三套 `RawSnapshotPoint`，约形成 900 万对象；
- 每个 Stage 1 Node 再重建多套完整 panel/dict，即使该节点只使用一个字段；
- Raw、Parquet bytes、asset map、Stage 2/3 中间对象在生命周期上重叠；
- 周频与月频因执行上下文身份包含 frequency，无法复用相同日度 Processing 结果。

### 3.2 P0：伪分区与全量聚合

- 2004–2026 整段历史目前是一个物理 Output Partition；任何变化都会全量读取、计算和写出。
- Aggregation 会读取完整 Parquet、转成 Python list/dict/set，再生成完整 output 和全量 canonical fingerprint。
- 即使周频/月频仅需要决策日，也会先装入全部日频点。

### 3.3 P1：Portfolio、Evidence 重复工作

- 每个 Portfolio Cell 都重复查询并构建相同 Cohort 的多年行情、基准、日历和可选资产面板。
- Common Evaluation Panel 虽已改成批量写入，但复用前仍会重建、排序、哈希并回读全部成员。
- 证据发布耗时和核心计算状态没有清晰分离，前端容易把 finalization 误判为回测卡死。

### 3.4 P1：运行韧性与可观测性不足

- 当前只有粗粒度 heartbeat，缺少 stage、rows、bytes、cache hit、wall time、peak RSS 和 ETA。
- Work lease 固定较长，普通 deterministic executor 没有稳定的周期续租和最终 fence check。
- 当前单 Suite 串行执行虽然慢，却避免多个 8 GB 任务并发；在内存优化完成前不能先提高并发。

## 4. 性能优化实施路线

### S0：基线与非语义 Telemetry

独立提交，仅增加观测，不改变任何计算指纹或数值：

- 对 Raw、每个 Processing Node、Aggregation、Strategy、Portfolio Cell、Evidence finalization 记录 wall time、输入/输出行数、读取/写入 bytes、cache hit/miss 和 peak RSS。
- heartbeat 携带 active suite/work/stage、已处理行数和更新时间。
- 所有长 Work 每 30–60 秒续租，发布前再次验证 lease/fence ownership。
- 记录 cold weekly、warm monthly、repeat run 的基线报告。

验收：Telemetry 失败不得改变研究结果；同一工作超过两个续租周期不得被第二个 worker 重复领取；worker 死亡后租约到期可恢复。

### S1：Processing 列式流式化

这是最高收益阶段：

- 数据库改为 server-side cursor / `yield_per`，每批转换为 Arrow RecordBatch；单批不超过 100,000 行。
- 不再构造三套 `RawSnapshotPoint`；Stage 1 Node 只读取 implementation 声明需要的列。
- asset map 只建立一次；Stage 1 完成后尽快释放 Raw batch、临时 bytes 和映射。
- Parquet 通过增量 writer 写出，不在内存中拼接完整文件。

验收：完整 cold weekly v5 峰值 RSS 不超过 3.0 GB，目标 2.0 GB；相对 8.2 GB 至少下降 60%。所有节点对 golden panel 的逐点输出与旧实现完全一致。

### S2：时间分区与 Rolling Halo

- 发布新的 Processing physical/runtime contract，不重解释旧 Artifact。
- 建议按自然年分区；每个分区读取该节点冻结的最大 lookback halo，但只写本年正式输出。
- manifest 冻结分区日期、行数、对象 hash、依赖 halo 和 Node version。
- Reader 只读取与请求日期相交的分区/row group。

验收：对 lookback-1、lookback、lookback+1 以及跨年边界逐点等价；缺失、损坏、重排分区均 fail closed；修改尾部数据不重算全部历史。

### S3：Aggregation 流式化

- Reader 在 Parquet 层按决策日和必要列过滤，不先转完整 `to_pylist()`。
- 按日期或分区聚合后立即写出；禁止同时保留所有输入 dict、complete set 和全量 output 对象。
- 用有序 partition descriptor/Merkle root 构造稳定指纹，后台 integrity scan 负责冷分区复核。

验收：Aggregation 峰值 RSS 不超过 1 GB；只读取相交分区；周/月输出值、质量、起止日期与原契约一致。

### S4：周/月 Processing 复用

新增 `processing_calculation_context_fingerprint`，只覆盖：

- exact Dataset publication；
- exact Security 集；
- Calendar；
- Raw Feature/Node versions；
- source snapshot proofs；
- 请求区间、暖机区间和参数。

明确排除 frequency、Strategy 和 decision grid。周频/月频 Graph 仍拥有各自的 Cohort、Strategy、Portfolio 和证据身份，但可以绑定同一个完成的 Raw/Stage1–3 Node Run。

验收：cold weekly 完成后，warm monthly 新增 Raw/Stage1–3 Node Run 数为 0，Processing 读取 `daily_bar` 行数为 0；Dataset、成员、Calendar、区间、参数任一变化必须 cache miss。

### S5：Cohort Market Panel 与 Evidence 复用

- 按 exact Cohort runtime contract 发布一次不可变 Market Panel；多个 Cell 只投影所需持仓资产和日期。
- Common Evaluation Panel 在 Cohort 发布时一次物化；Suite finalizer 只做 O(1) identity lookup/binding。
- 将 `calculated`、`finalizing_evidence`、`published` 分成明确状态。

验收：同 Cohort 的 N 个 Cell 只装载/物化一次基础 Market Panel；第二个 Result/Suite 不重新 INSERT 或全表扫描 Common Panel，目标耗时低于 1 秒。

### S6：受控并发与显式重试

仅在 S1–S5 达标后实施：

- 本机默认资源令牌：Processing=1、trainable=1、轻量 Aggregation/Portfolio=1–2。
- 调度全局 Graph Work，而不是盲目并行整个 Suite。
- failed/cancelled Work 只有显式 retry/new submission 才能重排；保留旧 attempt failure details。

最终真实性能验收只执行一次 cold weekly + warm monthly + repeat both，并要求仍为 5/5 completed、accepted/passed，评价区间保持 2007-01-03 至 2026-06-30。取得 S0 基线后，cold E2E wall time目标至少下降 50%，warm Processing 目标下降 90%。

## 5. 旧 Product、v4 与旧研究环境的彻底删除方案

### 5.1 用户目标与修订决定

最终 active 环境中不保留两个旧 Product、v4、旧 Draft/Round/Suite/Result/Evidence、旧运行缓存或其数据库墓碑；所需研究血缘由干净的 v5 环境重新发布和重跑产生。

不在当前 blue 数据库内逐表强删。实现方式冻结为 **blue-green clean rebuild**：

- blue：当前数据库、当前 Object Store 和全部旧身份，仅作为构建期间的只读来源与短期回滚环境；
- green：空数据库、独立 volume、独立 Object Store，只导入经哈希验证的 v5/v6 合法数据和必要主数据，不导入任何旧 Product/实验/缓存；
- green 全部验收后切换服务，最后整体删除 blue 数据库、volume、Object Store 和备份。

该方案最终同样实现旧 Product/v4 零残留，但不需要绕过 2,548 个下游 Artifact、append-only trigger、FK RESTRICT 和跨数据库/对象存储的非原子删除。

### 5.2 当前 v5 仍需重发的原因

当前依赖并非完全 v5-native：

- risk Dataset v5 本身来自 v3 修复链，不依赖 v4；
- Gate4 直接携带 Gate3，因而形成 `Gate4 -> Gate3 -> risk v4`；
- Runtime10 weekly/monthly 不可变地绑定 Gate4；
- Registry 0.22.3 直接绑定 Gate4；
- 当前两组 v10 实验通过 Runtime10 仍递归连回 v4。

因此不能只重跑旧 Runtime10。green 必须发布新的独立身份：

1. **v5 baseline import v1**：把已验收的 v5/v6 数据值作为带 hash 的新 genesis source 发布，不复制旧 Artifact ID/旧 lineage。
2. **Gate5**：直接引用 v5 transfer manifest、修复决议、质量/排除、生命周期、closure review，不得引用 Gate3、Gate4 或 v4。
3. **Cohort11 weekly/monthly**：冻结相同 2007-01-03 至 2026-06-30 评价环境。
4. **Runtime11 weekly/monthly**：分别绑定 Cohort11 与 Gate5。
5. **Registry 0.22.4**：绑定 v5 baseline、benchmark v6、Gate5 和 Runtime11。
6. **全新 Research Round/Suite/Result/Evidence/Ranking**：在 Runtime11 上各跑一次周频、月频 smoke；Product 表保持空。

具体版本号若被并行 migration 占用可顺延，但语义必须是全新的 immutable identity，不能覆盖 Gate4/Cohort10/Runtime10/Registry0.22.3。

## 6. 资产层批量数据导出设计

### 6.1 产品行为

资产页增加“导出已保存选择”按钮。导出只能基于服务器已保存的 exact Draft revision/selection snapshot，未保存的临时勾选先提示保存。

导出流程：

1. Preview：返回资产数、日期范围、预计行数/字节、exact Dataset/Gate/Registry、排除/警告和格式建议。
2. Confirm：创建异步、幂等 export job。
3. Status：显示 queued/running/completed/failed/cancelled、已处理行数/bytes、阶段和过期时间。
4. Download：完成后下载一个研究包；支持取消未完成任务。

不能使用“数据库中最新 Dataset”猜测。请求必须冻结 Registry 0.22.3、risk v5 或 benchmark v6、Gate4、selection snapshot、排序后的 Security IDs、日期范围、字段集合和 price semantics。任务开始后即使活跃 Dataset 更新，也继续导出原 exact version。

### 6.2 文件格式

默认采用 long-format Parquet + ZSTD，不采用宽矩阵，也不为 621 个资产各生成一个 CSV。建议研究包结构：

```text
manifest.json
data_dictionary.json
securities.parquet
prices/year=YYYY/part-0000.parquet
corporate_actions.parquet
membership_intervals.parquet
eligibility_intervals.parquet
lifecycle_events.parquet
quality_and_exclusions.json
checksums.json
```

`prices` 至少包含：

- `security_id`、`asset_id`、`security_key`、`symbol`；
- `session_date`；
- raw OHLC、adjusted OHLC/adjusted close、adjustment factor；
- `volume_raw`；
- exact dataset/version 和必要 known-at/price-semantics 标记。

数值保持 Decimal 语义，不经 pandas/float 隐式转换。按 year 分区、文件内按 `security_id, session_date` 排序，row group/batch 不超过 100,000 行。Parquet 已压缩，若外层使用 ZIP，应使用 store 模式避免重复压缩。

### 6.3 CSV 边界

CSV 仅作为小型便利导出：首版建议限制为不超过 10 个资产且 Preview 估算不超过 100 MB。全选 S&P 500 必须使用 Parquet 研究包。当前 v5 全池约 303 万行，CSV 未压缩体积粗估约 0.5–0.65 GB，浏览器同步生成和下载均不安全。

### 6.4 后端实现

建议 API：

- `POST /api/v2/v022/asset-data-exports/preview`
- `POST /api/v2/v022/asset-data-exports`
- `GET /api/v2/v022/asset-data-exports/{job_id}`
- `POST /api/v2/v022/asset-data-exports/{job_id}/cancel`
- `GET /api/v2/v022/asset-data-exports/{job_id}/download`

可复用现有 Signal export 的 job/idempotency/status/download 约定，但不能复用其 pandas、全量 DataFrame、内存中构造完整 ZIP 的实现。

实现必须：

- server-side cursor -> Arrow RecordBatch -> ParquetWriter；
- 写入临时目录并逐分区 hash，全部成功后原子发布 content-addressed package；
- 后端临时包写入独立 application-local cache/Docker volume；浏览器完成下载后，最终用户文件默认落入 `%USERPROFILE%\Downloads\MigratoryBirdExports`；
- Windows Downloads Known Folder 通常不在 OneDrive 下，但部署时必须按当前用户配置核对；它也可能受 Windows“存储感知”清理，因此不能作为系统唯一权威副本；
- 默认临时下载保留 7 天，job 元数据和 manifest/tombstone 长期保留；
- concurrency=1、磁盘剩余空间和配额 preflight；
- 同一 exact 请求复用已完成包；过期/损坏包重新生成；
- excluded、非 active identity、Dataset mismatch、缺失必要 bar 一律 fail closed，不静默补值。

### 6.5 导出验收

- exact active identity，不得因 version/member_count/created_at 自动漂移。
- 2 资产小包内容、manifest、hash 和 Decimal 精度正确。
- 621 资产合成/真实 dry-run 内存有界，batch 上限生效。
- 年度分区边界、公司行动、生命周期、成员/eligibility 区间完整。
- 取消、重试、幂等、过期、损坏、磁盘不足均有稳定状态和错误码。
- 浏览器完成“保存选择 -> Preview -> 创建任务 -> 进度 -> 下载 -> 本地读取 Parquet”烟测。

## 7. Medium 分阶段交付顺序

每阶段一个 concern、独立提交、先聚焦测试后下一阶段：

1. **B0 冻结旧 Product 活动**：停止旧 Product worker/调度，确保构建期间不再产生新 Product 状态；blue 数据暂不删除。
2. **P0 Telemetry/lease**：落地 S0 并取得真实性能基线。
3. **P1 Processing streaming**：落地 S1，达到 <=3 GB 门槛。
4. **P2 Partition/Aggregation**：落地 S2/S3，验证边界数值与 <=1 GB Aggregation。
5. **P3 Reuse/Panel**：落地 S4/S5；cold weekly 后 monthly 不重新 Processing。
6. **G0 v5 transfer package**：从 blue 导出、校验并冻结 v5/v6 合法数据和必要主数据；不携带旧研究/Product。
7. **G1 Green bootstrap**：空数据库、独立 volume/Object Store、migration/Catalog/security bootstrap。
8. **G2 v5-native 发布**：发布 baseline import、Gate5、Cohort/Runtime11、Registry0.22.4 和空白 Research Round。
9. **E1 资产导出契约与异步 Job**：针对 green exact identity 实现 Preview、job、Parquet writer、状态机和下载。
10. **E2 资产导出 UI**：资产页保存选择、估算、进度、取消、下载和错误恢复；最终文件落到 Downloads。
11. **G3 Green 验收**：cold weekly、warm monthly、repeat both；核对数据闭包、零旧身份、排行榜、结果详情、未来 Product警告模板和导出包。
12. **G4 切换**：切换服务到 green，完成最小读写和浏览器 smoke；blue 停止、只读进入短回滚窗口。
13. **D1 最终删除**：用户批准 zero-residual 报告后，整体删除 blue DB/volume、Object Store 和备份，并复核磁盘空间。

并发开发限制：P0–P3 必须顺序完成；G0 可在后半段准备，但 transfer package 只有在数据冻结且写入停止后才能最终签名；E1/E2 只对 green identity 验收，不能依赖旧 `latest` 查询；共享 migration head、Artifact/Gate/Cohort 发布器每次只能由一个阶段修改。D1 不得与任何功能开发并行。

## 8. 停止条件与需要再次确认的动作

出现以下任一情况立即停止并报告，不自行扩大修改：

- v5/v6 transfer package 行数、分区 hash 或身份清单与 blue 对照不一致；
- green 的任一 Artifact 递归依赖 Gate3、Gate4、v4、旧 Product 或旧实验 UUID；
- Gate5 不能在不引用 prior Gate 的情况下重建 353 个排除项和证据；
- green Product 业务表非空，或默认创建了旧四 ETF/旧草稿；
- 分区版与旧版出现任何非预期数值差异；
- warm monthly 仍重算 Processing，说明 identity 未正确拆分；
- 导出需静默填补/删除缺失行情才能完成；
- Windows Known Folder 配置变化，最终 Downloads 实际位于 OneDrive 内；
- 本机没有足够空间同时容纳 blue、green、transfer package 和回滚备份；
- forbidden-ID 报告无法证明旧 Product/v4 在 green 中为 0；
- blue 最终删除范围不能精确解析为独立 DB/volume/Object Store root。

D1 是不可逆边界。Medium 完成 G3、G4 和 zero-residual/空间清单后必须停止，等待用户批准。批准后删除的是完整、已停止的 blue 环境，不在 blue 内关闭 trigger 或执行复杂级联 DELETE。
