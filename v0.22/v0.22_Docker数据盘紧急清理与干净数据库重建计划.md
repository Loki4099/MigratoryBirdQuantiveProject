# 候鸟 v0.22 Docker 数据盘紧急清理与干净数据库重建计划

> **已被 v2 执行计划取代。** R0-R2 完成后的在线审计证明：Windows VHDX 约 454.95 GiB，而内部 EXT4 实际仅使用约 49.2 GiB。当前首选路线已调整为“保护其他项目 -> 精确清理 -> TRIM -> 冷 compact”；全局 clean VHDX 只作为 compact 失败后的后备。权威后续计划见 `v0.22_Docker数据盘压缩与后续清理计划_v2.md`。

状态：**待用户批准；本轮只读审计已完成，尚未执行任何清理**  
日期：2026-08-20  
适用工作区：`SignalAnalysis(American)`  
与既有计划的关系：本计划是磁盘故障下的紧急执行修订；它不改变 v5 免费研究基线、性能优化和资产导出的产品设计，但在存储恢复完成前暂停长回测与性能开发。

## 1. 审计结论

### 1.1 宿主磁盘

- Docker 数据盘：`%LOCALAPPDATA%\Docker\wsl\disk\docker_data.vhdx`
- 当前实际文件大小：`488,493,809,664 B`，约 **454.95 GiB**。
- 文件当前没有 Windows sparse 属性，约占 C 盘总容量的 47.8%。
- C 盘总容量约 952.74 GiB；审计时空闲约 **221.33 GiB**。
- Docker 日志本身约 0.03 GiB，不是主要占用来源。
- 候鸟宿主 Object Store `artifacts/v022_payloads` 约 0.82 GiB；整个 `artifacts` 约 4.76 GiB，也不是 455 GiB 的主要来源。

因此，不能把问题简化为删除几个结果文件。真正的大头是 Docker 全局 VHDX 内的 PostgreSQL Volume、其他 Volume、镜像层、缓存及已释放但尚未返还给 Windows 的 EXT4 空间。

### 1.2 文件系统故障证据

Docker VM 日志在 2026-08-20 17:01（09:01 UTC）记录了：

- `I/O error, dev sdd` 的读写错误；
- `EXT4 ... Detected aborted journal`；
- `Remounting filesystem read-only`；
- PostgreSQL 与 dockerd 收到 fatal signal；
- Docker Desktop 报告磁盘空间不足并停止。

审计时 `docker-desktop` 为 Stopped，Docker CLI 和 PostgreSQL 端口虽然由代理占用，但引擎/API/数据库查询均不响应。因此目前没有取得可信的在线 `docker system df -v` 或表级实时统计。

这是一条硬安全边界：**在 Docker 引擎恢复、PostgreSQL 完成 crash recovery 且逻辑备份通过之前，不得执行 prune、Volume 删除、库内批量 DELETE、VACUUM FULL、VHDX compact 或 factory reset。**

### 1.3 已知候鸟 Docker 资源

当前 `compose.yaml` 只声明：

- 生产 PostgreSQL Volume：`signalanalysisamerican_style_rotation_postgres`；
- 测试 PostgreSQL Volume：`signalanalysisamerican_style_rotation_postgres_test`；
- 镜像：`postgres:16-alpine`。

测试 Volume 可完全重建，是候鸟范围内的第一优先清理候选。生产 Volume 仍保存 v5/v6 权威数据，不得先删。

Docker 数据盘是全局共享资源。另一任务可能还有容器、Volume、镜像或缓存；在引擎恢复并取得完整清单前，禁止使用：

- `docker system prune -a --volumes`；
- 无项目标签过滤的 image/build-cache prune；
- Docker Desktop 的 Clean/Purge data 或 factory reset。

### 1.4 候鸟数据依赖

必须迁入干净环境的内容：

- risk v5：3,034,078 条日线、621 个有行情股票身份、34,931 条公司行动；
- benchmark v6：27,035 条日线、5 个 ETF/基准、434 条公司行动；
- Security/Identifier、S&P 500 历史成员、Universe、XNYS Calendar；
- 生命周期、停牌、退市、并购、换股、现金结算及其证据；
- v5 修复、排除、质量、closure review 和价格语义；
- Catalog、migration、契约与 Product 免费数据风险警告模板。

不迁入干净环境的内容：

- 两个旧 Product；
- v4 与更早的旧研究行情；
- 旧 Draft、Round、Suite、Run、Work、Result、Evidence、Ranking；
- 旧缓存、失败实验、测试库数据及旧 Object Store 运行对象。

当前 `Gate4 -> Gate3 -> risk v4`，Runtime10 与 Registry 0.22.3 也递归连回 v4。因此不能在原生产库中先删除 v4；正确做法仍是导出 v5/v6 的数据值和必要治理证据，在新库中发布全新 v5-native 血缘。

## 2. 推荐路线

本轮推荐采用：

> **恢复只读访问 -> 双重逻辑备份 -> 全局 Docker allowlist -> 隔离旧 VHDX -> 新建小型 Docker 数据盘 -> 仅恢复 v5/v6 clean green -> 验收 -> 用户批准后删除旧 VHDX。**

不推荐在疑似损坏且高度互联的 blue 库内逐表强删。这样既难证明没有误伤，也无法保证 Windows 立刻收回空间。

由于旧 VHDX 已占 454.95 GiB、C 盘只余 221.33 GiB，不能在 C 盘再复制一份完整 VHDX。若需要保留整盘回滚，应在完全停止 Docker/WSL 后，把旧 VHDX在同一 NTFS 卷上移动并改名到 Docker 管理目录之外；该动作本身不释放空间，只保留短期回滚能力。若存在可用外置磁盘，优先把整盘备份移到外置磁盘。

## 3. Medium 分阶段执行计划

### R0：停止写入与恢复门禁

目标：只让 Docker/PostgreSQL恢复，不让候鸟继续产生新数据。

1. 停止候鸟 API、Suite Worker、Product Worker 和 GC Worker；核对 PID/启动时间后再停止，不能误杀其他任务。
2. 启动 Docker Desktop，但不启动候鸟应用服务和长实验。
3. 确认 Docker engine、`docker-desktop` 和 PostgreSQL 正常响应。
4. 检查 Docker/VM/PostgreSQL 日志，确认没有新增 I/O、journal、read-only、page/WAL/Relation 错误。
5. PostgreSQL 只读检查：Alembic head、数据库可连接、关键 v5/v6 行数与身份可读取。

立即停止并向用户报告的条件：

- Docker 数据盘再次只读或出现 I/O/journal 错误；
- PostgreSQL 无法完成 crash recovery；
- page/header/checksum/WAL/relation 损坏；
- `pg_dump` 失败或关键 v5/v6 数据不可读。

禁止用 `pg_resetwal`、手删 `pg_wal`、强制 fsck 修复或 factory reset 掩盖损坏。

### R1：全局 Docker 和数据库精确清单

目标：先证明空间在哪里，并保护其他任务。

输出一份 JSON + Markdown dry-run 清单，至少包含：

- `docker system df -v`；
- 全部 Compose project、容器、Volume、镜像、build cache、网络及标签；
- 每项所属项目、是否运行、是否有 Volume、是否可重建、预计字节数；
- PostgreSQL 主库/测试库、schema/table/index/TOAST/WAL/live-dead tuple 大小；
- `daily_bar`、公司行动、Product、Round/Suite/Result/Evidence/Work 的版本化计数；
- Payload manifest/Object Store 强根、非强根、孤儿对象的数量和字节数。

规则：

- 只删除清单中带精确项目/Volume/ID 的 allowlist；
- 其他任务或未知资源默认保留并单独请用户确认；
- 不按 mtime、名字含 `old`、失败状态或文件大小直接判断垃圾。

### R2：候鸟恢复包与可恢复性证明

恢复包放到 Docker 外、OneDrive 外，例如：

`%LOCALAPPDATA%\MigratoryBird\recovery\2026-08-20\`

至少生成：

1. PostgreSQL globals；
2. 当前主库 custom-format dump；
3. `pg_restore --list` 清单；
4. v5/v6 transfer package：按 `dataset/security/year` 分区的 Parquet、schema、row count、日期边界、SHA-256 和总 manifest hash；
5. Security/Universe/Calendar/生命周期/结算/排除/警告等必要元数据包；
6. 当前 Git HEAD、Alembic head、配置和 Docker inventory；
7. 当前宿主 Object Store 强根 inventory。

现有 2026-08-18 M119 dump 早于本轮最终 v5 数据治理，只能作为辅助，不能替代新备份。

至少完成两种独立验证：

- dump 可被 `pg_restore --list` 完整解析；
- transfer package 的逐分区 hash、行数、资产数和日期边界与数据库一致。

如果 Docker/数据库保持健康且空间允许，再在独立临时库做一次 restore smoke。备份或校验失败时不得进入破坏性阶段。

### C1：第一批低风险、精确清理

这一阶段只为降低继续运行风险，不承担最终 C 盘回收目标。

按清单逐项处理：

1. 删除并重建 `signalanalysisamerican_style_rotation_postgres_test`；
2. 删除只属于候鸟且已停止的测试容器；
3. 删除明确无容器引用、带候鸟测试标签的临时/匿名 Volume；
4. 删除明确属于候鸟、可重新拉取且无容器引用的镜像层；
5. 删除明确属于候鸟的 build cache；
6. 对关闭 Research Round 仅运行现有 strong-root-aware GC 的 dry-run，报告后再执行。

禁止：全局 prune、主生产 Volume 删除、v4 原地级联删除、VACUUM FULL、手删数据库目录。

说明：这些动作主要释放 VHDX 内部空间；Windows 上的 454.95 GiB 文件通常不会因此自动缩小。

### G0：隔离旧 Docker 数据盘

前置条件：R2 全部通过、其他 Docker 项目已分类并得到保留/删除决定、用户单独批准。

1. 干净停止所有 Docker 容器；
2. 完全退出 Docker Desktop；
3. 执行 `wsl --shutdown`；
4. 证明 VHDX 已分离；
5. 把旧 `docker_data.vhdx` 移动/改名到 Docker 管理目录之外的 blue quarantine 路径；
6. 不删除旧 VHDX；记录原路径、大小和时间；
7. 通过 Docker Desktop 官方 reset/reinstall/bootstrap 流程创建新的空数据盘。

如果还有其他任务需要持久 Docker Volume，必须先分别导出并在新数据盘恢复；未经确认不能重置全局 Docker。

Docker 官方明确要求在 Docker Desktop 完全停止后才能备份 VM disk，并提醒 reset/uninstall 会销毁本地容器、镜像和 Volume：

- <https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/>
- <https://docs.docker.com/desktop/uninstall/>

### G1：clean green 数据库与 Object Store

1. 创建全新的生产 PostgreSQL Volume；
2. 测试 PostgreSQL 改为 opt-in profile，并在测试结束后精确销毁，不再长期常驻；
3. 新 Object Store 放在非 OneDrive 路径，例如 `%LOCALAPPDATA%\MigratoryBird\object-store-v5`；
4. 从空库执行 migration 和静态 Catalog bootstrap；
5. 不导入旧 Product、Draft、Round、Suite、Result、Evidence、Ranking 或 cache；
6. 从 transfer package 发布 v5 baseline 与 benchmark v6；
7. 发布 v5-native Gate5、Cohort11 weekly/monthly、Runtime11 weekly/monthly、Registry 0.22.4；
8. 创建空白 Research Round，不恢复默认 4 ETF；
9. 各运行一个最小周频、月频 deterministic smoke，生成全新 Result/Evidence/Ranking；Product 表保持空。

### G2：green 验收门禁

必须全部满足：

- Product 业务表为 0；
- v4 UUID、两个旧 Product、旧 Round/Suite/Result UUID 查询为 0；
- Artifact dependency closure 不包含 Gate3、Gate4、v4 或旧实验 Artifact；
- v5/v6 行数、资产数、公司行动数、分区 hash 与 transfer package 完全一致；
- Gate 排除项与可选资产交集为 0；
- 周/月 strict closure blocker 为 0；
- 两次 smoke 均 completed、accepted/passed，评价区间为 2007-01-03 至 2026-06-30；
- Product 免费数据/回溯复权/幸存者偏差警告模板仍完整；
- Object Store integrity scan 通过；
- 候鸟资产选择、排行榜、结果详情和导出最小烟测通过；
- 其他被保留的 Docker 项目均已恢复或确认不需要。

### D1：最终释放 C 盘

这是唯一删除旧生产数据的阶段，必须再次由用户明确批准。

批准前展示：

- old VHDX 精确路径与大小；
- blue/green forbidden-ID 对照；
- v5/v6 hash、closure 和 smoke 结果；
- 其他 Docker 项目恢复状态；
- recovery package 路径与 hash；
- 预计净释放空间。

批准后：

1. 删除 quarantined blue VHDX；
2. 删除旧 blue Object Store 和已被新恢复包取代的旧备份；
3. 再次统计 Docker 与 C 盘；
4. 对新的动态 VHDX 仅在完全分离/只读挂载时使用官方支持的 compact 流程；
5. 输出最终 zero-residual 与空间回收报告。

Windows 官方说明动态 VHDX 删除内部文件后不会自动收缩；`Optimize-VHD` 或 `compact vdisk` 要求 VHDX 未挂载或只读挂载：

- <https://learn.microsoft.com/en-us/powershell/module/hyper-v/optimize-vhd>
- <https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/compact-vdisk>

旧 VHDX 若被整体删除，则无需对旧盘 compact；Windows 会直接释放其实际文件占用。新盘保持小型、可重建即可。

## 4. 长期防复发修改

Medium 在 clean green 后单独提交以下维护改造：

1. `postgres-test` 改为显式 test profile，测试结束后按精确项目名销毁；
2. PostgreSQL 容器日志设置 `max-size`/`max-file`；
3. 每次完整实验前检查 C 盘空闲与 Docker 内部占用；
4. C 盘少于 100 GiB、Docker 数据盘超过 80% 或 Docker 日志出现 I/O/read-only 时拒绝启动完整研究；
5. 每周生成只读 Docker/数据库 top-N storage report；
6. 所有清理脚本默认 dry-run，禁止自动删除 Volume；
7. failed/cancelled Suite 不再因 runtime version 自动重排；
8. Object Store、导出和恢复包不放入 OneDrive；
9. 资产导出仍写入 `%USERPROFILE%\Downloads\MigratoryBirdExports`，并提示 Downloads 可能受 Storage Sense 清理；
10. 若未来增加其他物理磁盘，优先使用 Docker Desktop 的 Disk image location 设置迁移数据盘，而不是继续扩张 C 盘。

## 5. 预计空间结果

- 立即可证明的大头是旧 VHDX 的 454.95 GiB，而非候鸟宿主 Object Store。
- C1 的测试资源/cache 清理能释放多少，必须等待在线 inventory，不能提前承诺。
- G2 通过后删除旧 VHDX，理论上会释放接近该文件的实际占用；净释放量要扣除新 green VHDX、recovery package 和新 Object Store。
- 如果 clean green 数据盘控制在几十 GiB 以内，净回收应是数百 GiB量级；最终以 Windows 文件大小与 C 盘 FreeSpace 为准。

## 6. 用户批准点

Medium 不得把一次批准扩展到后续破坏性阶段。需要三个独立批准点：

1. **C1**：删除测试 Volume 和精确候鸟测试/cache资源；
2. **G0**：隔离旧全局 Docker 数据盘并初始化空盘；
3. **D1**：green 验收后永久删除 quarantined blue VHDX、旧 Object Store 和旧备份。

本轮只读审计不构成以上任何批准。
