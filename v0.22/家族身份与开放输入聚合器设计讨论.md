# 家族身份与开放输入聚合器设计讨论

> 文档等级：`historical/non-normative`  
> `superseded_by`：[`候鸟v0.22最终开发计划.md`](候鸟v0.22最终开发计划.md) 第 2.3、5、8 节；Family 命名、开放输入门禁和 LightGBM 状态以 RC1 为准。

> 状态：待确认稿  
> 建立日期：2026-08-10  
> 主题：Family 的严格边界，以及 LightGBM 一类能够接收开放数值输入集合的聚合器。

## 1. Family 不能由计算打包或下游用途决定

一次 Node Run 同时输出多个结果，只说明这些结果共享计算，不说明它们属于同一研究家族。

因此：

```text
body   ≠ range   ≠ upper_shadow   ≠ lower_shadow
```

它们使用不同公式、表达不同数值含义，应属于不同 Feature Family。即使为了性能在一次 Candlestick Geometry Node Run 中共同计算，也不能合并家族。

同样，多个信号最终进入同一个 Aggregation Node，不会因此成为同一家族。下游聚合关系与上游研究分类是两件事。

## 2. 推荐的严格 Family 判定

只有同时满足以下条件，才归入同一 Family：

1. 使用同一个规范化计算公式、规则或训练算法；
2. 输入端口角色及输入语义相同；
3. 输出语义、单位、Shape 和方向含义相同；
4. 经济解释或研究假设相同；
5. 差异仅来自该 Family 明确允许的参数轴；
6. Known At、缺失语义和频率契约没有本质变化。

可以简写为：

```text
Family Identity
= canonical operator/formula
+ input roles
+ output semantics
+ economic direction/hypothesis
+ temporal semantics

Variant Identity
= Family Identity
+ exact parameter preset
```

### 2.1 同一家族示例

```text
total_return
├─ window=5
├─ window=20
├─ window=60
├─ window=120
└─ window=252
```

```text
moving_average_ratio
├─ short=1, long=50
├─ short=1, long=200
└─ short=50, long=200
```

```text
price_cross_above_ma
├─ MA=1/50
└─ MA=1/200
```

### 2.2 不同家族示例

```text
body vs range vs shadow
price_cross_above_ma vs price_cross_below_ma
return_continuation vs short_return_reversal
low_illiquidity_quality vs illiquidity_premium
```

后两组即使共享上游值或部分计算公式，也因为规则、方向或经济假设不同而属于不同 Signal Family。

## 3. 计算身份与研究身份分离

推荐正式拆成：

```text
ProcessingNodeVersion
  负责：实现、输入、执行、缓存、多输出打包

FeatureDefinition / SignalDefinition
  负责：公式、输出语义、方向、研究解释

FeatureFamily
  负责：把同公式同语义、不同参数的 Variant 归组

FeatureVariant
  负责：精确参数，并引用 producer_node_version + output_port
```

示例：

```text
Node Run: candlestick_geometry_v1
├─ Output Port body
│  └─ Feature Family: candlestick_body
├─ Output Port range
│  └─ Feature Family: candlestick_range
├─ Output Port upper_shadow
│  └─ Feature Family: candlestick_upper_shadow
└─ Output Port lower_shadow
   └─ Feature Family: candlestick_lower_shadow
```

如果某个输出只是解释或诊断字段，例如事件信号同时保存的 `state` 和 `event`，可以作为主 Signal Variant 的 Companion Port，不必都成为可独立选择的 Feature Family。只有能独立进入后续加工的端口才需要独立 Feature Definition/Family。

## 4. Family、Variant、Version 与 Instance

推荐冻结以下层级：

```text
Family
  稳定公式/算法、输入输出语义和研究假设
    ↓
Variant
  已发布参数 Preset
    ↓
Version
  精确实现、Schema、Engine 和代码版本
    ↓
Instance
  在具体输入集合、Asset Context、Target 和训练上下文中的绑定
    ↓
Run / Fitted Artifact
  一次不可变执行或训练结果
```

因此：

- 参数变化通常产生新 Variant；
- 不改变公式语义的实现升级产生新 Version；
- 输入信号集合变化产生新 Aggregation Instance；
- 训练窗口或 Data Bundle 变化产生新的 Fitted Artifact；
- 公式、规则方向或经济假设变化通常产生新 Family。

### 4.1 Target Horizon 与超参数不拆分 Family

对于训练型聚合器，只要算法、Objective、输入输出语义和 Target Kind 相同，以下变化仍属于同一 Aggregation Family：

- `future_cross_sectional_rank` 的 H5、H21、H63 等预测窗口；
- `num_leaves`、`max_depth`、`learning_rate`；
- 正则化、列采样、行采样；
- 迭代轮数和早停 Preset；
- 其他已发布、不会改变模型任务含义的超参数。

推荐把 Target 与模型超参数保留为两个独立选择轴：

```text
Aggregation Family
  lightgbm_cross_section_rank_regression

Target Family
  future_cross_sectional_rank
  ├─ weekly_next_scheduled_execution_open
  └─ monthly_next_scheduled_execution_open

Hyperparameter Preset
  ├─ conservative_v1 (available)
  ├─ regularized_v1 (planned)
  └─ deeper_tree_v1 (planned)

Aggregation Instance
  = Family
  + exact input signal set
  + one Target Variant
  + one Hyperparameter Preset
  + Frequency / Asset Context
```

这样可以沿用 v0.21 将 Model Preset 与 Model Target 分开的优点，避免为了 H5/H21/H63 与每组超参数的组合重复定义 Family。

如果 Objective 或 Target Kind 改变，例如从未来截面收益回归变为 LambdaRank、熊市概率分类或波动率预测，则应建立不同 Aggregation Family。

## 5. “接受一切输入”的准确含义

系统可以提供开放输入聚合器，但“接受一切”必须限定为：

> 接受任意数量、任意已批准 Family 的聚合前数值信号，只要它们可以在同一个 `(decision_date, asset_id)` 样本键上被确定性地组装成固定 Schema 的数值特征矩阵。

它不表示直接接受：

- 原始新闻文本；
- 图片；
- 长度不固定且没有 Schema 的向量；
- 未对齐的事件流；
- 不同 Asset Context；
- 决策时点尚不可得的数据。

这些数据必须先在三个加工层中变成标量或具有冻结 Shape 的向量，并满足 Pre-Aggregation Signal Contract。

修订：所有 Raw/Feature Output 都可以抵达聚合候选区，但不要求全部预先成为有方向的 Signal。首版开放数值模型可以接受普通数值标量；文本、图片、未对齐事件或变长对象若没有兼容模型则保持可见但不可选。严格要求应表述为满足该 Aggregation Family 自己的 Input Policy，而不是统一满足同一份 Signal Contract。

## 6. Open Numeric Feature Set 契约

```python
class OpenNumericInputPolicy(StrictModel):
    minimum_signal_count: int
    maximum_signal_count: int | None
    accepted_kinds: frozenset[Literal["scalar", "fixed_vector", "event_score"]]
    require_common_sample_key: Literal["decision_date_asset_id"]
    feature_assembly_policy_key: str
    missing_policy_key: str
    allow_mixed_families: Literal[True] = True
```

每个 Aggregation Instance 冻结：

```text
selected signal artifact IDs
family and variant keys
vector dimension names
flattened feature column names and order
dtype and categorical flags
missing policy
training target
training and validation dates
walk-forward/retraining policy
model parameters and random seed
fitted model artifact
```

输入数量可以因实例不同而变化，但某个已训练实例在训练、验证和推理期间的 Feature Schema 必须固定。

## 7. LightGBM 在候鸟中的位置

### 7.1 v0.21 已有 Planned Family

v0.21 已定义：

```text
family = lightgbm_ranker
preset = lightgbm_ranker__conservative_v1
status = planned
target = next_period_cross_sectional_return
accepted output types = continuous / directional / event
input count = 2..32
frequencies = weekly / monthly
```

它尚未可用的既有原因是：PIT 股票数据、训练/测试规则和 Engine Artifact 未发布。v0.22 应继承这项设计，而不是创建无血缘的新模型入口。

### 7.2 为什么它适合作为开放数值聚合器候选

LightGBM 的正式 Dataset 接口接收二维特征矩阵或表格，支持数值特征、整数编码的分类特征和缺失值；`LGBMRanker` 还支持通过 `group` 表达学习排序的查询组。因此它可以接收多个不同 Family 的数值信号，但前提仍是候鸟先生成固定列名、固定顺序和共同样本键的 Feature Matrix。

官方资料：

- [LightGBM Dataset API](https://lightgbm.readthedocs.io/en/latest/pythonapi/lightgbm.Dataset.html)
- [LightGBM LGBMRanker API](https://lightgbm.readthedocs.io/en/stable/pythonapi/lightgbm.LGBMRanker.html)
- [LightGBM Parameters](https://lightgbm.readthedocs.io/en/latest/Parameters.html)

### 7.3 建议的聚合家族拆分

不建议建立一个模糊的 `lightgbm_anything` 家族。建议至少分为：

```text
lightgbm_cross_sectional_regression
  目标：预测连续的未来相对收益

lightgbm_cross_sectional_ranker
  目标：以每个 decision_date 作为 group，学习截面排序
```

回归与 LambdaRank/Rank-XENDCG 的训练目标不同，应视为不同 Aggregation Family，而不是同一家族的普通参数变化。

每个 Family 下再发布保守参数 Variant，例如：

```text
conservative_v1
regularized_v1
```

具体 `num_leaves`、`max_depth`、`learning_rate`、迭代次数、列采样和早停规则必须版本化，不能在回测后随意调到表现最好。

## 8. LightGBM 不能绕过的研究门禁

在从 Planned 改为 Available 前，至少需要：

1. 精确 PIT Feature Matrix；
2. Feature Schema Artifact；
3. Target Artifact 和标签可得时间；
4. Expanding/Rolling Walk-Forward Policy；
5. Embargo/Purge 或等价的重叠标签隔离规则；
6. 训练、验证、测试和最终 OOS 的不可变区间；
7. 重训频率和最小训练样本；
8. 随机种子、线程数、LightGBM 版本和依赖锁；
9. Fitted Model Artifact；
10. 特征重要性只作为解释证据，不作为无约束反复筛因子的入口；
11. 与等权、线性聚合和 Single Signal 的同期基线比较；
12. Product 只读取冻结模型，不在 GET 或推荐请求中临时重训。

LightGBM 是合理的候选模型，不应仅凭其在其他场景的声誉直接视为候鸟中的有效聚合器；是否有效仍由候鸟自己的严格样本外证据决定。

## 9. 本轮建议确认

### Q1：Family 的必要且充分边界

建议确认：同一公式/算法、同输入角色、同输出语义、同方向和研究假设，仅已声明参数不同，才属于同一 Family。

### Q2：多输出 Node 的每个可独立选择端口分别归属 Feature Family

建议确认：Node 只负责计算打包；Family 属于可独立进入后续加工的 Feature/Signal Definition。Companion Diagnostic Port 可以不建立独立 Family。

### Q3：开放聚合器的边界

建议确认：系统应支持 `Open Numeric Feature Set` 聚合器，允许输入任意已选的标量、定长向量和事件分数；输入实例经过显式 Feature Assembly 后冻结为二维矩阵。它不直接消费原始文本、图片或未对齐事件。

### Q4：LightGBM 的 Family 拆分（已由后续专项确认）

已确认回归预测和学习排序属于不同 Family。v0.21 的 `lightgbm_ranker` Planned 身份保留在迁移血缘中，但 v0.22 首个 available Family 为 `lightgbm_cross_section_rank_regression`；LambdaRank 继续保持独立 planned。

### Q5：v0.22 首版 LightGBM 收敛范围（已确认）

已确认首版只实现 `lightgbm_cross_section_rank_regression` Family：接受常规数值标量 Feature，在共同 `(decision_date, asset_id)` 样本键上组装固定矩阵，回归连续中心化的未来横截面排名，并输出连续 Final Signal。向量、文本模型、LambdaRank 和其他 Objective 暂时保留 planned。

### Q6：Target Variant 与 Hyperparameter Preset 是否保持独立选择轴

建议沿用 v0.21 语义：用户可以选择同一 Family 下的多个 Target Horizon 和多个已发布超参数 Preset；编译器只展开用户明确选择且兼容的组合，每个组合形成独立 Aggregation Instance 和实验分支。
