## 1. 版本目标

v0.22 的核心改动，是将 v0.21 固定的 `Factor → Signal → Model` 结构改造为：

```text
原始数据
  ↓
加工层 1
  ↓
加工层 2
  ↓
加工层 3
  ↓
聚合前信号集合
  ↓
信号聚合层
  ↓
Final Signal
  ↓
横截面策略
  ↓
可选 Defense Timing Policy
  ↓
最终目标仓位、Experiment、Product
```

三个加工层不是三种固定算法类型，也不再分别代表 Factor、Signal 和 Model。任意加工层都可以包含公式、统计方法、规则、机器学习模型、Pattern Detection 或 News Analysis。每个可发布信号的线路由研究者依据经济意义或既有研究显式设计，系统不进行随机组合、自动特征搜索或隐式线路生成。

Raw Input 是三个加工层之前的独立 Source，不计入三层加工深度。第一加工层的真实节点直接消费 Raw Input；Raw Input 若需要原样进入后续层，则通过零拷贝 Source Projection 成为第一加工层的可用输出，再按相同透传规则逐层传递。

## 2. 已确认的核心原则

### 2.1 层数由系统目录决定

- 用户无权在前端添加、删除或重新排列加工层。
- v0.22 当前设计三个加工层，因为现阶段最长的预期信号加工路径需要三层。
- 未来如研究需求超过三层，应通过新版本的后端契约、目录和前端共同升级，而不是由用户临时创建层。
- 每个加工层及其中的节点都由系统预先设计，整体交互类似一棵版本化的“天赋树”。

### 2.2 双向选择

系统同时支持两种研究入口：

1. 从上游向下选择：用户在前一层的选择会约束后一层的合法选项；真正不兼容的选项置灰且不能选中。
2. 从聚合前信号反向选择：用户直接选择希望进入聚合的最终信号，系统自动追溯其完整祖先血缘，点亮并选择所需的原始输入和各层加工节点。

两种入口必须编译成同一份规范化 Research Graph，不能产生语义不同但看似相同的研究分支。

#### 聚合输入只由第三加工层决定

- 聚合器的直接输入，只取决于用户在加工层 3 结束时明确选择的信号。
- 加工层 1、2 的选择只决定加工图、合法下游和中间产物，不会自动成为聚合器输入。
- 加工层 1、2 的任何输出若需要直接参与聚合，必须通过零拷贝逻辑透传到加工层 3，再由用户明确选择。
- 因此 `selected_for_aggregation` 只存在于加工层 3 的输出选择中。

#### 到达聚合层不等于能被聚合

所有 Raw Input 和各加工层 Output 都可以通过 Source/Layer Projection 抵达加工层 3，并在聚合候选区查看。对每个输出分别记录：

```text
reachable_at_aggregation       # 已抵达聚合候选区
compatible_aggregator_keys    # 当前能合法接受它的聚合器
selected_for_aggregation      # 用户是否明确选入某个聚合实例
```

没有兼容聚合器的输出仍可查看、追溯和导出，但在当前聚合器上下文中置灰，不能进入实例。能否聚合是 `Output Contract × Aggregation Input Policy` 的关系，不是输出自身的永久属性。

### 2.3 显式线路，不生成随机组合

- 每个聚合前信号都有明确的研究含义、输入依赖、参数、实现和输出契约。
- 系统不会因选择了 A、B、C 就自动生成 `A+B`、`A+C`、`B+C` 或其他组合。
- 一个需要多个输入的加工节点必须在目录中显式声明完整依赖和输入角色。
- 用户选择的是已设计好的节点或精确绑定的节点实例。

#### 人工构造的类神经网络结构

三个加工层和一个聚合层在拓扑形态上类似前馈神经网络，但不进行随机连接、自动结构搜索或自动特征生成：

- 每个节点只读取上一加工层的输出；
- 上一层的任意兼容输出都可以成为下一层节点的输入；
- 每条实际边都由研究者在版本化目录中明确设计；
- 同一加工层的节点互不依赖、互不改变；
- 每层可以并行执行，完成后再进入下一层；
- 聚合层只读取加工层 3 中明确选入聚合的信号。

Pattern Detection 示例：

```text
Raw Input：open / high / low / close
                     ↓
加工层 1：body / range / upper_shadow / lower_shadow
                     ↓
加工层 2：pattern occurrences / pattern type / local confidence
                     ↓
加工层 3：pattern_count / pattern_quality / pattern_state
                     ↓
聚合层：与其他已选信号共同生成 Final Signal
```

#### 每层保留 Family → Variant 层级

v0.21 的家族归纳必须保留并推广到三个加工层：

```text
Processing Family
├─ Parameter Variant A
├─ Parameter Variant B
└─ Parameter Variant C
```

- 相同经济含义或相同加工方法、仅参数不同的元素属于同一个 Family；
- 每个 Variant 冻结精确参数，并拥有独立的运行、Payload、诊断和血缘身份；
- Family 用于研究分类、前端折叠和同家族参数稳定性诊断，不替代 Variant 身份；
- 反向选择终端信号时，系统点亮精确 Variant，同时展开并置顶其 Family；
- 透传保留原 Family、Variant 和生产层身份，不在后续层创建新家族；
- 聚合器接收的是精确 Variant Output Port，不是模糊的 Family。

前端先展示 Family 卡片，再展开合法的参数 Variant。已选 Family 和 Variant 分别置顶；Family 只要存在至少一个合法 Variant 就保持可展开，所有 Variant 均不合法时才整体置灰。

同一规则适用于聚合层：v0.21 的 Model Family 映射为 Aggregation Family，不同参数、权重或训练 Preset 作为 Aggregation Variant 展示和运行。

### 2.4 聚合层取代固定 Model 层

- “Model”不再表示某个固定层级，因为模型可以出现在任意加工层。
- 最终层称为 `Aggregation Node / 信号聚合节点`。
- 聚合方法可以是等权、固定权重、投票、规则、回归、排序模型或其他训练型模型。
- 每个实验分支只能包含一个聚合实例、一个横截面策略实例，以及零个或一个防御择时策略实例。
- Workspace 可以同时选择多个合法聚合方法和多个策略；每一个合法组合形成独立实验分支。
- 一个聚合实例必须能够接受当前所有选中的聚合前信号；不能静默丢弃不兼容输入。

### 2.5 标准化 Final Signal

无论聚合器内部方法如何，最终输出必须是一个有统一方向和横截面排名意义的数值型变量。建议最低字段为：

```text
decision_date
asset_id
final_signal_score
direction
rankable
known_at
confidence          # 可选
missing_reason      # 可选
```

策略层只消费 Final Signal，不依赖上游是技术面、基本面、新闻、图形识别还是机器学习。

### 2.6 防御择时独立于横截面排序

- 防御择时不是加工图或聚合器的一部分。
- 它是每个横截面策略实例的可选配置。
- 横截面策略先产生风险资产内部归一化权重；防御策略再决定投入横截面组合的总资金比例。
- 剩余资金交给单独版本化的 Defensive Allocation Policy。

```text
cross_sectional_weight(asset)
    × risk_budget
    = final_risky_weight(asset)

defensive_budget = 1 - risk_budget
```

## 3. 术语

| 术语 | 定义 |
| --- | --- |
| Raw Input | 价格、成交量、基本面、新闻、图像等原始输入发布物 |
| Processing Node | 任意加工层中的公式、规则、统计方法或模型 |
| Feature Output | Processing Node 的输出，可为多种结构 |
| Pre-Aggregation Signal | 可以直接进入聚合器的标量或向量信号 |
| Aggregation Node | 将全部选中信号聚合为一个 Final Signal 的节点 |
| Final Signal | 具有方向和横截面排名意义的标准数值输出 |
| Strategy | 将 Final Signal 转换为风险资产内部权重的横截面规则 |
| Defense Timing Policy | 输出风险资产总预算的可选策略 |
| Defensive Allocation Policy | 将剩余预算映射到现金、短债或防御资产篮子 |
| Research Graph | 某次研究选择编译出的完整、有向、无环、版本化计算图 |

## 4. 三层加工与信号透传

### 4.1 用户提出的语义

每个加工层都允许上一层已有信号原封不动地继续向下，使原始信号和任何层新产生的信号最终都能进入聚合前信号集合。

### 4.2 推荐实现：零拷贝逻辑继承

应保留上述用户语义，但不应在每层重复生成相同数据集或伪造新的计算节点。

推荐实现：

- 信号第一次生成时发布唯一 Payload Artifact。
- 后续层只建立 `carried_forward / 逻辑继承` 可见性，不复制 Payload。
- 在前端显示“继承自加工层 N”，并可查看原始生产节点。
- 导出后续层时，Manifest 可以引用同一 Artifact ID 和 Content Hash。
- 编译器只把真实加工节点写入计算 DAG；透传关系写入 Layer Projection，不作为计算依赖。
- 缓存、物化和血缘不会因为跨层显示而重复。

这样可以继续使用同一份数据映射，同时避免：

- 同一信号被发布三次；
- 血缘中出现没有经济意义的 passthrough 节点；
- 存储和导出重复；
- 因层数变化导致信号身份和指纹无意义变化；
- 诊断时把同一信号误认为三个不同信号。

### 4.3 已确认的透传选择语义

透传只继承“在后续层可用”和“当前研究图中已激活”的状态，不继承“直接进入聚合器”的状态。聚合输入只由加工层 3 的显式选择决定。该规则已确认。

## 5. 双向选择的规范化模型

### 5.1 选择来源

每个选择应记录 provenance：

```text
explicit_upstream       # 用户从上游正向选择
explicit_terminal       # 用户直接选择聚合前信号
required_ancestor       # 因终端选择自动纳入
carried_forward         # 零拷贝透传到后续层
```

### 5.2 规范化编译

建议编译流程：

1. 读取 Asset Context、Frequency、数据能力和目录版本。
2. 合并用户显式选择的上游节点与终端信号。
3. 对终端信号求祖先闭包。
4. 验证所有显式上游选择与祖先闭包不存在冲突。
5. 计算每一层的真实加工节点与逻辑透传信号。
6. 读取加工层 3 中 `selected_for_aggregation=true` 的精确输入集合。
7. 验证选中的每个聚合器能够接受该集合中的全部信号。
8. 为每个聚合器 × Strategy × Defense Policy 生成独立分支。
9. 对规范化图、精确参数、输入角色和版本生成 Semantic Fingerprint。

### 5.3 前端显示

- 所有已选择元素置顶。
- `explicit_*` 使用主选择色。
- `required_ancestor` 使用血缘自动纳入色，并显示由哪些终端信号需要。
- `carried_forward` 使用继承标记，显示最初生产层。
- 真正不兼容的元素置灰并显示 Reason Code。
- 取消终端信号后，只移除不再被任何终端信号需要、且没有被用户显式选择的祖先。
- 被多个终端信号共享的祖先只显示一次，并显示下游引用数量。

## 6. 数据契约

### 6.1 两端严格、中间开放

系统不强制所有中间加工数据使用统一数学表格，但所有跨节点边界都必须存在最小技术契约。

#### Raw Input 严格契约

- 数据来源和 Snapshot；
- 原始格式及 Schema；
- Asset/Issuer/Document 身份；
- Event Time、Known At、Effective Time；
- 修订和缺失语义；
- Content Hash 与 Lineage。

#### 中间 Payload 最小信封

```text
payload_kind            # table/event_stream/document/image/tensor/vector/model/blob
media_type
schema_or_shape
serializer_version
entity_scope
event_time_semantics
known_at_semantics
storage_location
content_hash
object_or_row_count
quality_status
producer_node_artifact_id
```

系统可以不解释 Payload 的数学含义，但必须能验证身份、格式兼容、时间语义、完整性和血缘。

#### Pre-Aggregation Signal 严格契约

首版支持：

- `scalar_signal`：每日期、每资产一个数值；
- `vector_signal`：每日期、每资产一个有版本定义的向量。

必须声明方向、标准化、适用资产、频率、Known At、缺失原因、横截面可比性。向量还必须声明维度、顺序、Shape 和 Schema Version。

#### Final Signal 严格契约

必须收敛为每日期、每资产一个可排名数值，并满足第 2.5 节的标准输出。

### 6.2 每层导出

- 结构化数值优先导出 Parquet，并提供数据字典和 Manifest。
- 文档、图像、向量或模型按原生格式导出，外层使用 ZIP/Manifest 描述。
- 透传信号不重复存储；导出 Manifest 引用原 Artifact。
- 每次导出冻结节点、输入、Schema、时间语义、Content Hash 和完整血缘。

## 7. 聚合实例与实验分支

### 7.1 聚合实例身份

```text
Aggregation Instance
= aggregation_method_version
+ exact_direct_input_signal_set
+ input_roles_and_order
+ parameters
+ frequency
+ asset_context
+ training_target_and_policy       # 如适用
+ fitted_model_artifact            # 如适用
```

同一个方法使用不同输入集合时，必须形成不同实例。聚合器不得静默忽略任何已选输入。

### 7.2 分支规则

若 Workspace 选择：

- 3 个聚合实例；
- 2 个横截面策略；
- 2 个防御策略；

则在全部兼容时形成 `3 × 2 × 2 = 12` 条独立策略分支。每条分支只有一个聚合实例、一个策略和一个防御策略。`none` 也是一个明确的防御策略实例。

实验区间、成本场景和现有固定 Cell Matrix 在策略分支之后继续展开，具体矩阵规模需要在实施稿中单独控制，避免组合数量失控。

## 8. 防御策略暂行方案

v0.22 先完成可扩展接口、对照实验、血缘和展示，不把未经专项研究的规则宣传为已证明有效。

初始候选（经防御专项设计修订）：

- `none`：风险预算恒为 100%；
- `fixed_20`：沿用固定 20% 防御；
- `ma200_v1`：保留当前 200 日均线策略作为对照；
- `spy_rv20_target15_reserve_v1`：首个 exploratory baseline；基于 SPY 最近 20 个完整日收益的年化实现波动率，`risk_budget = clip(15% / RV20, 25%, 100%)`，不加杠杆、不加平滑，暂配 reserve-only allocation。

暂行的通用输出：

```text
decision_date
risk_budget
defensive_budget
regime
reason_code
known_at
policy_artifact_id
input_artifact_ids
```

Timing Policy 与 Defensive Allocation Policy 在后端拆分，前端以已发布 Defense Package 选择。首个波动率基线的窗口、参考波动率与预算上下限已经冻结；换手率与 MA+波动率复合规则保持 planned，不能以最终回测收益为目标反复选择参数。

## 9. Experiment 与 Product 展示

Experiment 详情和 Product 详情必须明确显示：

- Final Signal 身份与 Artifact；
- 聚合方法、参数和实现版本；
- 直接进入聚合器的全部 Pre-Aggregation Signals；
- 如为训练型聚合器，显示 Target、训练窗口、重训规则和 Fitted Model Artifact；
- 横截面策略、完整参数和 Target-K；
- Defense Timing Policy；
- Defensive Allocation Policy；
- 数据、Universe、执行、成本和 Benchmark 上下文。

默认详情不展开更上游加工层；用户通过 Lineage/Research Graph 查看完整祖先。

## 10. 与 v0.21 代码结构的迁移关系

v0.21 当前将固定层语义写入多个模块，v0.22 不能只修改 Workspace 页面。

| v0.21 位置 | 当前职责 | v0.22 方向 |
| --- | --- | --- |
| `workspace/catalog.py` | 合并 Factor、Signal、Model、Strategy 目录 | 发布 Processing Node、Signal、Aggregation、Strategy 目录和合法边 |
| `workspace/contracts.py` | 固定 factor/signal/model selection | 改为分层选择、终端信号、聚合实例和选择 provenance |
| `workspace/compiler.py` | Factor→Signal→Model→Strategy 编译 | 编译三层 Research Graph、祖先闭包、透传 Projection 和实验分支 |
| `workspace/options.py` | 按固定上游筛选下游 | 支持双向合法性、反向点亮和 Reason Codes |
| `workspace/preview.py` | 固定层 Compile Preview | 展示规范化图、自动祖先、透传和分支数量 |
| `factor/*`、`signal/*`、`model/*` | 分层计算、发布、诊断 | 逐步抽取为通用 Node Runtime；保留 v0.21 只读兼容适配器 |
| `strategy/*` | 消费 Model Dataset 并产生 Target | 改为消费 Final Signal Dataset，并组合 Defense Policy |
| `experiment/*` | Model/Strategy 固定身份与 Cell Matrix | 使用 Aggregation Instance、Strategy 和 Defense Policy 身份 |
| `product/*` | 保存候选策略、监控和推荐 | 增加聚合器、直接输入信号、防御策略的冻结展示 |
| `lineage/*` | 通用不可变 Artifact 依赖 | 继续作为 v0.22 血缘底座，新增节点运行和 Payload 角色 |
| `signal/export_jobs.py` | 信号批量导出 | 泛化为 Layer/Node/Final Signal 异步导出 |
| 前端 Workspace Context | 固定五层 key 数组 | 改为三层选择、终端信号、聚合器、选择 provenance 和图预览 |

### 10.1 兼容原则

- 不覆盖、不重写 v0.21 已发布 Artifact。
- 历史 Experiment 和 Product 保持只读可追溯。
- 通过兼容适配器把现有 Factor、Signal、Model 映射为 v0.22 图节点视图。
- 新的 v0.22 原生研究使用新契约、新 Artifact Type 和新迁移。
- 是否允许 v0.21 草稿自动升级为 v0.22 草稿，需要在迁移设计阶段单独决定；不能静默转换并保存。

## 11. 已确认的交互与图约束

### 11.1 透传区分“加工激活”与“直接进入聚合”

推荐把状态拆开：

```text
active_in_graph          # 已在当前研究图中生产或作为依赖使用
available_in_stage       # 通过零拷贝透传，在当前层可继续使用
selected_for_aggregation # 用户明确要求它直接进入聚合器
```

用户在加工层 1 选择 A 后，A 应自动在加工层 2 和 3 显示为“已激活、可继续使用”；但 A 不会因此自动成为聚合器直接输入。只有用户在加工层 3 明确勾选 A，才设置 `selected_for_aggregation=true`。

这一拆分可以避免 A 仅用于加工 B 时，聚合器意外同时收到 A 和 B。该规则已确认。

### 11.2 正向约束与反向自动补全采用三态交互

存在一个潜在冲突：

- 正向模式要求上游选择决定下游哪些选项合法；
- 反向模式允许点击终端信号后自动补齐尚未选择的祖先。

推荐区分三种下游状态：

1. `selected-compatible`：当前上游已完整满足，可直接选择；
2. `available-with-ancestors`：当前未选齐祖先，但没有冲突；可以点击，点击后自动补齐并提示；
3. `incompatible`：资产、频率、数据能力或显式排斥条件冲突，置灰且不能点击。

这比简单的“未满足就全部置灰”更能同时支持双向选择。

采用统一页面上的三态交互，不额外拆成两个模式。该规则已确认。

### 11.3 一个 Signal Version 只有一张确定生产图

推荐：一个具体 `Pre-Aggregation Signal Version` 只能绑定一条确定的生产图。如果经济含义相同但加工路径、算法或参数不同，应发布不同 Signal Version，分别诊断和选择。

该身份规则已确认。

### 11.4 禁止加工层内节点互相依赖

真实计算依赖必须从前一加工层进入后一加工层，保证“天赋树”易读、编译简单、不会出现同层隐式顺序。较早层信号通过零拷贝透传后，逻辑上成为上一层可用输入。需要连续两次处理时，应分别放入两个加工层；若三层不够，再通过版本升级增加层数。该规则已确认。

## 12. 已确认的节点与数据边界

### Q1：一个 Processing Node 能否产生多个具名输出

Pattern 示例中的一次蜡烛结构计算可能同时得到 `body`、`range`、`upper_shadow` 和 `lower_shadow`。有两种方案：

1. 每个输出都是一个独立 Processing Node，结构简单但会重复读取和计算；
2. 一次 Node Run 可以产生多个具名 Output Port，每个输出可独立进入后续节点、诊断和导出。

推荐方案 2：Node 是计算单元，Output Port 是天赋树中可连接、可选择的元素；多个端口共享一次运行发布物，但各自具有名称、Schema、Semantic Role 和 Content Hash。

该规则已确认。

### Q2：异构数据连接是否必须经过显式对齐节点

相邻层可能同时存在资产日频表格、新闻事件、Embedding、图像特征和市场级状态。即使它们都位于上一层，也不能直接假定时间、实体和 Shape 已兼容。

推荐：只有端口契约兼容时才能直接连接；否则必须存在显式的 Alignment/Adapter Node，例如：

- 新闻事件按 `known_at` 聚合为资产日频信号；
- 文档 Embedding 按资产和决策窗口池化；
- 市场级状态广播到资产截面；
- 日频数据对齐到周频决策日；
- 不同向量 Shape 通过明确模型转换。

对齐不能由运行时静默完成，否则无法审计未来数据、聚合窗口和实体映射。

该规则已确认。

### Q3：普通加工节点是否全部使用固定输入绑定

推荐：除最终 Aggregation Node 外，三个加工层中的每个具体 Node Version 都冻结输入端口和来源语义；若同一算法支持不同输入集合，则发布不同 Node Instance/Version。用户不能在前端为普通加工节点任意接线。

Aggregation Node 是唯一允许把用户在加工层 3 选择的完整信号集合绑定为实例的节点类型，并且必须验证它能接受全部输入。

该规则已确认。

### Q4：取消被下游依赖的上游节点时如何处理

推荐：如果 A 正被已选下游 B 或终端信号依赖，普通点击不能直接取消 A。前端应显示“由 B、C 需要”并提供显式的级联操作：

```text
同时取消 A 及受影响的 2 个下游选择
```

执行级联前展示将被移除的节点和最终聚合输入；自动纳入的祖先在不再被任何下游需要、且没有其他显式选择来源时自动清理。不能在无提示情况下静默级联，也不能留下依赖不完整的草稿。

该规则已确认。下游已经存在对应选择时，上游普通选择控件应被锁定；用户只能通过显示完整影响范围的显式级联取消操作修改该链路。
