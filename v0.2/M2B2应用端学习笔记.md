# M2B2 应用端学习笔记

## 为什么“抓到了数据”还不等于“数据可用于回测”

抓取层只证明某个时间点从某个入口获得了哪些字节。它不能保证字段完整、日期对齐、复权正确或没有未来信息。因此 M2B2 只生成 source snapshot；M2B3 的解析、验证和发布通过后，数据才成为正式研究输入。

这类似收货流程：snapshot 是封存原包装和快递单，canonical dataset 是验货、统一规格并签字入库。直接拿未验货包裹投入生产，出现问题时很难定位责任。

## 为什么 Yahoo 和 FRED 的“原始”含义不同

- FRED 适配器直接发 HTTP 请求，因此能保存服务器返回的原始字节。
- yfinance 是第三方 wrapper，它先替我们处理供应商响应。系统能忠实保存的是 wrapper 交付给我们的未清洗表格，而不是它内部收到的所有网络报文。

这种限制必须写进元数据。清楚承认数据能力边界，比用“raw”一词制造过度承诺更可靠。

## 为什么交易日历也要版本化

周末规则很简单，但交易所假日、特殊休市和提前收盘并不简单。日历库也可能修正规则。如果只在代码里临时询问“某天是否开市”，以后可能无法复现当时的执行日期。

冻结日历版本后，每次实验可以明确回答：使用哪个库版本、覆盖哪段日期、当天几点开盘和收盘。

## 检查类似采集设计时可以问

1. 保存的是供应商字节、wrapper 输出，还是已经清洗的数据？命名是否诚实？
2. 请求参数、依赖版本、请求时间、完成时间和 as-of 是否完整？
3. 重复执行会复用相同 artifact，还是悄悄覆盖旧数据？
4. 假日和提前收盘由专业日历处理，还是手写周一到周五规则？
5. 网络成功是否被错误等同于数据质量通过？
