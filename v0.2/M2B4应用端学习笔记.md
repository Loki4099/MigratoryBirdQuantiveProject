# M2B4 应用端学习笔记

## 为什么页面使用一个 overview 接口

Data 页面需要同时解释 source、dataset、bundle 和 eligibility。如果浏览器分别请求很多接口，用户可能看到不同时间点的零散结果，错误和空状态也更难统一。一个只读 overview 是面向页面的“阅读模型”，减少前端拼装，但不会改变底层对象仍然分表、分版本的事实。

优点是页面契约简单、一致；代价是响应比单对象接口大。因此当前限制源快照数量，未来对象增长后可增加分页和详情接口，而不改变正式计算链。

## 为什么浏览页面可以显示 latest，正式计算却不可以

浏览者通常想先看当前发布状态，因此 overview 选择最新已发布 bundle 和 eligibility 很合理。但正式研究如果也在运行时选择 latest，同一命令日后可能使用不同输入，无法复现。

所以要区分：

- UI 的 latest 是导航便利；
- 计算的 artifact ID 是研究承诺。

## 为什么“不完整”不是“错误”

一个新环境可能尚未发布 bundle 或 eligibility，但 API 和数据库本身工作正常。这时用 `partial` 告诉用户链路尚未齐备，比报系统错误更准确。真正的数据质量 error、失效 artifact 或服务不可用才应进入 error。

## 检查类似设计时可以问

1. 页面展示的数据是后端已发布事实，还是浏览器临时重算？
2. latest 只用于浏览，还是偷偷进入了正式计算？
3. 空数据、链路不完整、质量警告和系统错误是否被区分？
4. 前后端字段是否来自同一份 OpenAPI 契约？
5. 查询是否只读取 published 版本，并有真实数据库测试？
