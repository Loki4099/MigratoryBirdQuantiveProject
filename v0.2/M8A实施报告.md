# M8A 实施报告：不可变比较队列与产品排行

## 1. 本阶段交付

M8A 把 Experiment 的已接受结果组织成可审计的 Comparison Cohort，并在该 cohort 内提供单指标策略产品排行。它没有引入综合评分，也没有把排名写回 Strategy、Model、Signal 或 Factor。

主要交付包括：

- 版本化统一暖机政策；
- 类型化、不可变的 Comparison Cohort 及成员关系；
- 应用服务与数据库触发器的双层严格上下文校验；
- 单指标 competition rank 计算；
- 只读产品排行 API；
- Dashboard 与 Experiments 的中英文排行界面；
- Python 单元测试、真实 PostgreSQL 集成测试、前端测试和浏览器检查。

## 2. 为什么先建立 Cohort

产品排行最危险的错误不是排序算法，而是把不同市场假设下的结果排在一起。例如 2 bps 与 10 bps、不同回测终点、不同数据快照或不同指标口径，即使都叫“Net Sharpe”，也不能直接比较。

常见选择有两种：

1. 页面临时筛选：开发简单、交互灵活，但筛选条件容易遗漏，刷新后也很难证明当时比较了什么。
2. 发布不可变 cohort：需要更多表、校验和版本管理，但候选集合与共同假设可以追溯，并能被 API、页面和未来报告共同复用。

v0.2 选择第二种。Cohort 不是“表现优秀的策略清单”，而是“在同一模拟市场环境中允许被放在一起比较的结果集合”。同一个策略在不同成本或区间下会属于不同 cohort。

## 3. 为什么同时做应用校验和数据库校验

应用服务负责给出清楚的错误信息、构造 fingerprint 并复用完全相同的发布物；数据库触发器负责守住最后边界，避免其他脚本、未来 CLI 或维护操作绕开服务写入错配成员。

优点是正式比较边界不依赖某一个调用入口。代价是规则存在两处表达，因此修改比较语义时必须同步更新服务、触发器和测试。这里值得承担这项维护成本，因为错误 cohort 会污染所有下游排名和比较结论。

## 4. 为什么排名动态计算

名次取决于 cohort、所选 metric、undefined 处理和排序方向。把“当前第几名”永久写入 Result，会在加入新结果或切换指标后立即过期，并让同一结果出现多个互相冲突的永久名次。

因此 M8A 只保存不可变候选集合和原始指标，读取时动态计算：

- 用户必须明确选择一个指标；
- 并列值共享相同名次；
- undefined 保留状态和原因，但不参与名次；
- 最大回撤按数值较高（回撤较浅）为优；
- 不计算黑箱综合分。

如果未来有监管、报告签发或客户留档需求，可以增加 Ranking Snapshot，保存“特定 cohort + 特定 metric + 特定时点”的完整视图；这与给 Result 增加永久排名字段不同。

## 5. 页面应如何理解

页面先展示共同指标区间、SPY 产品基准、单边成本、币种、统一暖机与候选数量，再展示所选指标的排名。用户切换指标时，候选集合和市场上下文不变，只改变观察角度。

排名回答的是：“在这个已经发布的历史模拟环境中，按照这一项指标，候选结果如何排序？”它不回答策略未来能否盈利，也不替代对回撤、成本、稳定性、模型逻辑和完整实验审计的检查。

## 6. 何时重新评估

出现以下需求时，应重新检查当前设计：

- 需要对两个 cohort 做并排但不混排的受控比较；
- 需要保存正式对外报告中的历史排名快照；
- 需要引入不同币种、非 SPY 产品基准或不同市场日历；
- 需要按多个指标生成透明、预注册的决策规则；
- cohort 成员数量大到动态查询出现可测量的性能瓶颈。

其中前两项分别属于 M8B Compare 和未来 Ranking Snapshot，不应通过放宽 M8A 的严格上下文规则解决。
