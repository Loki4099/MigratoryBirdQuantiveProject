# M1C学习笔记：为什么要区分Fingerprint与Content Hash

## 1. 它们分别负责什么

Semantic fingerprint回答：“这是不是同一个研究定义或同一组输入？”

Content hash回答：“这次实际发布出来的内容是否逐字节意义一致？”

Lineage manifest hash回答：“这个结果依赖的完整上游版本组合是否一致？”

三者共同使用，才能既复用相同任务，又发现实现不确定或上游被换掉的问题。

## 2. 只保存一个hash的风险

如果只hash配置，同一配置因代码错误产生两份不同结果时无法发现。如果只hash结果，则无法判断结果为什么不同，也不能在计算前复用已有发布。若hash中混入UUID或创建时间，每次运行都会不同，失去幂等意义。

## 3. 常见替代方案

- 只用数据库自增ID：简单，但ID不说明语义和内容是否相同；
- 只用文件checksum：擅长检查文件损坏，不足以表达研究输入身份；
- Git commit作为版本：能定位代码，但不能独立描述数据、参数、模型和策略组合；
- 本项目三类hash：结构稍复杂，但问题定位和复用能力最完整。

## 4. v0.2为什么这样选择

研究平台最怕“名字一样、内容已变”和“结果不同却不知道哪里变了”。v0.2将语义、内容、依赖分别固定，并规定相同semantic fingerprint却出现不同content hash属于确定性故障，需要停止发布并调查。

## 5. 何时重新评估

当数据量大到不能把所有发布行直接纳入hash时，可改为分块Merkle tree或对象存储manifest；概念仍保持不变。跨CPU/库版本需要容差比较时，应增加独立数值近似报告，不能把近似相等伪装成hash相等。

## 6. 如何判断它工作正常

- 同一目录连续bootstrap两次，第二次应显示`reused: true`且所有hash不变；
- 修改有语义的配置后，fingerprint应变化并要求新版本身份；
- 直接修改published artifact应被数据库拒绝；
- invalidated上游仍被保留，下游显示tainted；
- `lineage show`应能展开根对象的完整依赖清单。

## 7. 只需记住的术语

- Fingerprint：研究身份；
- Content hash：实际内容校验；
- Manifest：完整依赖快照；
- Immutable：发布后不可改；
- Idempotent：相同请求重复执行仍得到同一正式结果；
- Tainted：内容保留，但因上游失效而不再适合作为正式结果使用。
