# M1D学习笔记：为什么API只读且前端不重算

## 1. 这项设计负责什么

只读API负责让页面和外部研究工具安全地查看已经发布的对象。前端负责筛选、导航、绘图和解释状态，不负责重新计算因子、收益或hash。

## 2. 如果浏览器也能计算或发布

同一指标可能在Python和TypeScript中出现两套实现，舍入、缺失值和日期规则容易不同。浏览器刷新、断网或误操作也不适合承担长任务和原子发布。更重要的是，写入接口一旦开放到网络，就需要账户、权限、CSRF、审计和更复杂的安全设计。

## 3. 常见选择及优缺点

- 前后端都计算：交互快，但最容易出现两个真相；
- API既读又写：使用方便，但权限和误操作风险更高；
- 当前只读API＋CLI写入：浏览器安全、研究口径唯一，代价是高级用户发布时需要命令行；
- 未来认证写API：适合多人和远程部署，但必须在真实需求出现后再承担复杂度。

## 4. v0.2为什么这样选择

当前是单机研究工具，最重要的是研究结果一致和可追溯，而不是多人在线协作。CLI更适合运行、发布、失效和重建；页面更适合查看和比较。

## 5. 何时重新评估

出现多人协作、远程任务提交或非开发用户必须启动研究时，再设计认证、角色、写API和任务队列。不能简单地把现有CLI函数暴露为HTTP POST。

## 6. 如何判断实现正常

- OpenAPI paths只有GET；
- POST artifact返回405；
- 页面数值来自API响应，不存在重复金融公式；
- API错误显示明确状态，而不是页面用0补齐；
- tainted/invalidated仍可查看，但带醒目标识；
- 语言切换不改变artifact ID、hash和研究上下文。

## 7. 只需记住的术语

- Read-only API：只能查询的接口；
- OpenAPI：前后端共享的接口说明书；
- Generated types：根据说明书自动生成的TypeScript类型；
- ETag：判断响应是否变化的缓存标识；
- SPA fallback：直接打开前端子路径时仍返回React入口页。
