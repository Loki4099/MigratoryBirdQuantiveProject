# M3B 应用端学习笔记

## 为什么计算公式还需要一个 Engine Version

公式说明“应该怎么算”，Engine Version 说明“实际上由哪份代码和环境算”。同一公式在依赖版本、数值库或实现细节变化后可能出现微小差异，因此正式结果必须同时记录 Git commit、依赖锁、数据库结构和数值环境。优点是争议时能重建现场；代价是每次正式代码升级都要发布新的 engine version。

## 为什么一次运行会产生 28 个 Dataset

20 日收益和 252 日收益虽然属于同一测量概念，但参数、暖机要求和下游用途不同。独立数据集使 Signal 能准确引用一个实例，也使错误和质量问题容易定位。代价是对象数量更多，但数据库和血缘管理正是用来承担这部分复杂度的。

## 为什么要求统一暖机

如果每个参数从自己的最早可算日期开始，短窗口会比长窗口拥有更长样本，横向比较容易混入区间差异。v0.2 用目录中最长需求统一 eligibility 暖机，再让全部 variant 从同一天输出。优点是可比；代价是会舍弃前面一段本可供短窗口使用的数据。

## 为什么必须先全部算完再发布

假设第 27 个公式失败，而前 26 个已经成为正式数据，下游会看到一个看似完整、实际残缺的研究批次。M3B 先完成所有计算与检查，再用一个事务发布；成功就是全套，失败就是零套。这叫原子性。

## 使用或审查类似设计时可以问

1. 结果是否绑定了精确数据版本、有效资产、区间和代码版本？
2. 暖机区间是否足够，并且各测量是否从统一起点输出？
3. 公式失败时会留下部分正式结果吗？
4. 重复运行会复用原结果，还是悄悄制造重复对象？
5. 价格复权、raw volume 和时间顺序是否写成明确规则？
6. 这些值只是测量，还是已经被错误地赋予了方向和策略收益含义？
